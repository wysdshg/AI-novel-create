## 二、命名与匹配机制（2026-10-04 用户拍板，SK02b/SK03 照此实现）

- **两层身份**：大类（52+1 清单）+ 子事件（可选，2~6 字具体形态，如 学院大比/宗门大比/炼丹大会）。
- **判类输出**（每弧）：`{大类(必填), 子事件(可选), 依据一句话, 置信度}`。
- **模板名**：`大类--子事件`（如 擂台大比--学院大比）；无可辨识子形态时用大类单名（开山建派，**不造「开山建派--建派」这种同义退化**）；同 (大类,子事件) 下合不拢的多张 → `-1/-2` 变体。
- **匹配/检索**：①(大类,子事件) **精确匹配优先**（用户指定的第一种）→ ②同大类其他子事件（**仅限检索参考，组装不适用**）→ ③副标签。生成时的口述检索同样先过这条链；**组装链路只认精确键，落单弧走单弧模板**。
- **子事件词表管理**：判类产出的新子事件名进「待审区」，用户拍板后固化（防「炼丹大赛」式乱造名）；近义子事件（学院大比 vs 学院大比风波）判类后合并提案。

### 踩坑

- 🔴 **argparse dest 是下划线形**：`--dry-run` → `dry_run`。照任务单字面写 `mode == "dry-run"`
  会静默走错分支（我第一版把 `--dry-run` 跑成了 verify）。判断 mode 一律用下划线形。
- 🔴 **JSON 列在两种访问方式下类型不同**：raw `sqlite3` 读出是 **str**，SQLAlchemy ORM 读出是 **dict**。
  `isinstance(x, str)` 当类型判据会**恰好跳过全部目标行**。统一走 `_as_json()` 归一。
- 🔴 **GBK 控制台**：所有模式用 `_Tee` 双写 UTF-8 日志（沿用 sk01），中文一律读日志文件而非控制台。
- 🔴 **静态池铁律**：`StaticPool` 单连接 + 同连接 `wal_checkpoint(PASSIVE)`，否则写入对其他进程不可见。
  旧 100 的三路向量块必须清（766+486+486=1738），否则成孤儿块且与新库对不上账。
