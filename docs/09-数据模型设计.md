## 0. 设计原则（先定原则，再定字段）

| # | 原则 | 依据 |
|---|---|---|
| P1 | ✅ **能进描述的别结构化** | 品阶（下品~极品）、境界要求、进阶形态（青莲剑歌→九莲剑歌）一律写进 `full_desc`——架空历史/都市题材没有品阶，硬给结构化字段会**误导 AI 硬填** |
| P2 | ✅ **派生值不落库** | 「多章未出现」= `当前章 − last_seen_chapter` 的派生结果，**只展示不入库**（入库必然漂移）。状态只存真实态：存活 / 死亡 / 失踪 |
| P3 | ✅ **主键保持 uuid**（不换 bigint 自增） | 本项目要**导出/合并/回灌**模板库与作品，自增 ID 在合并时必冲突 |
| P4 | ✅ **两档文本**：`summary`（检索/注入用）+ `full_desc`（写作时展开） | RAG 常规做法；注入时给 summary，涉及该实体写作时给 full_desc |
| P5 | ✅ **关系统一走中间表**，各实体表**不存**"持有物/掌握技能"这类引用字段 | 避免双向维护与孤儿（现有 `characters.skills` / `skills.owner_id` 就是反例，本次一并收敛） |
| P6 | ✅ **方向与逆关系进字典表**，不写死在代码 | 「仇敌」对称、「持有物品」「师徒」有方向；逆关系（师徒↔弟子、持有↔被持有）是检索反查的基础 |
| P7 | **注入不抠 token**（100w 上下文） | 见 `03 铁律 17`：prompt 内容不做省 token 式截断，靠**结构化分块 + 排序**保证可读性 |

| `summary` / `description` | text | 摘要 + 详细描述（功效、结构、阵法效果） | 改造 |
| `tags` | json | 标签：开阔 / 比武场地 / 宗门 | **新增** |

> **删除**：`related_ids`（JSON → `entity_relation`）；**❌ 弃用 `map_id`** —— 改用 `parent_id` 树（见下）。
> **删除**：`characters.relationship_network` 式的字符串引用一律不再新增。

#### 为什么是「父地点树」而不是「map_id 平铺」（2026-09-18 用户拍板）

| 问题 | map_id 平铺 | **父地点树（采用）** |
|---|---|---|
| 人界一张图，开局主角在县城、未婚妻在中州大宗门 | 两点相距极远 → **地图太大且稀疏** | ✅ 只渲染顶层（南荒 / 中州 / 西域 / 燕北）；**点中州才展开其内部** |
| 一座城池里地点很多 | 图上的点**互相重合** | ✅ 下钻到城池再看，同级密度可控 |
| 秘境（可能很小但内含大量地点） | 得为它单独开一张 map | ✅ **秘境就是一个地点**，天然可下钻 |
| 「青云演武场」既属于青云宗、又在青云峰内 | map 只能表达"属于哪张图" | ✅ `parent_id` 表达**完整归属链**（青云演武场 → 青云峰 → 青云宗 → 中州 → 人界） |

**坐标语义**：`pos_x/pos_y` 是**相对父地点**的局部坐标（不是世界绝对坐标）。
于是——**任何有子地点的地点都是一张可下钻的地图**，层级不限：
`位面 → 大陆 → 州 → 城池 → 府邸 → 院落 → 房间`。

**渲染约定**（前端）：
1. 父图上按子地点的 `pos` 定位；图标大小按 `size_value` 相对比例；
2. `importance` 决定是否显示标签（次要 = 悬停才显示），**防同名/近距标签重叠**；
3. 面包屑显示归属链（人界 › 中州 › 青云宗 › 青云峰 › 演武场），可逐级返回；
4. 未填坐标的地点落「未定位」区（不阻塞录入）。

**跨层距离（可选能力，非必需）**：沿 `parent_id` 上溯累加各层坐标可估一个粗略距离；
但跨层（厢房 → 中州）的"精确距离"本无意义——**写作时用描述表达「隔了几千里」更自然**。

## 2. 关系层（2 张新表）

### 2.1 `entity_relation` 通用关系（中间表，只存关联不存长文本）

| 字段 | 类型 | 说明 |
|---|---|---|
| `a_id` / `b_id` | varchar(36) | 实体 A / B 的 ID（**联合主键**，另加唯一约束） |
| `a_type` / `b_type` | varchar(16) | 实体类型：`character` / `skill` / `item` / `faction` / `location` |
| `relation_type` | varchar(24) | 关系类型（取自字典表，见 2.2） |
| `meta` | json | 附加信息：**键必须来自固定枚举**——`proficiency`（熟练度）/ `quantity`（数量）/ `holding`（临时/永久）/ `since_chapter` |
| `note` | text | 可选短备注（如「第 12 章夺自周执事」） |
| `created_at` | datetime | — |

**约束与约定**
- `UNIQUE(a_id, b_id, relation_type)` 防重；
- **方向**：字典表声明；对称关系（仇敌 / 同盟 / 兄弟）存一条即可，查询按对称处理；
- **逆关系**：字典表声明（师徒 ↔ 弟子）；**只存一个方向**，反查由字典表翻译，避免"两行数据互相漂移"；
- 规模预判：几百实体 × 平均 5 条 ≈ 数千行 —— SQLite 完全够用（**不引入图数据库**，见 §5）。

### 2.2 `relation_type` 字典表（新）

| 字段 | 说明 |
|---|---|
| `name` | 关系名（师徒 / 弟子 / 持有物品 / 掌握技能 / 隶属势力 / 领袖 / 仇敌 / 盟友 / 位于 / 需要物品…） |
| `symmetric` | 是否对称 |
| `inverse` | 逆关系名（可空） |
| `weight` | 注入权重（排序用：亲属/恩仇 > 同门 > 泛泛之交） |
| `applies_to` | 适用的实体类型对（如 `character→item`），供校验 |

## 3. GraphRAG 注入协议（检索即组装 prompt）

```
种子（本章/本篇要写的实体）
  ← 商讨：extract_mentions(作者问题)
  ← 写作：篇计划 recall_chars ∪ 本章出场角色 ∪ 模板槽位映射出的角色
        ↓
一跳：查 entity_relation（a_id ∈ 种子 ∪ b_id ∈ 种子）
        ↓ 按 relation_type.weight 排序
  · 存活实体 → 注入 summary（人物卡短版 / 物品技能摘要 / 势力概况）
  · **死亡实体 → 只注入「名字 + 关系 + 已死亡」**（如 `小四（表哥，已死亡）`）
        ↓ 二跳（可选）
  · 只有"角色 → 其掌握技能/持有物品"这一级值得展开，且**仅在预算内**
        ↓
分块组装（关键信息前置）：
  ① 本章任务/计划行 → ② 出场角色卡（前置）→ ③ 其技能与物品 → ④ 势力与地点 → ⑤ 关系网摘要 → ⑥ 模板套路参考
        ↓
模板库检索（**独立一条链**）：套路骨架注入末尾，标注「只借鉴结构，禁止照抄专名」
```

**与现状的衔接**：`entity_graph.expand`（一跳扩展）已在商讨链跑通，本次只是把「关系来源」从
`relations`（仅角色-角色）换成 `entity_relation`，并补上物品/技能/势力的注入块。

## 5. 明确不做

- **不引入图数据库**（Neo4j 等）：几百实体用 SQLite 两跳 JOIN 足够，本地单机工具不背这个运维包袱。
- **不做品阶/境界要求/进阶形态的结构化字段**（P1）。
- **不存派生状态**（P2：多章未出现 = 算出来的）。
- **不做全库快照**（沿用单实体粒度的修订历史）。
- 城市题材的"等级"用描述字段表达，不硬设数值化 `rank`。
- **不用 `map_id` 平铺地图**：地点用 `parent_id` 树，层级不限、逐层下钻。
- **不把通用词写成"成品描述"**：条目库只存名词 + 一句话说明（描述一律重写，不抄原文）。

| 4 | 老列是否物理删除 | ✅ **先只弃读**（`characters.skills` / `relationship_network` / `factions.members` / `locations.related_ids` 等标记 deprecated，前端不再读；等前端全切新后再议物删） |
| 5 | 物品/技能是否要修订历史 | ✅ **暂不考虑** —— 丹药/技能一旦落库描述就定死；**可成长物品由作者手动更新**即可（省掉一整套修订链的复杂度）。**新增待议**：见 §7 全局物品/技能尺度库 |

## 7. 全局物品/技能库（拟，独立阶段）——**条目库 + 尺度库双库共存**

### 7.1 为什么要两库（2026-09-18 用户论证，采纳）

「筑基丹 / 洗髓丹 / 灵石 / 御剑术 / 大火球术」是**类型惯例**——读者认知的一部分。
若不给通用词，AI 会一本正经地造出「伐骨丹」「破基丹」「青云术」「大火球诀」——**不是错，是别扭**。
但只给条目（成品描述）又会让所有书长得一样。**两者缺一不可**：

| 库 | 装什么 | 解决什么 |
|---|---|---|
| **条目库** `global_items` / `global_skills` | **通用名词条目**：名称 + 类别 + 一句话通用说明 + 别名（如「筑基丹｜丹药·突破｜助修士破入筑基，通用且廉价」） | 让 AI **优先使用通用词**，不硬造近义词；抽取时**归一化**（各书抽到「洗髓丹」都指向同一条目，不重复写描述） |
| **尺度库** `global_item_scales` / `global_skill_scales` | **类别级设计尺度**：类别 / 功能位 / 强度尺度 / 代价尺度 / 叙事位置 | 让 AI **知道怎么造新的**（本书需要独创物品时，按尺度造，而不是凭空编） |

### 7.2 注入策略（写作时）

```
本章/本篇任务涉及"境界突破"
  → 注入「丹药·突破类」尺度（功能位 + 强度/代价尺度）
  + 通用名词候选（筑基丹 / 洗髓丹 / 破障丹）
  + 要求：优先用通用词；确需独创时按尺度造名，并在备注里说明理由
```

### 7.3 侵权三档（与既有模板库同纪律）

| 内容 | 风险 | 处理 |
|---|---|---|
| **类型惯例词**（筑基丹 / 洗髓丹 / 灵石 / 储物袋 / 御剑术 / 大火球术） | 低——仙侠玄幻的通用设定（类似奇幻的「龙 / 精灵 / 魔法」） | ✅ 收入条目库；**说明一律自己重写**（不抄任何原文） |
| **归纳出的抽象结构**（「丹药用于突破瓶颈」） | 低——思想/方法不受版权保护，表达才受 | ✅ 收入尺度库 |
| **特定作品的独创专名 / 独特体系**（标志性名词与设定组合） | **高** | ❌ **不收录**；若为研究而收，标 `reference_only` 且**禁止注入生成** |

**三条硬纪律**：① 条目库**只存名词 + 一句话通用说明**，**不存任何原文片段/整段描述**；
② 尺度库存结构不存成品；③ 独创专名一律排除，注入只给尺度 + 通用词候选。

### 7.4 落地位置
