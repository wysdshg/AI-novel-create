#### 7.1 弧归并层落地（2026-09-11 晚，DeepSeek V4.1 Flash）

**背景**：用户察觉"切出来的段不像完整篇章"→ 诊断确认是**粒度错位** —— 段（beat）是"事件粒度"，
模板需要的单元是**故事弧**（arc，一个完整套路 = 一个爽点周期，8~15 章）。缺的就是这一层归并。

**实现**：`merge_arcs()` —— 读该书的段序列 → DeepSeek 归并 → 写回 `chapter_summaries.arc_no/arc_name/arc_summary`；
报告升级为**三级结构**（弧 → 段 → 章）。CLI `--stage arc`（`all` 已含）。

**模型调参（实测踩坑）**：`deepseek-flash` **默认思考模式开着**，2000 token 预算会被 reasoning 全部吃光、
content 返回空且耗时 10.7s；加 `thinking={"type":"disabled"}` 后 **1.7s** 拿到完整 JSON。归并任务不需要思考。

**真机验证（修真四万年前 30 章）**：19 个段 → **5 个故事弧**（covered=19，leftover=0），耗时 **5~6 秒**。
归并质量达标 —— 例如**弧 2「晶脑维修与夺舍觉醒」（8~12 章）**把原本切碎的三个段
（维修晶脑 / 幻梦百炼宗 / 反夺舍）合成了一条完整的金手指觉醒弧，正是"粒度错位"问题的直接修复。

**Key 存放**：`app_configs.llm.deepseek_key`（**只进数据库，不进代码不进 git**；已全仓库扫描确认无泄漏）。

**下一步（7.1 收尾）**：20 本放量 → 凝练模板（人工合并：AI 出候选弧 + 用户确认）→ 7.2 篇规划流。

#### 7.1 模板凝练落地（2026-09-11 晚，弧 → 模板）

**新模块 `services/plot_distill.py`**（步骤 5）：
- `cluster_arcs`：用 bge-m3 向量算弧概括相似度聚类（阈值 0.80）→ **AI 候选组**；
  向量不可用时退化为"每弧一组"（不硬报错）；
- `distill_template`：一组弧 → DeepSeek 凝练成模板结构（`phase → beat → variants[各书走法]`）+ logline/tags/pitfalls/rhythm；
  含**重试一次**（LLM 偶发格式问题，实测救回 1/5 组）；
- `distill_all`：聚类 + 逐组凝练 + 入库（`status="draft"`）；`replace_drafts=True` 重建时清旧 draft（**reviewed 不动**）。

**人工确认原则落地**：AI 产出一律 draft；人工审核后改 `status="reviewed"`。当前审核入口是 Markdown 报告 + `/plot-templates` API，交互 UI 待做。

**真机结果（修真四万年 5 弧 → 5 个种子模板）**：结构质量达标，例如「夺舍觉醒」：
4 个 phase（开局委托 / 异象触发 / 梦境历练 / 夺舍反转）× 10 个 beat，每个 beat 带 variants（`src` 溯源到书名 + 具体处理），
pitfalls 4 条都很实用（"夺舍反转缺乏前期伏笔，显得突兀机械降神"）。

**发现并修掉一个检索排序缺陷（重要）**：只索引 beat 块时，块的语义被"具体情节"主导，
模板名/logline/标签（如"金手指觉醒"）权重被稀释 → 模糊口述"主角觉醒金手指"把「夺舍觉醒」**排到最后**。
修复：**新增模板级块**（`name + logline + 标签 + 各 beat 标题`）与 beat 块一起索引（`template_chunks`），
同样 query 后排序升到**第一**。

> ✅ **已验证（2026-09-11 深夜，30 个模板）**：6 组模糊口述查询 **Top1 命中率 6/6** —— 模板级块 +
> 30 模板规模下区分度足够。详见下节。

#### 7.2 篇规划流落地（2026-09-11 深夜，端到端验证通过）

**新表 `article_plans`**（一个篇一条当前计划）：
`plan["lines"]` 每行一章 `{no, beat, summary, new_chars, recall_chars, target_words, hook, template_ref}`；
`origin=template|free|ai_draft`；`raw_ai` 留档（供 4.3 反馈对比）；`status=draft|confirmed`。

**生成**（`plan_crud.generate_plan`，DeepSeek 关思考）：
模板检索（top-2，检索不到 → 自由规划 `origin=free`，**不硬凑**）+ 本书上下文
（卷概要 / 角色 / 伏笔 / 前情结尾）+ 作者口述 → 逐章计划。
**防幻觉双闸**：召回角色后端校验（查无此人剔除并报告 `unknown_chars`）；新角色只进计划、拍板后走待确认实体。

**行级局部修改**（不用重新生成整份）：
- 表格直接改：`PUT …/plan`（`save_lines`）
- **AI 只改一行**：`POST …/plan/refine-line {line_no, instruction}` —— 其余行原样
- **拍板**：`POST …/plan/confirm`（draft → confirmed）

**生成联动（最后一米）**：`layers.layer_chapter_plan`（**P_CRITICAL 级，永不裁剪**）——
把作者确认的「本章任务卡」注入生成上下文：节拍 / 要点 / 钩子 / 字数 / 新角色 / 召回角色 + 前后章计划。

**★ 踩坑（重要，已修）**：SQLAlchemy JSON 列的**共享引用污染** ——
`lines = plan.plan["lines"]` 拿到的是**同一个列表对象**，修改它会把 SQLAlchemy 记住的旧值一起"污染"，
赋新值时 `new == old` → **UPDATE 被跳过**（实测：refine 返回正确但库纹丝不动，DeepSeek 白调）。
修复：取 lines 时 `copy.deepcopy`。**方法论：凡"读 JSON 列 → 改 → 写回"，取值时必须先深拷贝。**

**端到端验证（真实 DeepSeek，临时项目已清理）**：6 章退婚流计划生成 ✓
（模板检索命中「退婚逆袭」、每章 beat/钩子/字数齐全、防幻觉剔除 3 个幻觉角色）
→ AI 改第 2 行 ✓（其余行不动）→ 拍板 ✓ → **layer_chapter_plan 产出完整任务卡** ✓。

**API**（5 个，路由 160 / paths 96）：generate / GET / PUT / refine-line / confirm。
**待做**：前端规划页（结构化表格 + 行级编辑 + 拍板按钮）—— 当前可先用 API 驱动。

#### 7.1 速度优化实测（2026-09-11 晚，斗破苍穹）

**动机**：串行逐章跑斗破 1671 章需 14~16 小时，必须优化。

**实测对比（各 9 章 / 30 章，`interval=2s`）**：

| 配置 | 每章耗时 | 1671 章推算 | 失败 |
|---|---|---|---|
| A 逐章串行（原） | 30.2s | ~14 小时 | 0 |
| B **批量 3 章**/请求 | 5.1s | ~2.4 小时 | 0 |
| C 批量 3 + 并发 3 | **2.2~2.5s** | **~70 分钟** | 0 |

（C 配置三轮 30 章复测：2.51s/章、`failed=0`；其中漏章补跑已含在内，见下）

**结论：批量是主杠杆（5.9×），并发再叠 2.4×，合计提速 ~11 倍**。原因：单章那 30s 里**绝大部分是固定开销**
（排队 / 首 token / prompt 处理），输出 150 字还是 450 字对时长影响很小 —— 一次问 3 章等于把固定开销摊薄到 1/3。

**实现要点**（`import_chapters_batch`）：
- 线程模型：**LLM 调用在工作线程（纯 IO），DB 写入全部回主线程串行** —— SQLAlchemy Session 非线程安全，
  这样既拿到并发又避开多线程写 SQLite；Key 在主线程预取后传入 `_sf_post`（工作线程不碰 session）；
- `RateLimiter` **加锁**（多线程共享，否则多个请求同时穿过判定 → 打爆限流）；
- **漏章补跑（两级）**：实测批量模式下 8B 偶尔漏掉批内某章（30 章漏 1~4 章）→ ① 把漏章**重新凑批再跑一轮批量**
  （3 章批量 ~15s，比单章 3×30s 省得多）；② 仍漏的才用**单章 prompt 兜底**。
  30 章复测（漏 4 章）`failed=0`、2.51s/章 —— 单章补跑会让耗时涨到 4.17s/章，两级补跑把它压回 2.51s；
- **概括有效性校验** `_valid_summary`：≥15 字且无 JSON 残片特征（单测暴露出补跑路径会把 "这不是 JSON" 原样入库）。

**未做**：令牌桶（当前用"加锁的固定间隔"，实测未触发限流，够用；若要更高并发再上）。

#### 7.1.1 入库管线补全（2026-09-12 ✅ 完成 —— 真机端到端验收通过）

**背景**：用户将放**多个 AI 并行灌数据**。深查入库链路后发现 **4 个洞**，其中第 1 个会直接打破已通过的门槛。

**已落地（2026-09-12）**：
- `--stage all` 现在 = 概括 → **匿名化** → 段 → 分类 → 弧 → **`verify` 自检** → 报告（顺序改动见下"洞 1"）；
- 新增 `--stage verify`：**纯 SQL 零调用**的专名残留 + 覆盖率自检（把门槛 2 变成可回归）；
- 新增 `--stage full` = `all` + distill（单点用；**专名残留不为 0 时拒绝凝练**）；
- 凝练加 cast（B 方案，见 7.3）；`core/database.py` 加 WAL + `busy_timeout` + `synchronous=NORMAL`。

**★ 真机端到端验收（2026-09-12）**：
- `--stage all`（道诡异仙 1~30 章，424s）：概括 30 章 0 失败 → 匿名化 38 映射触及 30/30 → 段 24 →
  分类 24/24 → 弧 8（covered 24 / leftover 0）→ 自检通过 → 报告。
- `--stage verify`（3 本书）：斗破 200 / 修真 30 / 道诡异仙 30 → 覆盖 100%、**人物势力类专名残留 0**。
- `--stage distill`（3 本书 41 弧 → **37 模板**，193s）：**37/37 含 cast**，每模板 3~6 槽位，
  slot 为功能名、`srcs` 溯源正确、**同功能位跨代称合并生效**。
- 单测 **297 全绿**。

**验收中发现并修掉的 2 个真 bug（都是我自己引入的）**：
1. **`_book_cast` 的映射只取了 `CAST_KINDS`** → `role_desc` 里 item/place/realm 类专名全部漏网，
   实测 18 处（清风观 / 紫晶源 / 斗之气 / 魔兽山脉 / 炼药师公会…）带进了模板 cast。
   修复：映射改用**全 kind**；`mapping_strong` 再剔 `item`（该类把「丹药」这类普通名词也当专名，
   替换反而污染向量语义）。
2. **LLM 写的 `desc` 没有兜底匿名化** → 模型会自己带出源书专名（DeepSeek 的先验知识）。
   修复：`_normalize_cast` 里对 desc 再过一遍匿名化（确定性兜底，不只靠 prompt）。
   结果：cast 中真专名残留 **18 → 0**。

**顺带修**：`verify` 的判据原先不分类型 → 把 item 类普通名词误判为失败（道诡异仙 21 处「丹药」），
现分**硬判据**（protagonist/role/sect/family/force，判失败）与**软提示**（item/place，只报告）。

**仍未做**：WAL 是否真生效（需重启后端后查 PRAGMA）；**跨书聚类仍未成功**
（3 本书 41 弧只聚成 37 组 —— 流派差异大，属真实结果，需 7.4 放量后再看）。

**实测现状**（脚本 `backend/scripts/import_novel.py` → `services/plot_import.py`）：

| 项 | 实测 |
|---|---|
| 模型分工 | 概括/切段/打标 = **硅基流动 `Qwen/Qwen3-8B`**（`enable_thinking=false`）；**弧归并 = DeepSeek `deepseek-flash`**（`thinking={"type":"disabled"}`） |
| `--stage all` 内容 | summarize + segment + label + arc + 报告 |
| **是否含 anonymize** | ❌ **不含**（`plot_import.py` 全文无 anonymizer 引用，已 grep 确认）。现有 204 条映射是用户**事后单独跑** `--stage anonymize` 补的 |
| 是否含 distill | ❌ 不含（需单独 `--stage distill`） |
| 入库格式 | **当前 7.1 版**（章概括=纯文本；段=`{segments:[{chapters,summary}]}`；弧=`{arcs:[{segments,name,summary}]}`）—— 与 7.3 的差距**只在"无 cast"** |
| 是否写 `characters` 表 | ❌ 不写。仅在 anonymize 阶段把「代称 + role_desc」写入 `book_aliases` |
| 是否有角色向量 | ❌ 无。`vector_chunks` 只有 `plot_template`(665) + `ref_doc`(133) |

> ⚠️ **概念区分（防止后续混淆）**：**模板侧槽位**来自源书，存 `book_aliases`，用于凝练进模板 cast；
> **本书角色池**是作者自己小说的角色，存 `characters`，用于 7.3 选角。
> **素材入库绝不该往 `characters` 写** —— 那是作品自己的角色库，会被 20 本小说的人物灌爆。

**四个必须堵的洞**：

1. **`--stage all` 不含 anonymize** → 并行 AI 按现有投递单跑出的书 = 概括/段/弧齐全但**未匿名**；
   接一次 `distill` 就凝练出**带源书专名的模板**，**直接打破门槛 2**（"16 个源书专名命中 0"）。
   → 改：`all` = summarize → **anonymize** → segment → label → arc（匿名化紧随概括，下游段/弧都在干净文本上生成）。
2. **`distill_all` 默认 `replace_drafts=True` 会清空所有 draft 再重建**（`plot_distill.py:234`）
   → **并行跑 distill 必然互相清空**。→ 定规矩：**并行 AI 只跑到 anonymize 为止；distill 由单点串行跑**
   （新增 `--stage full` = all + distill，仅供单点使用）。
3. **数据库未开 WAL / `busy_timeout`**（`database.py:53-58` 只设了 `check_same_thread=False`）
   → 并行多本书写库会 `database is locked`。→ 加 `journal_mode=WAL` + `busy_timeout`（改完需重启后端）。
4. **`RateLimiter` 是进程内的**（`plot_import.py:60`）→ N 个 AI 并行 = **N 倍请求率**
   （投递单铁律 2/3 禁并行正为此外）→ 并行时每个 AI 降并发，并限定书数上限。

**改动清单**：
- `plot_import.py` / `import_novel.py`：`all` 纳入 anonymize；新增 `--stage full`；帮助与阶段说明更新。
- `plot_distill.py`：`_distill_prompt` + `distill_template` 加 cast（B 方案，见 7.3）。
- `core/database.py`：WAL + busy_timeout。
- **`.workbuddy/tasks/2026-09-11-模板导入-OpenCode.md` 必须同步改**（命令 / 铁律 / 验收），
  否则并行 AI 照老单子跑，第 1 个洞照样发生。
- 每本书验收加一项：**源书专名命中 0 抽检**（门槛 2 的回归测试）。

**推进顺序（用户指定）**：改完 → **用户先跑几十章验收** → 再放并行 AI 灌数据。

##### 7.1.2 成本可观测 + prompt 瘦身（2026-09-13 ✅ 完成 —— 真机验证通过）

##### 7.7 正文风格迭代——段落与对话形态对抗（2026-09-13 ✅ v6 达标，多章均值待跑）

2. **v3~v6 few-shot 轮（达标）**：task_lines 末尾压【分段形态示范】（自写古风正例+反例，防污染）→ 段均 18.8（+49%）；再压【对话形态示范】+ SKILL「对话潜台词与信息量」重写（台词长度锚/语气口语/人格化铁律「换个人说是否一字不差」/情绪进措辞）→ 四轮修补（v4 反利用→v5 轮次纪律→v6 字数补偿）→ **v6：段均 26.0 首次过 25 硬指标、叙述段均 39.0、台词条均 10.1（真实 18.1）、审讯乒乓 7/20 串→0、章字数 4631**。

**🔴 本机环境大坑（四次回填实验才定案，必须记牢）**：

**症状**：脚本写入 SQLite 后「自读正常、跨进程读旧数据」；WAL 文件暴涨（82MB）但 `wal_checkpoint` 报 0 帧；`dangerouslyDisableSandbox` 不解决。

**定案结论（WorkBuddy 工具环境的文件虚拟化）**：
1. **池化多连接 = 每个连接是独立视图**：SQLAlchemy 默认 pool 下，连接 A 的写入对连接 B / 新进程不可见；`commit/rollback` 归还连接后换新连接，**之前的写入直接"蒸发"**（v4 实测：回填后统计从 793 跌回 0）。
2. **WAL 帧跨进程不可见**：写连接 commit 的帧只有 checkpoint 进主库文件后才对其他进程可见。
3. **唯一可靠形态**：**StaticPool 强制全局唯一连接（写读自洽）+ 结尾在同一连接上 `PRAGMA wal_checkpoint(PASSIVE)`**（实测 20160 帧刷入、跨进程立即可见）。
   checkpoint 前若有挂起读事务会被自己挡（`database table is locked`）→ 先 `commit()` 结束事务再跑。
4. **适用边界**：用户手动启动的 dev.py 后端**不受影响**（无虚拟化层，单进程池自洽）；受影响的是**WorkBuddy 工具内启动的 Python 进程对 SQLite 的写**——以后凡写库脚本（import_novel / reindex 等）在工具内跑完，**必须跨进程验证落盘**。

**给 OpenCode 的模板产线影响**：零改动 —— `distill → tpl_crud.create → index_template` 三路自动带出，新模板的 cast 槽位自动进原型库；但 **OpenCode 在自己终端跑（非本工具环境）写入是真实落盘的**，与本坑无关。
