## 0. 为什么是切片式重写，不是全量重写

2026-09-09 已论证并拍板。核心理由（防止日后动摇）：

1. **架构没崩，崩的是工程纪律。** `router/service/core` 分层清晰、gateway 适配器模式正确、上下文引擎设计合理。缺的是测试/日志/变更记录——换仓库这些还是没有。
2. **全量重写有死亡谷**：写到 60–70% 时旧的不能忍、新的不能写稿，项目多半死在这段。
3. **硬踩过的坑会重踩**：04 里记的模型行为坑（思考字段厂商差异、重复惩罚逼崩采样…）是几十次调试换来的，重写等于清零。
4. **AI 结对特性**：AI 擅长"给定契约的单模块重写"，极不擅长跨全仓重构。切片是顺应为之。

**切片式重写的含义**：每个模块**内部允许 100% 推倒重写**，但必须一次一个、接口契约不动、写完有测试。

### Phase 6 · 工具调用（function calling）（2026-09-10 规划，**待拍板**）

**核心判断：项目不缺「工具调用」，缺的是「闭环」。**
现状有 4 种手搓替代品，**全部单向**——模型说完、后端执行，**模型拿不到结果**，无法据此续答或多轮：

| 现有交互 | 用在哪 | 硬伤 |
|---|---|---|
| **文本标记协议** `LOAD_REFS:` / `LOAD_SETTING:` | 商讨按需加载 | 正则抠 id，脏输出即漏；小模型把握不住"该不该请求" |
| **JSON 抽取** | `/角色` `/地点` 指令、写后摄取记忆抽取 | 一次性；模型**不知道落库结果**（重名被跳过？字段缺了？） |
| **人工编排 DAG** | 工作流 8 种节点 | **模型不能自主决定调用哪个节点**，顺序写死在图里 |
| **SKILL 文本注入** | `skill_dispatch` | 只是 prompt 拼接，谈不上"调用" |

**已撞到的天花板（证据）**：`routers/chapter.py:254` 注释 —— 章节生成**主动放弃** AI 两阶段 LOAD_REFS，
理由「本地 4b 模型在该协议上不稳定，**时而全不加载、时而一股脑全加载**」，改用确定性打分 top-up。

**已有基础设施（关键，改造是插拔式的）**：`services/reference_selector.py` 已定义 **A/B 策略抽象**——
`MarkerSelection`（A，现状默认）/ `ToolCallSelection`（B，**占位未实现**，连"未来实现要点"都写在注释里）。
且明确「**无论 A 还是 B，之后的 fetch/inject/Pass2 完全共用**」→ 换策略不动主链路。

#### 扩展方向（按性价比排序）

| 优先级 | 方向 | 现状痛点 | 落地要点 |
|---|---|---|---|
| **P0** | `retrieve_refs` / `load_setting` 工具化 | 靠正则抠文本标记 | 实现 `ToolCallSelection` + 适配器加 `chat_with_tools()` |
| **P0/P1** | **实体 / 伏笔入库工具**（`upsert_character`、`plant_foreshadow`、`create_location`） | 模型收不到落库反馈 → 无法自我纠正 | 工具返回「已创建 / 重名跳过，是否改名」，模型据此调整 |
| **P1** | **检索类工具**（`search_chapters`、`get_character_state`、`list_open_foreshadows`、`query_timeline`） | 上下文引擎"一股脑塞 + budget 裁剪" | **省 token 的关键**：改成模型主动取，比"预塞+裁剪"更准更省 |
| **P2** | 一致性检查（`check_consistency` / `lookup_setting`，纯只读） | 长程设定自相矛盾 | 只读工具，安全，可先上 |
| **P2** | 工作流节点暴露为工具 | DAG 只能人工编排 | 从 DAG 走向 Agent；**风险高，靠后** |
| **P3** | 写操作类（改章节 / 扩大纲） | — | **必须 dry-run + 用户确认**，不许模型直改稿 |

> **附带收益**：P0/P1 的实体/伏笔工具会**顺带修复已记录的"伏笔断链"**（`foreshadow_actions` 曾被抽取但从不写入 `ForeshadowORM`；Phase 2.1 已用非工具路径补上，工具化后模型能感知结果）。

#### 工程配套（不做这些会翻车）

1. **适配器抽象**：`BaseModelAdapter` 加 `chat_with_tools()`。三家字段不同——OpenAI `tools`/`tool_calls`、Claude `tools`/`tool_use`、Ollama 仅部分模型支持
2. **必须保留 marker 降级**（抽象层已具备，正好用上）
3. **Agent 循环**：步数上限（建议 5）、超时、可中断（复用现有 `stop` 机制）
4. **SSE 事件**：新增 `tool_call` / `tool_result` → 前端显示"正在查资料库…"，否则是黑盒
5. **观测**：工具名 / 参数 / 耗时 / 结果大小落库（复用 `load_observation` 思路）
6. **日志**：工具调用必须记日志（呼应 Phase 3.5 铁律）
7. **成本**：只给"按需取数"类工具，**别把全量 schema 常驻 prompt**

#### ★ 前提：取决于主力模型（先确认再动工）

- **主力云端**（ModelScope Qwen3.5 / GLM）：原生 tool_calls 成熟，**值得做**
- **主力本地 4b**：连 marker 协议都不稳，指望它填对 `tool_calls` 的 JSON 参数更不可行 →
  **方向应转为确定性算法**（同 `chapter.py` 当时的取舍），别硬上

#### 🔴 边界约束（2026-09-12 增补 —— 定这条是为了防滥用）

**FC 只用于「步数不确定的探索型取数」。确定性取数一律后端预取，不给模型自主权。**

判据（三问，任一为"否"就走预取）：
1. 取哪些数据，是否**依赖模型自己的推理过程**才确定？
2. 取数次数/顺序是否**无法事先写死**？
3. 模型拿到第一批结果后，是否**可能改变**下一批要取什么？

反例（**不该用 FC**）：7.3.5 的"回归理由材料包"—— 谁是蛰伏角色（casting 已算）、他哪章消失（台账已算）、
其后梗概（一个 SQL），**三步全确定** → 用 FC 等于把确定任务交给不确定组件，
与 `chapter.py:254` 当年放弃 AI 两阶段 `LOAD_REFS` 是同一个坑。
正例：`retrieve_templates(query)` —— 模型才知道自己该查什么（见 7.6）。

> 附带约束：**章节生成链路继续用确定性 top-up，不做 agent 化**（03 原话："那条链要的是稳定不是自主性"）。
> 给生成层加自主性 = 把已经修好的问题主动修回去。

#### 建议推进顺序（3 步，每步可独立验收）

1. **`retrieve_refs` 工具化** —— 成本最低，且能**先验证原生 tool_calls 在你的模型上到底稳不稳**
2. 稳了再做**实体 / 伏笔入库** —— Agent 味最强，附带修断链
3. 最后做**检索类工具**省 token

### Phase 7 · 模板库与规划驱动写作（2026-09-11 立项，**已拍板**）

**立项背景（用户对现状的判断，原话要点）**：当前生成链路本质上只服务「已写完全书大纲、甚至每章梗概」的作者
—— **输入侧（规划）是空的**。卡文/水情节的根因 = 缺「章计划」这个中间层：一篇的情节概括只有几百字，
直接扩成几万字必然发散失控；不扩则两三章过完一篇，太平淡。真正缺的是**别人验证过的「几百字 → 9 章」拆法**，
且同一节拍要有多种走法可供借鉴（卡文时看别人怎么走）。

**已拍板（2026-09-11）**：
1. 入库管线「人工合并」步骤 = **AI 给候选组 + 用户点确认**（全自动凝练会产出平庸均值与错误归类）；
2. 起步 **20 本**书，但**先用 Qwen3-8B（硅基流动 API，零成本档）跑 1~2 本验证概括/切分质量**再放量
   （管线模型走 `model_configs`，可随时切换）；
   > ⚠️ **2026-09-12 更正**：此处原写"Ollama 本地"，与代码不符 —— 实测 `plot_import.py` 直连
   > **硅基流动 `Qwen/Qwen3-8B`**（`SF_BASE=https://api.siliconflow.cn/v1`，`enable_thinking=false`）；
   > **弧归并走 DeepSeek `deepseek-flash`**（升档模型，非 8B）。
3. 章计划**用新表** `article_plans`（不复活冻结的 outlines）；
4. 成本事实（2026-09-11 核实）：FC 闭环最坏 5 步吃满前缀缓存 ≈ **0.025 元**，与现状一次生成持平 ——
   **经济不是约束，延迟与模板数据质量才是**。

#### 7.1 模板库

**两层资产**：
- `plot_templates`：`scale = arc(篇级 8~15 章) | segment(情节段 1~3 章，乐高件)`；核心结构
  `structure = {phases: [{phase, beats: [{beat, variants: [{src, how}]}]}]}` ——
  **beat × variants 是灵魂**（卡文时查的是"这个节拍别人还有哪几种走法"，`src` 溯源到哪本书）；
  `genre_tags` 做跨题材同构匹配（学院大比 ≈ 商业竞标 ≈ 武林大会）；`pitfalls` / `rhythm` / `source_stats`。
- `chapter_summaries`：入库管线中间产物（书名/章号/百字概括/段归属/情节标签），本身是可回溯资产。

**检索三层**（回答"原文存还是向量查"：**向量负责找，结构化 JSON 负责用，原文永不入库**）：
1. `genre_tags` / `scale` 标签过滤（SQLite，零成本）；
2. **bge-m3 向量检索，chunk 粒度 = beat**（不是整篇模板）—— 篇规划查模板级目录，**卡文时精确命中当前 beat 的 variants**；
   混合语义（"学院大比+秘境寻宝"）天然落在两簇之间、两边都召回；多关键词走 multi-query + RRF（A 线现成逻辑）；
3. LLM 扩查（可选）：口述太模糊时先拆成 2~3 个候选查询再各查一路融合。

**消费两条路**：
- **路径 A · 嵌入式（MVP 首选）**：top-2 模板的结构 JSON（2~4k tokens）直接拼进规划调用，一次出章计划；
  简单、可调试、无闭环、模板前缀缓存友好；
- **路径 B · 工具式（Phase 6 落地后升级）**：模板目录常驻 prompt（几十 token/个），AI 调
  `retrieve_templates(query)` 拉详情 —— 库大了不爆 prompt，步数上限 3，**可降级回路径 A**。

**入库向导（项目内页面，六步）**：切章 → 逐章概括（LLM，落库断点续跑）→ 情节段切分 → 段分类打标 →
**人工合并（AI 候选组 + 用户点确认）** → 凝练入库 + 向量化。
向量化进 `vector_chunks`（`source_type='plot_template'`）→ **A 线 Hybrid 检索直接复用，检索代码零新增**。

#### 7.2 篇规划流

- 新表 `article_plans`：article 绑定、`template_ids`、`plan` JSON（行 = 章号/beat/summary/new_chars/
  recall_chars/target_words/hook）、`origin = template|free|ai_draft`、`raw_ai` 留档（4.3 反馈对比用）、`status`。
- 规划上下文**全部复用现成字段**：卷大纲、上篇结尾（stage_summaries）、活跃角色（characters + memories）、
  未回收伏笔、设定 —— 不新建上下文系统。
- **防幻觉双闸**：`recall_chars` 后端校验 `characters` 表存在性（查无此人即剔除）；`new_chars` 只进
  `planned_chars`，拍板后走既有的待确认实体机制。
- **局部修改（结构化表格，不是一坨文本）**：行级操作 = 改 / 删 / 插 / **换走法**（该 beat 的其他 variants）/
  **AI 只改一行**（`refine-line {line_no, instruction}`，其余行原样）—— 不是全局重新生成。
- **未找到参考，三种情况都不硬凑**：① 检索为空 → 自由规划模式，或口述升格为 `ai_draft` 临时模板（**可反哺模板库**）；
  ② 模板与本书设定冲突 → LLM 标注冲突 beat，前端标黄逐行决定；③ 本书上下文不足 → 降级跳过召回建议。
- **生成联动（最后一米，2.1 伏笔回注同款模式）**：`build_chapter_messages` 新增 `layer_chapter_plan` ——
  注入本章 beat / 目标字数 / 结尾钩子 / 可引角色 + 上一章完成情况。

#### 7.3 批量生成器

- 按 plan 连写 M ≤ 3 章；每章 = 生成 → 落库 → **同步摄取**（连写必须等摄取完成，下一章上下文才含它；
  与现行异步 `_background_ingest` 的关键差异）。
- `batch_progress` SSE 事件（第几章/共几章）+「停止」按钮；`done_up_to=N` 断点恢复，已落章节完整可用。
- 连写时同会话前缀缓存命中率高；打斗/博弈类在 plan 里拆成 2 个 beat，连写共享"场"级约束 ——
  衔接质量优于逐章手动点。

#### 7.4 FC 闭环（第一个真实场景）

- **单工具** `retrieve_templates(query, scale?, tags?)`，不做万能工具箱。
- **仅篇规划会话启用** —— 章节生成继续用确定性 top-up（那条链要的是稳定不是自主性）。
- 步数上限 3，超限降级直出计划；不支持 tool_calls 的模型自动走 7.1 路径 A。
- SSE：`tool_call`（"正在检索模板库…"）→ `tool_result`（"找到：学院大比(12本)、秘境寻宝(8本)…"）。

**2026-09-12 增补（两条）**：
- **边界**：FC 只用于**步数不确定的探索型取数**，确定性取数一律预取 —— 完整判据见 §Phase 6「🔴 边界约束」。
  据此，7.3.5 的**回归理由材料包不走 FC**（三步全确定），仅在其缺席期超窗口、确需多轮补取时才考虑。
- **候选第二工具**（不是现在做）：`retrieve_reentry_context(character, from_chapter, to_chapter)` ——
  仅当①缺席期材料超窗口且②后端两级预取效果不足时才启用。**默认不启用。**

**前置条件（2026-09-12 核实）**：规划层用的是 **DeepSeek**（`plan_crud` → `plot_import._ds_post`，关思考），
**不是本地 4b** → 模型侧支持原生 `tool_calls`，**FC 在规划链路上可行**。
但适配器当前 `chat()` **只返回 `str`，不暴露 `tool_calls`**，`reference_selector.ToolCallSelection`
**仍是抛 `NotImplementedError` 的占位**（05 §11.1）→ 需先补 `chat_with_tools()`。

**实施顺序**：7.1（**MVP 门槛：20 本灌完后，"学院大比+秘境寻宝"类混合口述能召回正确模板族**）
→ 7.2 → 7.3（可与 7.2 并行）→ 7.4。
**风险排序（诚实记录）**：模板数据质量 > 格式设计 —— 种子期只用完本/口碑书，第一批模板用户亲自过目；
格式先跑再迭代，不过度设计。

- 境界 → `境界1~境界N` **绝对阶梯**（修正 2：不用"相对主角"的 C/D/B —— 主角升级后锚点漂移）
- 每个代称带 `role_desc` 槽位功能说明 → 计划生成时**选角**到本书角色
  （修正 3：解决「模板 A 的男配10 与模板 B 的男配13 聚合时角色混乱」——
  模板代称是来源书槽位，计划里一律映射回本书真实角色）

**实现**：新表 `book_aliases`（双向表：正向匿名 / 反向还原）+ `services/anonymizer.py`
（cast 抽取 → 代称分配 → 长名优先正则替换）+ 概括原文备份 `*_raw` 列（可回滚）+ CLI `--stage anonymize`。

**踩坑**：①LLM 自报境界顺序不可靠 → 按**首现章号**排序；②对已替换文本再抽取 →
「一星境界2」链条污染 → 抽取读 `summary_raw` + 过滤子级条目（含数字段/星阶）。

**真机**：斗破 152 条映射、修真 52 条（秒级）；**重凝练后 29 个模板，16 个源书专名命中 0** ✓。
计划生成同步加「选角规则」。单测 9 例；全量全绿。

**速度注记**：30 章 17 分钟（~34s/章）→ 755 章全量约 7 小时。放量前需做**并发优化**（3~5 并发 + 限速器改为令牌桶）。

#### 7.3 角色向量选角（2026-09-12 规划 → ✅ 2026-09-13 已实现 —— 用户方案）

**动机**：计划生成的"选角"目前靠 LLM 在 prompt 里自行分配 —— 跨模板聚合时
（模板 A 的友·配角10 与模板 B 的友·配角13 是两个世界的角色），代称对 AI 无意义，容易混乱；
且选角结果不可解释（为什么是药老？）。

**方案（用户提出）**：把模板角色从「代称」升级为「**人格化槽位**」—— 选角变成**向量检索 + 可解释匹配**。

##### cast 结构定稿：B 方案（功能槽位 + srcs 溯源）

**不做 A 方案**（cast 直接记来源书代称）。A 的问题不在单书 —— 单书时两方案产出几乎逐字相同
（**这正是"看不出差别"的原因**：当前 29 个模板全是单书模板）。差异在**跨书聚成一组后**爆发：
斗破的 `友·配角4` 与修真的 `友·配角2` 其实是**同一个功能位**（引路人师长），但编号/措辞不同 →
cast 从 2 个功能位膨胀成 4 个槽位 → **两个槽位抢同一个角色**，即"模板 A 配角10 vs 模板 B 配角13"
的原病从"计划里"前移到"模板里"。且代称编号随重聚类漂移 → 已定 cast 失效。

```json
{"slot": "引路人师长",
 "desc": "主角的导师型角色，掌握关键资源、推动主角成长",
 "mode": "助力",
 "beats": ["异象触发", "梦境历练"],
 "srcs": [{"book": "斗破苍穹", "alias": "友·配角4"},
          {"book": "修真四万年", "alias": "友·配角2"}]}
```

- 与 `variants[{src,how}]` **同构**：`slot` 是跨书契约，`srcs` 溯源到各书实现。
- 每模板 **cast 限 3~6 个关键槽位**（不列全部代称，否则模板爆炸）。
- 校验：`srcs` 里的 alias 必须真实存在于该书 `book_aliases`，否则丢弃。

##### 六步实现顺序

1. **凝练带 cast**：`collect_arcs` 联查 `book_aliases`（`kind ∈ protagonist/role/sect/family/force`）
   把 `role_desc` 带进凝练输入；`_distill_prompt` 输出 schema 加 `cast`。
   ⚠️ **`role_desc` 必须即时匿名化**（复用 `anonymizer._replace_all`，**只在内存层替换，不改库值** ——
   `book_aliases` 要留作反向还原原料）。**实测风险（2026-09-12）**：现有 204 条 `role_desc` **直接含源书专名**
   （"…称主角为**萧炎**哥哥""**云岚宗**宗主""**萧薰儿**"）→ 原样入 cast 会**打破已通过的反抄袭门槛 2**。
2. **槽位向量库**：`source_type="plot_cast"`、`project_id=__global__`、
   **`source_id=template_id` + `chunk_idx = cast 数组下标`**（命中后直接 `structure["cast"][i]` 反查，
   不必解析 chunk 文本）。向量文本 = **功能描述 + srcs 典型实现（混合文本）** ——
   纯功能描述过于抽象，与"具体角色人设"的向量距离偏大、分数会整体偏低。
   `create`/`update`/`delete` 三个入口都要维护，**两个 source_type 都要清**（否则留孤儿向量）。
3. **计划向量选角 → 新表 `plan_castings`**：
   `id, plan_id, project_id, article_id, template_id, slot, slot_desc, slot_mode,`
   `character_id, character_name, score, source(auto|manual), needs_reentry_note`，**`UNIQUE(plan_id, slot)`**。
   - **表是唯一真相源**，plan JSON 里只放**只读展示冗余**；人工改 casting 走独立端点，**不碰 plan.json**
     （避开 7.2 已踩的 JSON 列共享引用坑）。
   - **必须登记进级联删除**（`project_crud` / `article_crud` / `volume_crud`）。
   - **打分统一走显式余弦**（两侧文本批量 embedding 后在 Python 里算），**不用 store 的 score**：
     后端生效实现是 `SqliteVecStore`，其 `score = 1/(1+L2)` **不是余弦** ——
     同一 0.7 余弦在库里显示 **≈0.56**，**若照 0.65~0.75 直接标定会过严（实际要求 cos≈0.90+）**。
4. **角色状态门**（A 档，从 7.3.5 并入 —— 见下方"为什么并入"）：候选池先按状态过滤，
   `已死`/`离场` **默认不进池**（可显式放行）。**没有它 casting 会系统性产出连续性错误。**
5. **阈值标定 + 出场校验**：标定前提见下；出场校验复用 `entity_graph` 一跳扩展，
   **只做过滤/标记，不参与打分**。
6. **平局判据（两级）**：① 历史共现次数 → ② 活跃度（`last_seen` 更近者优先）。
   **只改排序，不动打分。**

##### 三处算法决策（讨论定稿）

- **不做「出现可能性 × 相似度」的乘法**：槽位是否出现是结构决定的（节拍被采用=出现），
  乘法让两个误差相乘、量纲混乱。两步走：①选角（人设相似度）→ ②出场校验（历史出现 + 节拍需要）。
- 多候选冲突用「历史共现次数」打破平局。
- **（2026-09-12 新增）否决"活跃系数"乘法惩罚**：用户提出"长缺席角色用活跃系数惩罚"，意图正确
  （长期不出现→合理召回难度大），但**形式与上一款是同一个错误** —— 无量纲启发式标量乘到余弦上，
  说不出量纲含义、无法标定，且**当前无真实长篇数据可标定（只能拍，而拍出来的系数比拍出来的阈值更危险：
  阈值错只是漏召回，系数错是系统性扭曲排序且无人能发现）**。
  替代（效果相同且干净）：**① 硬门 = 离散状态，不参与 vs 分数低；② 平局次级判据 = 相似度接近时
  （top1−top2 < 0.03）优先选活跃度高的**。若将来真实数据证明排序确实被长缺席角色污染，
  **正确形式是"先归一化再线性加权"（`0.85·cos + 0.15·activity`，activity 归一到 [0,1]、权重可标定），不是乘法。**

##### 阈值标定前提（硬约束）

现有 `characters` 表只有 **2 个角色**（林尘/苏若雪），且 `personality`/`background`/`brief`/`talent`
**全为空字符串** —— 真实数据上**没有可向量化的角色池**，匹配效果与阈值都无从实测。
→ 标定必须用**临时测试项目 + 8 个带真实人设的角色**（覆盖师长/对手/同伴/长辈等类型），
产出标定表（正例最低分 / 负例最高分 / 分位数），**用完连同角色、向量、记忆一起删**（顺带验证级联删除）。

**验收（对应 docs/01 §4 门槛 6）**：同一配角在整篇计划中身份一致；每个选角有可解释的匹配分数与槽位说明；
无匹配的槽位明确走 `new_chars`（不硬凑）；**已死角色不出现在任何一行**。

**前置依赖**：匿名化归一（✅ 已落地，否则槽位文本带源书专名）；7.1.1（凝练加 cast）。

#### 7.3.5 角色连续性（2026-09-12 规划 → ✅ 2026-09-13 B 档已实现 —— 用户提出）

##### 为什么单独立项：四问实测，三处零机制、一处有数据没逻辑

| 用户担心 | 实测 | 证据 |
|---|---|---|
| AI 需要新角色 → 合理引入 | ❌ **不存在**。`planned_chars` 全仓库只出现 **2 次且都是注释** | `routers/plans.py:12`、`services/plan_crud.py:10` —— 无列、无代码、无端点；"拍板后走待确认实体"是**空头承诺** |
| 角色已死 → 被复活 | ❌ **无法表示**。`characters` 表**没有 status 列** | `models/orm.py:31-50`（隔壁 `factions` 有，`orm.py:86`） |
| 几十章没出现却被匹配到 | 🟡 **数据在、没人读**。`chapter_memories.characters` 每章落库 | `orm.py:411`；但全仓库唯一读取点是 `memory_crud.py:207` 的序列化 —— **无任何逻辑算"最近出场"** |
| 上篇在场 → 本篇莫名消失 | ❌ **完全没人管**。篇间无交接 | `layers.layer_chapter_plan` 注入 beat/要点/钩子/字数/前后章，**无角色状态**（`layers.py:561-581`） |

**加重项**：`plan_crud._book_context` 取角色是 `characters.limit(40)`，**无排序、无筛选**（`plan_crud.py:49-50`）
→ **死角色、失踪角色、三百章没出现的角色，与主角平等地进上下文**。

##### 为什么 A 档（状态门）并进 7.3 而不是放在这里

casting 是"计划生成时算一次、全篇锁定"，而角色可用性**随章节推进变化**（第 3 章活着，第 50 章死了）。
一次锁定 + 忽略状态 = 必然出现"第 60 章还在用第 3 章选的角色，而他 40 章前就死了"。
**所以状态不是加分项，是 casting 的必需输入** —— 没有它，7.3 交付的是一个会系统性产出连续性错误的选角器。

##### 状态模型定稿（四态）

| 状态 | 含义 | 选角规则 |
|---|---|---|
| **在世** | 正常 | 正常参与选角，可直接召回 |
| **蛰伏** | 久未出场（超阈值章数） | **可入选，但必须写明回归理由**（不禁"久别重逢"，但强制交代） |
| **离场** | 明确离开（离队/远走/失踪/飞升） | 召回须交代回归理由；**用户原提"虚死"即此态**（改名以避免实现者真按死处理），保留**显式放行** |
| **已死** | 死亡（有明确事件） | **默认不进候选池**；回忆/幻象/夺舍等需**显式标记**才放行 |

##### 字段定稿：派生 vs 抽取要分工（关键）

| 字段 | 来源 | 理由 |
|---|---|---|
| `last_seen_chapter` / `appearance_count` | **纯派生**（扫 `chapter_memories.characters` 统计，可重算） | **绝不能靠 LLM** —— 统计能重算、能验证 |
| `status` | **抽取 + 人工可改** | "最后出场"≠"死了"（可能是闭关/失踪/退居幕后），纯统计推不出来 |
| `disappear_mode` / `disappear_chapter` / `disappear_evidence` | **窄任务抽取 + 人工可改** | 见下 |
| `status_evidence` | 抽取（哪一章、哪句话） | **可解释、可回溯、可翻案** |

##### `disappear_mode`：用户最有价值的一条（把模糊概念变成可判定字段）

```
explicit  有具体离场事件（失踪 / 跌落 / 被追杀失散 / 死亡）
silent    只是后续章节没再写他
unknown
```
`explicit` 再分 **`dead` / `missing` / `departed`**（三者的放行条件完全不同：死亡回归只能靠回忆/幻象/夺舍；
失踪回归天经地义）。

**为什么关键**：`silent` 退场的人回归几乎不需要理由（他就是没被写），
`explicit` 失踪/死亡的人回归**必须交代**。没有这个区分，"编回归理由"根本无从下手。
**注意区分**："被人提到/回忆"**不算**出场，也不算消失事件（用户明确要求）。

##### 回归理由：确定性预取，**不走 FC**

| 步骤 | 由谁决定 | 需要模型自主决策吗 |
|---|---|---|
| 谁需要回归理由 | casting 已算出（`needs_reentry_note`） | 不需要 |
| 他哪一章消失 | 台账已算出 | 不需要 |
| 消失后到现在的篇章梗概 | 一个 SQL + 按实体命中补取细节章 | 不需要 |

**三步全是确定性查询 → 用 FC 等于把确定性任务交给不确定性组件**，与 `chapter.py:254` 当年放弃
AI 两阶段 `LOAD_REFS`（"本地模型在该协议上不稳定，时而全不加载、时而一股脑全加载"）是同一个坑；
也是 03 里"那条链要的是稳定不是自主性"的同一判断。

**FC 在这个场景的正当用武之地**（不否认）：缺席期很长（如 80 章）导致材料超窗口时，模型可能需要
**多轮取数**（先看篇章梗概 → 发现某几章关键 → 再取细节）——**步数不确定**才是 FC 的场景。
即便如此，**后端两级预取**也能做，仍保持确定性。→ **本功能用预取实现，FC 留给 7.6 的 `retrieve_templates`。**

##### 回归理由的来源优先级（2026-09-12 用户认可后补充）

```
① 他自己的未回收伏笔   ← 埋-收结构天然成立；伏笔表现成（buried_chapter + status）；
                          且 01 已把伏笔列为"长篇最核心价值" → 几乎零额外成本
② 缺席期的世界线事件   ← 势力在动 / 大事记
③ 纯新编               ← 兜底，质量最差
```
**把"编理由"变成"收伏笔"**，比让模型凭空编高一个档。

##### 新角色引入链路（补上断掉的一环）

现状断在中间，需要补的是 `new_chars` → `pending_entities` 这一环：

```
计划生成 → new_chars（只在计划里）
   ↓ 拍板        ← 【缺这一环：落 pending_entities】
待确认实体（现成机制，当前只接写后摄取的 new_entities）
   ↓ 作者确认
写 characters（带 first_appearance / status=alive）
```
三条约束（防止"引入新角色"变成"人物爆炸"）：
1. **必须绑定功能位** —— 即"他是来补哪个 cast 槽位"。与 7.3 的 `unmatched` 槽位**天然是同一条链**：
   槽位没匹配到 → 问作者"新建角色 / 改选现有角色"。新角色因此**天生带 role_desc 和 slot**，不是凭空的名字。
2. **限额**：一篇新角色上限 **≤3**（LLM 没有成本感，不设限会一篇造五个）。
3. **必须指定首次登场章**（`first_appearance` 写死），否则会出现"第 2 章就用了第 7 章才登场的人"。

##### 篇间交接校验（最便宜、收益最高，零 LLM 成本）

1. 规划前取**上一篇最后 1~3 章**的 `chapter_memories.characters` → "上场遗留名单"；
2. 计划生成后做**差集**：遗留名单里的人，本篇**既不在 `recall_chars` 也不在任何行的角色里** →
   **警告**（非报错）并列出，让作者三选一：交代他离场 / 安排他出场 / 忽略；
3. 同一位置做**硬拦截**：`已死` 角色出现在 `recall_chars` → **直接剔除并报告**
   （复用现在"查无此人剔除"的同一位置）。

##### 分档（避免一次吞掉）

| 档 | 内容 | 归属 |
|---|---|---|
| **A** | `last_seen` 派生 + `status` 字段 + casting 候选池按状态过滤 | **并入 7.3**（casting 的前置依赖） |
| **B** | 新角色引入链路（`planned_chars` 落地 + 限额 + 首登场章）+ 篇间交接差集校验 | **本小节 7.3.5** |
| **C** | `status` 自动抽取（改写后摄取 prompt）+ 状态可视化 UI | 以后再说（成本高，先靠作者手改也能跑） |

##### 验收（对应 docs/01 §4 门槛 8）

`已死` 角色不出现在计划中；久缺席角色被召回时**带可解释的回归理由**（且理由优先来自未回收伏笔）；
上一篇在场、本篇消失的角色被显式交代。三者均为**代码层校验**，不依赖模型自觉。

##### 诚实边界（不得标 ✅）

1. **一条都验不了**：`chapters` = 0 行、`chapter_memories` 33 行、`characters` 2 个空角色
   → 只能造临时项目验逻辑，效果验不了。
2. **`disappear_mode` 抽取未实测**：新概念，需先小样本真机测 prompt（会不会把 `silent` 判成 `explicit`），

### 8.1 批次3 原方案的两处前提修正（重要，防误做）

原方案写「建卡 prompt 注入 top-3 原型（`_plan_prompt` ≤1800 字符护栏）」。经读码核实，**两处对不上**：

1. **建卡没有 prompt**：`plan_crud.confirm_planned_char`（:482）是**纯写库动作**（拿作者手填的 `attrs` 直接
   `create_character`），整条链无任何模型调用 → 「注入 prompt」无处置入。
2. **`_plan_prompt` 属于规划阶段**（`generate_plan`），彼时 `new_chars` 只有角色名字符串，**尚无任何人格信息**
   → 拿不到原型去比对；且强行注入等于在规划期就定死人格，**越权**。

**修正后的注入点**：**建卡弹窗顶部的「功能位参考」区**（`PlanView.vue:486` 弹窗内）。理由：作者填
`personality`/`brief` 的地方，正是「这个功能位该是什么样的人」该参考的地方；且 `planned_chars` 已带
`slot`/`slot_desc`，**现成查询键**。

### 8.2 借鉴层级定稿（四层，本项目角色设计的方法论基石）

经用户论证修正（2026-09-15）—— **性格与位阶必须组合使用，单给性格反而有害**：

| 层 | 内容 | 数据现状 | 决策 |
|---|---|---|---|
| **L1 功能位** | 「主角起步期的引路人」 | ✅ 793 条现成 | **S1 做** |
| **L2 性格 × 位阶** | 「自私的长老」vs「自私的散修」vs「自私的商贾」 | 🟡 可从现有 desc 提取，未结构化 | **S1 做**（位阶拆分） |
| **L3 具体设定** | 残魂成因、退婚、专名（魂殿/药老） | ❌ **刻意不给** | 本书自创（护栏：卡片须标注） |
| **L4 行为逻辑** | 语言风格、思维方式、习惯、信念 | ❌ **库里没有，需回源重抽** | **S5 做** |

**L2 为什么关键（用户核心论证，已采纳）**：
- 性格是多维组合（理智/守序/隐忍/求稳/利己…且每维程度不同），**AI 难以凭空组合出令人满意的角色**；
- 更危险的是**单给性格标签会导致错误匹配**——「无恶不作的小混混」被 AI 配上「见义勇为」，
  因为**性格脱离位阶就无法判定行为**；
- 同一个「自私」，长老表现为结党营私、散修表现为偷奸耍滑、商贾表现为囤积居奇 ——
  **「性格 × 位阶」才是最小可用的借鉴单元**。

**L3 为什么刻意不给（用户举例，已采纳）**：借鉴的是「主角身边有个已陨落但仍在指引的强者」这个**功能**，
而**不是**「被魂殿追杀」「化成残魂」这些**具体成因** —— 后者一旦提供，写第三本书还会照抄。

### 8.3 检索多样性（治「库大反而稳定雷同」）

用户原判断「只要爬够多，雷同概率就低」——**前半句成立，后半句不成立**。原因在检索而非库容：
`search_similar` 是 top-k 语义近邻，**库再大，命中集仍是那几条最贴近的**；连写三本书用同一功能位，
检索词高度相似 → 命中同一批模板 → **库大了是「更稳定地雷同」，不是「更随机地多样」**。

→ **解法在检索层**（S1 实施）：
1. **排除最近 N 次已用过的模板**（查 `article_plans.template_ids` —— ⚠️ 2026-09-16 更正：原文写的「`usage` 表」**在库里不存在**，实测 34 张表无 usage；最近用过的模板由计划的 `template_ids` 派生，**不必新建表**）；
2. **跨书组轮换**（库内已有 7 个跨书组，天然轮换池）。

| 位阶结构化 | `archetype_text` 增加 `rank` 维度（长老/弟子/商贾/散修），**重新回填 793 块** |
| 检索去重 | 用 `article_plans.template_ids` 取「本作品最近 N 篇用过的模板」并排除（见 8.3；**原写的「usage 表」不存在**） |
| 前端 | 建卡弹窗顶部「功能位参考」卡片区（`PlanView.vue:486`） |
| 护栏 | 卡片显式标注「**只参考功能位，具体设定请本书自创**」；单卡 desc 截 80 字 |
| 交互 | 「用作草稿」按钮**只填 `brief` 一个框**（不代笔 personality，避免 AI 代笔惯性） |
| 失败降级 | 向量库不可用 / 无 `slot` → 参考区**整块隐藏**，不阻塞建卡 |

**查询串退化顺序**（用户确认）：`slot_desc` → `slot` → 二者皆无则**隐藏**（不拿角色名瞎搜）。

**效果**：793 条原型**首次被消费**（建成半月从未被任何一次建卡使用）；新建角色有立体度参考。
**注意**：本阶段**不会自动让角色变立体**——它只提供参考，B 病症需作者据此填 `personality`。

**验收**：建 1 个角色 → 弹窗出现 3 张卡 → 卡片与 `slot_desc` 语义相关（人工判断）→ 「用作草稿」只改
`brief` 不改其他框 → 单测 ≥390 绿。

### 8.6 S2 · 治「黑袍人」病（三项，缺一不可）

**用户修正后的定稿**（禁止代称**不可一刀切**，会砍掉叙事钩子）：

| 子项 | 内容 |
|---|---|
| **① 代称分流** | **普通配角/路人/随从 → 必须有名字**；**刻意隐藏身份 → 允许代称**，但必须标记「待揭晓」（`name_known: false`）；真名出现时（如「黑袍人揭开兜帽，露出周执事的脸」）**自动归并到真名**（复用已有 `aliases` 表，3009 条）。**核心：允许代称，但要求「代称 → 真名」有归并路径，不许永久悬空** |
| **② 放开限额 + 舞台切换** | `PLANNED_CHAR_LIMIT` 3 → 8；规划 prompt 新增 `stage_change` 判断，为 `true` 时配额放宽（8 → 12）且**要求本篇前 2 章完成新人铺设**（先铺人，再写事） |
| **③ 提高 `new_entities` 抓人敏感度** | 当前抽取**根本没在抓人**（实测抽出的全是道具/概念）。要求抽出「有名字有戏份的新角色」进待确认队列 —— 这是治「第一篇没角色」最直接的一刀 |

**为什么用「舞台切换」而非「保证角色库 > 10」**（用户原提后者，经论证替换）：

| | 保证库 > 10（原方案） | 舞台切换显式化（采纳） |
|---|---|---|
| 依据 | 拍脑袋的阈值 | 剧情实际需要 |
| 换地图时 | 要重新凑数 | 自动放宽 + 要求前 2 章铺人 |
| 会不会造僵尸 | **会**（凑数凑出来的） | 不会（都是剧情要的） |
| 作者可控性 | 不能 | 能（提示可忽略） |

**根因**：角色库是**全局的、不受篇章约束**——库里 5 人、下篇换地图要 8 个新人，库变 13 个，
但这 8 人与上篇 5 人毫无关系，**「库里数量达标」≠「本篇该有的人铺上了」**。

**人口基线（提示而非报错，不阻塞）**：
```
本篇可用角色 = 库内活跃角色（status=alive 且近 N 章出场）+ 本篇 new_chars
若 < 6 → 计划页提示「本篇可用角色偏少，建议补充新角色或召回旧角色」
```

**风险点**（必须知道）：
- 「禁止代称」可能被模型用「看似有名字但敷衍」（如「路人甲」）绕过 → 需**后校验**（`_valid_lines` 检查名字长度与黑词）；
- 放开到 8 有可能真爆炸 → **先放开看实测**，不要预先做配额系统（那是 S4 的判据）。

**效果**：A/B/D 三病缓解；一篇常驻人口 3 → 6-8（正常网文水平）。
**验收**：生成一篇 8 章计划 → `new_chars` ≥5 且**均有具体姓名**（无代称）→ 单测全绿。

### 8.7 S3 · 角色修订表（里程碑）

> **为什么这是里程碑**：这一步之后角色从「静态卡片」变成「有历史、有版本、可追溯的活体」——
> 这才是用户所说「角色彻底立体」的**真正支点**，而非 S5 的库。

| 项 | 内容 |
|---|---|
| 新表 | `character_revisions`：`character_id / snapshot(JSON) / source(ai_extract·manual) / status(pending·approved·rejected) / chapter_no / created_at` |
| 写入时机 | ① 建卡时写一版；② 作者改卡时写一版；③ 章节摄取抽出角色变化时写 **pending** 版 |
| **AI 改动纪律** | **默认 pending，不直接覆盖角色卡**；计划页推「第 N 章显示 X 有转变迹象」待作者确认 |
| 回档 | 角色详情页可查历史版本、一键回滚 |
| 客观项 | 出场章/互动关系等**继续自动更新**（已实现，无害） |

**为什么不做全库快照**（用户原提「每篇结束存档数据库」）：SQLite 全库快照每次复制几十 MB，且**粒度太粗**
（想恢复一个角色却整库回退）。改为**单角色粒度**，复用 Phase 4.1 `chapter_variants` 的既有范式。

**两档分工（治漂移的核心）**：

| 类型 | 处理 | 理由 |
|---|---|---|
| **客观项**（出场章、互动关系、势力归属） | ✅ 自动更新 | 可重算可验证，自动无害 |
| **主观项**（性格、信念、地位变化） | ⚠️ **只提示不覆盖** | 一章的剧情表现会带偏人设（30 章冲动、31 章谨慎 → 卡片来回横跳 → 薛定谔的性格） |

**效果**：角色能随剧情生长，但不会失控；可回档。
**验收**：造一次 AI 改动 → 角色卡不变 + 计划页出现待审 → 确认后生效 → 能回滚到上一版；单测全绿。

### 8.8 S4 · 常驻角色动态配额（待定，预计不需要）

**用户原方案**：第一篇章常驻上限 8 → 第二篇 9 → …第 10 篇 15；战场篇临时调高、冷淡篇调低、
章数多则小幅度增加。

**保留意见（预计 S2 后此问题自解）**：
- 该方案**本质是用配置模拟剧情判断**，而「这篇是战场篇还是冷淡篇」**只有模型读剧情才知道** → **调参地狱**；
- 若 S2 做完仍爆炸，做**最简形态**：不是配置表，而是给 `_plan_prompt` 一句「本篇常驻角色建议 N 人」
  （N 由现有活跃角色数算出，**不手工配**）。

**注意用户提出的两个语义澄清（已采纳，需在 UI 体现）**：
- **常驻角色 ≠ 每章必须出现**（现 AI 可能有此错觉，硬给角色找事做）；
- **非常驻 ≠ 本篇不出现**（可通过他人回忆、他人提及引入 —— 这正是 GraphRAG 一跳的价值）。

### 8.9 S5 · 角色样本库 L4（最后，前置条件硬性）

**做什么**：回源书 2453 章，为重抽「该槽位角色的典型台词/行为片段/思维方式」改凝练管线；
建 `char_sample` 第四路向量索引。

**为什么放最后**：

| 风险 | 说明 |
|---|---|
| 波及面大 | 要动 `plot_distill.py`，而它承载 165 模板 + 793 原型 → **重跑一次两个现成资产都要重来** |
| 成本高 | 2453 章重抽 + 凝练，小时级任务 |
| **前提未验证** | S1 还没跑过，**不知道「借鉴原型」到底有没有用** |

**🔴 前置条件（硬性，不可跳过）**：S1 实测后，必须能回答「**用了原型参考的角色，比没用时更立体吗？**」。
回答不了，S5 不启动。

**备选做法**：若 S1 证明有用，先**小规模试**——只抽 1 本书（如斗破 200 章）建样本库，验证效果再定全量。

### 8.10 最小可用版（若嫌规划太大）

**S1 + S2 即可见明显改善**：原型被用起来（S1）+ AI 会起名、有基本人设（S2）→ 重跑一篇可见
「黑袍人消失 + personality 非空」。**S3 之后再单独立项**（涉及「AI 能否改人设」的权限设计，需仔细）。
