### A2 · 沙箱起后端产生关不掉的 8000 孤儿进程
- **2026-08-11 确诊**
- 现象：沙箱里起后端后，`taskkill` 报"找不到进程"，但端口一直被占，只能重启机器。
- 根因：uvicorn `--reload` 会 `subprocess.Popen` 拉一个**孙进程 worker**（真正绑 8000 的）。沙箱只跟踪它直接 spawn 的 reloader；reloader 被杀后 worker 变孤儿，**PID 不在任何可寻址空间**。
- 解决：① `dev.py` 默认改 `reload=False`（已做）；② 沙箱起后端一律 `DEV_RELOAD=0`。
- 现状：已根治。换端口（8001）只是应急，不是解法。

### A7 · ⚠️ 在沙箱里跑 `git fetch` / `git rebase` 会**破坏 `.git`**（2026-09-10 实测，代价很大）
- **现象**：一次 `git rebase <远程sha>` 报 `could not mark as interactive: No such file or directory`，
  随后所有 git 命令变成 `fatal: not a git repository`。
- **根因**：`.git/refs/` 整个目录被抹掉（连同 `refs/heads/main`），且**新写入的松散对象丢失**
  （`git commit` 刚成功的提交对象、`git fetch` 刚拉下来的提交对象都读不出来）。
  沙箱对 `.git/refs/**`（尤其 `refs/remotes/`）的写/改名做了拦截，git 拿不到预期的文件系统语义，
  清理或回滚时把目录一起带走了。同类现象：`git fetch` 报告 `[new branch] main -> origin/main` 成功，
  但 `refs/remotes/origin/main` 根本不存在（`git rev-parse origin/main` 报 unknown revision）。
- **判别方法**：git 判定「有效仓库」要求 `HEAD` + `objects/` + **`refs/`** 三者齐全。
  一旦 `.git/refs/` 消失，git 会直接说 "not a git repository"，**而不是**报 refs 缺失——很容易误判成仓库被删。
- **恢复流程（已验证有效，约 5 分钟）**：
  1. **立刻 `cp -r .git /e/AI_novel_git_backup_<ts>`**（把损坏的 .git 整体留档，禁止在原件上试错）；
  2. `mkdir -p .git/refs/heads .git/refs/tags`（**只建目录**）→ git 立刻恢复识别仓库；
  3. `git cat-file --batch-all-objects --batch-check` 枚举现有 commit，确认历史断在哪一条；
  4. 本地 pack 若也缺对象（`git ls-tree <sha>` 报 unable to read），**以远端为准重建**：
     `mv .git .git.corrupt.<ts>` → `git init -b main` → 配 remote → `git fetch origin main`
     → `git update-ref refs/heads/main <FETCH_HEAD>` → `git reset --mixed`（重建索引，**不动工作区**）；
  5. `git status` 会列出全部未提交变更 → 重新提交 → push。
- **关键前提**：**工作区文件从不受影响**（沙箱只搞 `.git`），所以只要远端有完整历史，就能 100% 还原。
- **铁律（写进工作方式）**：
  1. **沙箱里不要用 `git rebase`**。要同步远端新提交，用 `git fetch` + `git merge`，或干脆以远端为准重建本地仓库；
  2. **push/rebase 前的第一件事是 `cp -r .git` 备份**（1.6MB，一秒的事）；
  3. 每次 `git push` 前先 `git ls-remote origin main` 对一下远程 SHA，避免"远程被别人改过"导致的拒绝+随后一串危险操作；
  4. 远端仓库本身就是最好的备份——**保持每次工作结束都 push**，本地 `.git` 就不是单点。

### A8 · ⚠️ 沙箱里删「目录内任一文件」会**连带清空整个同级目录**（2026-09-10 实测，Phase 3.1 踩中）
- **现象**：用 `git rm frontend/src/components/workspace/ChapterElementsPanel.vue`（只删 1 个文件），
  结果 **`components/workspace/` 整个目录 7 个文件全没了**；把 `Remove-Item -Recurse` 指向 `_deprecated/`
  时，连 `views/  store/  router/  layout/  utils/  styles/` 一起消失（共 31 个文件）。`git status` 显示一地 ` D`。
- **根因**：沙箱的文件系统拦截层在「删除受保护目录内的条目」时，会把**同级目录树**一并标记删除，
  不是 git 的错（`git rm` 本身只删指定路径）。同一命令**单文件 `rm -f` 时不触发**，
  但 `git rm` 或 `Remove-Item -Recurse` 会触发。
- **判别方法**：删完**立刻数文件**——`find <dir> -type f | wc -l`，与期望值逐一核对；
  再看 `git status --short | grep "^ D"` 有没有出现**你没打算删的路径**。
- **恢复（100% 可靠，全部源码都在 git 里）**：
  ```bash
  rm -f .git/index.lock                     # 被杀进程常留陈旧锁
  git restore --source=HEAD --worktree --staged <path>
  ```
  本次 31 个文件、63 个文件规模都秒级还原；**工作区内容从不受损，只是被误删**。
- **铁律**：
  1. **删文件优先用 `rm -f <单个文件>`**（实测安全），**不要**用 `git rm` / `Remove-Item -Recurse`
     在**多文件目录**上操作；
  2. 必须让 git 记录删除时，用 **`git update-index --force-remove <path>`**——纯索引操作，
     **完全不碰文件系统**，彻底绕开此 bug；之后再 `rm -f` 单个文件清磁盘；
  3. 批量删除前先 `cp` 备份到 `/tmp/`，删完立刻数文件核对；
  4. 一旦发现误删，**先 `git restore`**，不要在乱状态上继续操作（尤其别 `git add -A`，
     否则把误删写进暂存区，风险陡增）。

### A10 · ⚠️ git commit「报错但实际成功」+ 同名分叉提交的处置（2026-09-10 实测，Phase 3.4）
- **现象一：commit 报 `nothing added to commit`，但提交其实已经产生。**
  本次执行 `git commit -F <msgfile>` 时，输出是：
  ```
  nothing added to commit but untracked files present
  ```
  紧接着 `git status` 显示**暂存区空、工作区也干净**，而 `git log` 里**已经多出了那条提交**。
  根因：前一步 `git reset --soft HEAD~1` + 紧接着的 `git add` 之间，**索引被并发/沙箱包装层写坏**，
  commit 在读取到旧索引的另一条路径上完成了。
  → **铁律：`git commit` 后不要只信它的 stdout，必须 `git status --short` + `git log --oneline -1` 双验证。
  看到「nothing to commit」而工作区又干净时，先查 `git log`，十有八九已经提交成功，再 commit 一次会建重复提交。**
- **现象二：远端与本地出现「同名不同 sha」的分叉提交。**
  因为上面那次「报错但成功」，远端留下了 `832ef4f`，随后我又压了一条 `2ec2e51`；
  两者 **`parent` 都是 `dae35c4`** → 是**兄弟分叉**，不是父子，所以普通 `git push` 必被拒
  （`non-fast-forward`）。
  **判别分叉**（别硬猜，一条命令看清）：
  ```bash
  git log --format="%h %p %s" -1 <A>   # 看 A 的 parent
  git log --format="%h %p %s" -1 <B>   # 看 B 的 parent
  # parent 相同 = 兄弟分叉；A 的 parent 是 B = A 是 B 的后代
  ```
  **处置（本次采用）**：先 `git diff --stat <远端sha> <本地sha>` 看清两者**实际差什么**——
  本次只差 CHANGELOG 的 2 行（本地版修了一个多余的 `- ` 前缀 + 补了路由口径说明），
  即**本地版严格更优**，且仓库是**单人本机工具**、远端无他人提交 → 打两个备份 tag 后
  `git push --force-with-lease=main:<远端sha> origin main`（**带 lease 比 `-f` 安全**：
  若远端在此期间被别人推进过，lease 校验会直接拒绝）。
  推完 `git ls-remote origin main` 核对 sha，并删除备份 tag。
  → **反例警示**：如果两者差异是「各有对方没有的内容」，就必须走 `merge`/`rebase` 合流，
  **绝不能 force**。force 只适用于「远端那条已被证明是废弃品且无独有内容」。
- **现象三：`origin/main` 报 `unknown revision` 但 push 却成功。**
  沙箱拦截 `refs/remotes/**` 写入（同 **A7**），`git fetch` 显示 `[new branch] main -> origin/main`
  但盘上**只生成了 `.git/FETCH_HEAD`、没生成 `.git/refs/remotes/origin/main`**。
  → **核对远端状态一律用 `git ls-remote origin main`（直接问服务器），不要信 `origin/main` 这个本地 ref。**
  同理 `git status -sb` 里的 `[gone]` 也是这个原因，**不代表远端分支被删**。
- **衍生教训（编码误判）**：我一度以为提交里 CHANGELOG 是乱码，差点据此做决策。
  实际把 `git show <sha>:CHANGELOG.md` 的**字节流**取出来解码数 `\ufffd` 与 `\uXXXX` 字面量，
  两个提交**都是干净的** —— 我看到的是**工作区的临时中间态**。
  → **判断「提交内容坏没坏」必须看提交对象（`git show <sha>:<path>`），不能看工作区当前文件。**

### A11 · ⚠️ 用 `git checkout -- <file>` 还原「实验性改动」会**连未提交的正式改动一起回滚**（2026-09-10 实测，Phase 3.5）
- **场景**：为验证新写的护栏测试**真的能抓到违规**，我临时把 `load_observation.py` 的一个
  handler 改成 `except Exception: pass`（违规版）。验证通过后想还原这个**实验性改动**，
  顺手执行了 `git checkout -- backend/app/services/load_observation.py`。
- **后果**：该文件**尚未 commit** 的 Phase 3.5 正式改动**被一起回滚掉了**——因为
  `git checkout -- <file>` 的语义是「**把工作区该文件恢复成 HEAD 的版本**」，
  它**不认识**"哪部分是实验、哪部分是正式"，一律丢弃。
  （侥幸发现：我在注入前 `cp` 过一份 `.bak`，但命令里 `git checkout ... || cp .bak` 的
  短路顺序写错——`git checkout` 成功返回 0，`.bak` 分支**根本没执行**，差点白丢。）
- **铁律**：
  1. **任何"改代码做实验"之前**，若该文件有**未提交**改动，先 `git stash push -- <file>`
     或 `cp` 到项目外的临时路径（**别信 `||` 兜底，成功即短路**）。
  2. 实验完还原时，**优先用 `cp` 把备份放回去**（语义明确），不要用 `git checkout --`（它回 HEAD）。
  3. 若确实误回滚了：未提交改动**无法从 git 恢复**（`git reflog` 只救 commit 过的）。
     只能靠备份 / 重新实现。**所以备份是唯一保险。**
- **自检习惯**：回滚一个文件后立刻 `git status --short` 看它**是否还在修改列表里**——
  若本该有改动却消失了，就是被回滚了（我这次正是靠这步发现）。

### A7. `git push` 静默 128：真凶是 gh credential helper 子进程（2026-09-13，三次更正终版）

- **现象**：push 恒 rc=128，stderr 只有 `Pushing to ...` 一行（PowerShell 管道连 fatal 文本都捕不到）。
- **三次误判史**：①最初判"凭据助手被杀"→ ②推翻为"PowerShell 静默即杀看门狗，GIT_TRACE 是开关"
  （15:10 无 trace 连挂 3 次、带 trace 首试即中）→ ③ 16:15 **带全套 trace 依然 128**，二次推翻。
- **对照实验（终版定论）**：两次推送都带全套 GIT_TRACE，唯一差异 `-c credential.helper=`——
  禁 helper 一次成功（pack 传输 trace 全程可见）。trace 尾部证据：HTTP 正常完成后
  `run_command: gh.exe auth git-credential store`，助手子进程没回来 → git 128。
  **真凶 = gh credential helper 子进程被环境杀（get/store 阶段都可能，呈随机性）；
  "带 trace 即成功"是幸存者偏差——那几次 helper 恰好活着。**
- **最终稳定方案（token URL 下 helper 纯多余，禁用无副作用）**：
  ```powershell
  $tok = gh auth token
  git -c credential.helper= push --progress "https://oauth2:$tok@github.com/<owner>/<repo>.git" main
  ```
- **排障顺序**：push 128 → 先 `git ls-remote` 确认网络/仓库可达 → token URL + 禁 helper 重推
  → 仍 128 才叠加 GIT_TRACE 系列看卡在哪个阶段。

### A14 · ⚠️ Windows 回收站删除的「报败实删」三连坑（2026-09-19 实测，源书清洗）

**背景**：清洗四本源书（删作者交流章）时要在**不永久删除**的前提下删 ~70 个文件，试了三种方案：

| 方案 | 结果 |
|---|---|
| `ctypes` SHFileOperationW + FOF_ALLOWUNDO | **rc 不可信**：报 rc=2（失败）但文件**实际已进回收站**；且 `c_wchar_p` 遇内嵌 `\0` 截断 → pFrom 单 null 结尾（要求双 null），每轮行为随机（一轮只成功 1~2 个） |
| PowerShell `Microsoft.VisualBasic.FileIO.FileSystem::DeleteFile(..., 'SendToRecycleBin')` | **同样报败实删**：failed 列表记了全部 59 个，实际全删成功；另 `Set-Content -Encoding UTF8`（PS 5.1）写 BOM，Python 要 `utf-8-sig` 读 |
| ✅ `send2trash`（pip 包，内部走 IFileOperation COM） | **唯一结果可信**：报错=真失败、成功=真删 |

**附带坑**：
- Bash 里 `subprocess` 调 `powershell` 被安全层拦（"bypasses PowerShell security checks"）；PowerShell 工具里 `Add-Type` 也被拦（"compiles and loads .NET code at runtime"）→ 纯 PowerShell 路线两头堵。
- Shell 类 API 在**沙箱内必被拦**（与热键/GUI 同类），需 `dangerouslyDisableSandbox`。

**铁律**：① 删文件要可恢复 → 直接用 `send2trash`，别再试别的；② **任何批量删除后必须用文件系统现状核账**（重扫计数），别信 API 返回值——三种方案里两种在撒谎。

### A15 · ⚠️ 用系统 Python 起后端 = 向量链路静默降级，且 8000 端口会「谁起谁占、互不知情」（2026-10-03 实测，DEV-F9b 验收期）

**现象**：`plot-templates/search` 与计划生成的模板检索时灵时不灵；`generate` 返回 `origin=free`、`raw_ai` 无 fallback 账；embedding 相关 WARNING 刷屏 `未配置硅基流动 API Key` / `EmbeddingError`。

**根因（两层）**：
1. **解释器错**：系统 Python 3.12（`C:\...\Python312\python.exe`，PATH 里的 `python`）**没有 `sqlite_vec`**。`.venv` 有。后端必须用 `E:\AI小说创作\.venv\Scripts\python.exe dev.py` 起。
2. **端口占位混乱**：Windows + uvicorn 的 SO_REUSEADDR 语义下，先后多个 dev.py 进程都能绑 8000（`netstat` 只显示一个 PID）；执行会话的进程退出后，另一个（可能是手动用系统 Python 起的）顶上——**同一天三个进程（13764/5664/35308）先后占 8000，配置与代码加载状态各不相同**。旧进程内存里的旧代码/坏配置继续接请求，新代码的验证全打在旧进程上。

**识别方法**：`Get-CimInstance Win32_Process -Filter 'ProcessId=<8000监听PID>'` 看 CommandLine 是不是 `.venv\Scripts\python.exe`；再看 `backend/logs/backend.log` 最新一段有没有 `EmbeddingError`。

**铁律**：① 起后端只认 `.venv` 绝对路径；② 服务异常先杀干净所有 `dev.py` 进程（`Get-CimInstance | Where CommandLine -like '*dev.py*'`）再起一个；③ 验证行为异常时，先确认「打到的是哪个进程」，别在代码里找鬼。

### A16 · ⚠️ `article_plans.updated_at` 等时间戳存的是 **UTC**：按本地时间核账会「行消失」（2026-10-03 实测）

**现象**：18:48（北京时间）生成的计划，DB 里 `updated_at = 2026-10-03 10:48`——按本地时间排序/过滤会以为「最新生成的那行不存在」。

**根因**：`plan_crud.py` 等多处用 `datetime.utcnow()` 写时间戳（06 手册已知 deprecation，尚未统一改 timezone-aware）。**同一表里新老行混用**（旧行可能是本地时间）时，`ORDER BY updated_at DESC` 的结果**不可信**。

**连带坑**：`article_plans` 存在**孤儿行**（`article_id` 指向已不存在的文章，如 `d2d00cf9`）——04-D6「先做差集再引用行数」的老规矩在这里同样适用；且对孤儿 article 发起 `generate` 会**静默落库成孤儿行**（`_book_context` 全容错，无 article 校验）。

**铁律**：① 核账/排序前先确认该列存的是 UTC 还是本地时间（看代码写入点）；② 引用任何行数前先对 `project_id`/外键做存在性差集（D6）；③ 「新生成的数据查不到」时，先怀疑时间戳时区与孤儿行，再怀疑代码。

## B. 模型行为类（**最值钱的一组，改提示词/参数前必读**）

### B1 · ModelScope Qwen3.5-122B 长生成中后段退化 = 重复惩罚
- **2026-08-14 A/B 实测确诊**
- 现象：章节"前段正常，写约 1/3 后突然变无标点长段 + 成语接龙 + 人名退化成拼音（Biao Yuan Zhou）+ 夹英文词"。
- 根因：`frequency_penalty=0.4` + `presence_penalty=0.4` 把该模型中后段采样逼崩（惩罚推"求新"→偏离正常分布）。
- **关键教训**：**短生成测试永远正常，是假象**。必须测长输出（≥5000 token）才能复现。
- 解决：`chapter.py` 按 combo 判断——`qwen3.5 in model and modelscope in api_base` → freq/pres 默认 **0.0**（env `NA_CHAPTER_REP_PENALTY`/`NA_CHAPTER_PRES_PENALTY` 可覆盖）；ollama 保持 `repeat_penalty=1.3`；其余厂商保持 0.4。
- 现状：已修。`assist.py` 草稿仍 0.3/0.2，**若长草稿退化需同样处理**。

### B2 · 思考字段的厂商差异（错一个字段，正文全进 reasoning）
- **2026-08-12 / 08-13 两次确诊**
- 现象：NVIDIA GLM-5.2 生成章节，弹窗只显示"思考过程"17273 字，**正文 0 字**。抓 SSE 日志：`content_len=0` 全部帧，`reasoning_content` 非空（里面其实是中文正文）。
- 根因：`openai_compat.py` 把 `nvidia` 归进 `chat_template_kwargs.enable_thinking` 阵营；而 NVIDIA NIM 的 GLM-5.2 应用**顶层 `thinking:{"type":"enabled"}`**（同 zhipu/deepseek）。字段不匹配 → 模型进入"只走 reasoning、content 为空"的异常态。
- 解决：厂商白名单——`qwen`/`nvidia`… 修正为：
  - `zhipu` / `nvidia` / `deepseek`：顶层 `thinking.type`（deepseek 还需 `reasoning_effort`）
  - `qwen`：`chat_template_kwargs.enable_thinking`
  - `openai`：无思考字段（o1/o3/o4 用 `max_completion_tokens`）
  - kimi/ernie/spark/siliconflow/custom：无标准字段
- 现状：已修。**新增厂商时先确认它认哪个字段，否则 400 或正文丢失。**

### B3 · vendor 填错导致安全网被绕过
- **2026-08-14 确诊**
- 现象：默认模型标 `vendor="custom"`（非 `qwen`），而 `chapter.py` 的 `_broken_thinking_combo` 安全网与 `openai_compat._payload()` 都只匹配 `vendor=="qwen"` → **完全绕过**；`custom` 又不发任何思考字段 → 模型按默认 thinking=ON 跑 → reasoning 泄漏进 content，表现为"无标点长段 + 英文推理词 + 同义反复循环"。
- 解决：安全网改为按 `(qwen3.5 in model) and (modelscope in api_base)` 命中（**不限 vendor**），并在该组合下补发 `chat_template_kwargs.enable_thinking=false`。
- 教训：**别用 vendor 单一维度判断模型行为**，vendor 是用户手填的，可以填错。

### B4 · 长文复读（RepetitionGuard）的正确姿势
- **2026-08-10 → 08-12 三轮迭代**
- 现象：小模型/非思考模型写长文，同一段落复读 4–5 遍，直到 token 烧爆。
- 演进：
  1. 第一代：滑动窗口检测（600 字符，重叠率 >55% 且 >40 字符）→ 触发后停止 yield 但**继续消费迭代器** → 云端继续计费，且第二次生成内容未过滤混入正文。
  2. **错误修复**：有人写成 `for _rest in adapter.stream(...)` → **重新发起一次完整生成**（双倍计费 + 内容错乱）。已改为 `loop_stopped=True` 标志。
  3. 终版：触发后 `break` + `finally` 里 `gen.close()` → 关闭 HTTP 连接 → **模型立即停止、云端立即停计费**。
- 附带发现：GLM-5.2 **关闭思考**写 3000 字长文必复读；开 thinking 后恢复正常（2362 字完整）。→ `chapter.py` 章节生成**强制 `want_thinking=True`**（vendor≠ollama 时；ollama 例外，因为 ollama 在 think=true 时正文为空）。

### B5 · "越多约束越好"对 LLM 是假命题
- **2026-08-13 确诊**
- 现象：章节正文突然变成"成语接龙 + 无标点长段"。
- 根因：`skill_dispatch.py` 把「禁忌」类列为可无限叠加，导致 chapter 场景同时注入 3 条高压禁忌 SKILL（防复读 p310 / 去AI味 p300 / 一致性守卫 p290）。其中"防复读"内容极高压（"每 300~500 字必须新信息""每 800 字停一次自检""禁止解释前文"）→ 模型被逼出病态输出：每个成语都是"新信息"→ 成语接龙；不敢写过渡/呼应→ 无标点长段。
- 解决：**禁忌/禁令类必须互斥**，同类只留 priority 最高的一条。
- 教训：约束叠加会反向致病态输出。**排查"文风变怪"时优先看是不是 SKILL/提示词叠加过度。**

### B11 · 后处理"防复读"误杀：字符集 Jaccard 对中文短段落完全失效
- **2026-09-09**（Qwen3.8-Flash-Next 开 thinking 实测发现）
- 现象：开 thinking 后字数反而暴跌（流式 3018 字符 → 落库仅 1536），**DB 与流式不一致**；表面看像"模型写短了"。
- 根因：`_dedup_trailing_repeats`（尾部复读兜底）用**字符集合 Jaccard** 判段落相似。中文短段落 6~7 个字，字符集只差一个字 Jaccard 就爆 0.85——实测「沈砚看水洼。」vs「沈砚看向水洼。」= 0.857，触发"从此段全裁"，**后面 97 段正常剧情（1482 字符）全部陪葬**（含收尾钩子"牙印上刻着'伍'"，0 段真重复）。
- 修复（三重防线，离线 4 用例全过）：① 短段 <20 字不参与判定（短句呼应是正常手法）；② 相似度换 difflib（内容敏感），字符集 Jaccard 仅作 0.3 以下快速预筛；③ 连续 ≥3 个长段相似才判定复读（单段相似=呼应）。
- **最终定案（对照实验汇总）**：Qwen3.8-Flash-Next 正确配置 = **惩罚 0 + thinking 可开**。开 thinking 实测写 1894~2800 字达标正文（关 thinking 只自然停 1493），代价是首字 ~130s（reasoning 时间）。路由层 `_content_only_stream` 保证 reasoning 不进正文。
- **教训：① 判"重复"要看内容序列（difflib/编辑距离），不能看用字面（字符集合）——中文叙事段用字面高度重合是常态；② 兜底逻辑（防复读/防退化）本身必须有防误杀设计和测试用例，否则它杀的正常正文比病还重；③ e2e 报告里"DB 与流式不一致"是发现这类静默坑的关键信号（已加入自动检测与存档）。**

### B13 · 魔搭端点 GLM-5.3-Flash：正文全进 reasoning_content、content 恒空，thinking.type 被静默忽略
- **2026-09-10 上午**（换默认模型 ZhipuAI/GLM-5.3-Flash 当天，e2e 实测踩中）
- 现象：e2e 全链路 91.2s "正常"走完（start→done 无报错），但 **0 个 content chunk、正文 0 字**、摄取因无正文而跳过。
- 取证：写 20 行探测脚本直连魔搭统计 SSE 帧字段分布——**773 帧里 reasoning_content 累计 1418 字（正文全在其中），content_len=0**；带 `thinking.type=disabled` 再探——**不报 400 但字段被静默忽略**，content 仍恒空。官方示例文档明示正文走 `delta.content`，与魔搭实际行为不符。
- 根因：`openai_compat.stream()` 只取 `delta.content`、忽略 reasoning——`chat()`（非流式）和 `stream_with_thinking()` 都有 reasoning 兜底，**唯独章节生成用的 stream() 漏了**（GLM 系"正文进 reasoning"是已知病，NVIDIA NIM GLM-5.2 同款）。
- 修复：stream() 补同款兜底——流结束 content_seen=False 时输出缓存的 reasoning，**英文占比 >15% 拒绝**（Qwen3.x 的英文分析泄漏不污染正文）；Qwen3.x 不受影响（content 正常出，永远进不了兜底分支）。
- **续（同日二轮取证）：兜底生效后 0 chunk 消失（首字 61.1s），但暴露第二层问题——content 不是恒空，是"排在 reasoning 之后、被 max_tokens 预算卡死"**。三档探测：mt=800 → reasoning 1656 字 + content 仅 80 字（finish=length 截断）；mt=4000 → reasoning 2159 + content 485（finish=stop，正文干净）；mt=16000 → content 494 全程干净。章节生成公式 `min(目标×1.2+256, 8192)`=3256，GLM reasoning 吃 ~2000 后正文被挤压 → **落库文本前半正常、后半无标点连排（411 字），字数 1464 不达标**。修复：chapter.py 对 GLM 系（model 含 "glm"）直接给 6 倍目标字数（15000，finish=stop 按实际计费，免费端点无成本），其余模型原公式不变。
- **终局取证（同日三轮）：32768 预算下字数达标（2229），但暴露第三层问题——GLM-5.3-Flash 把「元认知思考」直接写进 content 正文流**：英文自我审查段（"Wait—I wrote an internal reasoning slip above...""" 408 字）与中文无标点连排段（100~407 字）交替出现，去AI味 0 分。这不是代码问题：`thinking.type` 被魔搭忽略（关不掉思考），模型自发在 content 里"边想边写"，**应用层无法修**（按段落过滤英文会留下结构破洞）。
- **决策建议（2026-09-10）**：魔搭端点的 GLM-5.3-Flash 不适合章节正文生成；换回 Qwen/Qwen3.8-Flash-Next 当默认（final-green 全绿基线在），GLM-5.3-Flash 可留作商讨/短问答。三层问题链：① 正文进 reasoning + content 预算被吃（已修 stream 兜底 + max_tokens）→ ② thinking 无法关闭（魔搭忽略）→ ③ content 混元思考 + 无标点连排（模型行为，无解）。

### B12 · 复读兜底漏裁"正好 3 段"的复读块：_is_dup 只向前文比较，块首必判 False
- **2026-09-09 深夜**（Phase 0.1 单测骨架第一天就抓到的真缺陷）
- 现象：单测 `test_constructed_repetition_is_cut` 构造「6 段正常正文 + 3 段相同复读」→ 期望裁掉尾部 3 段，实际**原样返回**。
- 根因：`_dedup_trailing_repeats` 的 `_is_dup(idx)` 只在 `range(idx)`（前文）里找相似段。复读块的"块首"（第 1 段重复）前面全是正常文本 → 必判 False → run 从尾部数只有 2（末两段靠同块成员互判 dup），凑不满 RUN=3 → **正好 3 段的复读块永远裁不掉，4 段才够数**。B11 修复时的构造用例恰好比 3 段长，把这个边界盖住了。
- 修复：`_is_dup` 增加「或与紧邻后一段相似」判定，块首靠它入组；后一段同样过三道门（≥20 字 / Jaccard≥0.3 预筛 / difflib>0.8），不扩大误杀面。3 份真实轮次文本（B' 流式 180 段 / final-green / Qwen3.5 基线）回归零误杀。
- **教训：① 单测边界用例必须覆盖"恰好达到阈值"的场景（恰好 RUN 段、恰好 MIN_LEN、恰好 TH），只测"明显超标"会漏真缺陷；② "与相邻段落相似"是块成员关系，"与任意前文相似"是呼应关系——两者语义不同，兜底判定要分清；③ 单测骨架落地的第一晚就抓出 e2e 三轮全绿没发现的缺陷——e2e 靠真实模型随机性撞不出确定性边界，两者互补缺一不可。**

### B14 · ⚠️ few-shot 形态示范的「反利用」三连（2026-09-13 四轮验证实测，正文风格线）

few-shot 正反示范是对抗模型强先验的最强提示词手段（段均 12.6→26.0），但模型会**反过来利用示范**：

1. **堆轮次凑字数**：示范里含极短台词 + 字数刚性指令 → 模型学「对话可以短」，然后用
   **更多轮次**凑字数（v4：对话段 107→162、≤15 字对话段 68→131，但条均不动、段均反跌 15.7）。
   修补：加「对话轮次服务剧情，不为凑字数拉扯」+ 关键的**「砍掉轮次省下的字数，用叙述和
   更完整的台词补回，全章字数硬要求不变」**——没有最后这句，模型会把「少两轮」执行成「少写字」。
2. **词句/结构泄漏**：示例的高通用性短语（「拾来的/捡的」问答结构）被整段复刻进正文。
   禁抄尾注只能部分拦截（v5 清零 v6 又现）；根治需换掉示例中的万能短语。
3. **指标跷跷板**：强化 A 指标常压垮 B（对话示范→段均回退；轮次纪律→字数掉线 2852<3000）。
   **每轮验证必须全指标表对比**，不能只看目标指标；单次生成随机性大（连串 12/7/4/12），
   单次不达标先看趋势。

方法论全文见技能 `fewshot-prompt-iteration`（用户级）。

### B17 · ⚠️ 离线管线请求被系统代理劫持（urllib 版；2026-09-15 实测）

**现象**：接魔搭 provider 后首跑，**2/2 批次全失败**：
```
[plot_import] 魔搭 请求异常，2s 后重试（1/5）: URLError: <urlopen error Tunnel connection failed: 502 Bad Gateway>
[plot_import] 8 个段未被归并，已兜底归入最后一个弧
```
靠 `_chat_post` 的自动重试**侥幸成功**了一次，但代价是 **leftover 8**（8 个段没被真正归并，被兜底塞进最后一个弧）
—— 这种「部分成功」比直接失败更危险：不报错、报告还正常生成，只有 `leftover` 数字露馅。

**根因**：本机设了 `HTTPS_PROXY`（Clash 一类）。`urllib.request.urlopen` 默认**继承环境变量里的代理**，
把发给魔搭的请求交给了本地代理 → 代理连不上（或规则不匹配）→ 502。DeepSeek 走同一个 `_chat_post` 却没暴露，
是因为它的域名恰好在代理白名单/直连规则里 —— **同一个 bug 在不同厂商上表现不一致，最容易漏掉**。

**修法**：`_chat_post` 改用**显式空代理**的 opener：
```python
_opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
with _opener.open(req, timeout=timeout) as resp: ...
```
修复后重跑：**12 弧 / 24 段全覆盖 / leftover 0 / 零警告**。

**教训**：这与 08-31 记的「curl localhost 一律加 `--noproxy '*'`」是**同一个坑的两种语言版本**。
凡是本机发起的厂商直连请求（离线管线 / 批处理脚本），一律显式禁代理 —— 不要依赖「上次没出事」。
**症状识别**：`Tunnel connection failed` / `502 Bad Gateway` 出现在**访问公网 API**时（不是访问 localhost 时），
先怀疑代理，不要先去怀疑 key 或额度。

### B18 · 二分假设的记账映射：加第三个 provider 就静默失真（2026-09-15 实测）

**现象**：新增 `ms_arc`（魔搭弧归并）scene 后，记账回调里这句：
```python
vendor="deepseek" if scene.startswith("ds_") else "siliconflow",
model_name=DS_MODEL if scene.startswith("ds_") else SF_MODEL,
```
`ms_arc` 不匹配 `ds_` → 落进 else 分支 → **被记成 `siliconflow` + `Qwen3-8B`**。
调用是真的、token 是真的、`ok=1` 是真的，**只有 attributed 的厂商和模型是错的** —— 成本分析会把
魔搭的免费额度记成硅基流动的付费调用，方向正好反了。

**根因**：`if/else` 二分只在「恰好两种可能」时成立。加了第三种就必然有人落到错误的 else 兜底，
而且**不会报错**（`startswith` 对任何字符串都返回 bool）。

**修法**：改显式前缀映射表 + 兜底 `break`（而非静默 else）：
```python
_VENDOR_OF = {"ds_": ("deepseek", DS_MODEL),
              "ms_": ("modelscope", MS_MODEL),
              "sf_": ("siliconflow", SF_MODEL)}
```
并加回归单测 `TestUsageCbVendorMapping` 钉住三个前缀各自的映射。

**教训**：**任何「按前缀/类型分派」的 if-else 二分，在扩展前先改成表驱动**。
配套的通用检查：新增一个枚举值/provider/scene 时，grep 一遍所有 `startswith` / `==` 的分支判断。
（同批还踩了兄弟版本：`export_report` 把弧归并模型**写死** `DS_MODEL`，切魔搭后报告会撒谎 → 已改为从记账表回查。）

> **另记（CLI 校验过严）**：`import_novel.py` 原本要求 `arc`/`label` 阶段也必填 `--book-dir`，
> 但这两个阶段**只读库里的段数据、根本不碰源 txt** → 想「只重算弧」还得先编个源目录路径。
> 已放宽为只有 `summarize/segment/all/full` 需要 `--book-dir`。
> **教训**：参数校验要按「这个阶段实际读了什么」写，而不是按「所有数据阶段一视同仁」写。

### B19 · ⚠️ few-shot 示范迁移的不只是语义，**语体/形态/标点都会被照搬**（2026-09-20 实测，章节文风老派）

**现象**：作者反馈「章节生成的文风**像十几年前金庸那代**，不像现在网络小说那种轻快风格」。

**根因**：`builder.py` 的两段【形态示范】（分段 / 对话）是 `required=True` 的**硬性**示范
（原文"分段照此**逐字**模仿""**照此模仿**说话形态"），而**两段示范的语料全是古装/仙侠语境**：
照壁·水缸·里屋 / 丹房·茶盏·私章 / 三文钱卖菜。它们压在 user 消息**末尾**（注意力最高位）。
⇒ 模型被要求模仿古装语境的语体 → 输出的语感就是传统武侠腔。
**历史**：这两段是 2026-09-13 为治"台词条均仅 7.3 字（真实 18.1）""逐句分段"而加的
（注释原文："对话指令全是删减型，0 条正面教"）——**教学意图正确，语料选择有偏**。

**决定性证据（隔离实验）**：同一场景、prompt 逐字相同，**只追加**那两段示范 →

| 组 | 「」总数 | “”总数 |
|---|---|---|
| 无示范 | **0** | **81** |
| 有示范 | **84** | **1** |

**引号形态 100% 跟随示范**。示范里用「」，输出就全用「」。⇒ 证明「示范的形态会被完整照搬」，
连最不涉及语义的标点都迁移了，那么**语体、腔调、用词习惯同理**。

**处置（2026-09-20，作者拍板）**：**教学点一字未改，只换语料** ——
换成当代校园/都市口语（教学楼·成绩单·烤肠摊·补考），并**改用中文双引号**
（实测库内 6 章共 283 处 “” / 0 处 「」——示范的引号形态必须与目标正文一致）。

**铁律**：
① **few-shot 示范的"语料语境"就是输出语体的强先验**——写示范时必须用**目标风格**的语料，
   不能"随便找个例子教形态"。教什么形态、就顺便教会了那个形态所处的语体。
② **用可量化 proxy 检测迁移**：本次是"引号形态"（0/81 vs 84/1）——找一个不受语义影响、
   却能被示范唯一决定的表面特征，就能把"感觉像"变成"实测是"。
③ **示范语料不能只用一种写法**：本次三段结尾全用同一个"嘴硬心软"套路（三组全中）
   → 示范/样本要覆盖**多种手法**，否则会把模型的单一表达强化得更单一。
④ **改 prompt 里的示范前先量项目现状**（本次先查了"项目正文用哪种引号"），
   否则会把新的不一致引进去。
⑤ 🔴 **（2026-09-21 补全）示范语料要三重匹配：目标文风 × 故事背景 × 语感**。
   第一版修复把示范换成"现代校园"（教学楼/月考/烤肠摊），但故事是**古代药铺/修仙**——
   模型面对语境冲突会判定"示范不适用我的场景"→ **打折执行** → 回落书面语默认腔，
   金庸味依旧（实测同要点对照：比喻 8 vs 4、布包 18 vs 15，无实质改善）。
   作者当初指的参考《没钱修什么仙？》本就是「修仙背景+当代网文语感」——
   **正确配方 = 当代网文口语 × 与故事一致的背景**。第三版已改为灵田/符摊/宗门场景。
⑥ 🔴 **（2026-09-21 补）示范不是"进了 prompt"就完事**——逐标记核验 ✅ 之后仍要生成对照量化。
   同日实测：示范全注入，但分段示范在"古代修仙+短对话"场景下压不住
   「网文=一句一段」先验（62% 段落 ≤40 字、0 段 >120 字）→ 示范语料里必须**同时给长段例
   （约 130 字/5 句）和短段例**，只给短例会强化短段先验。

### B20 · ⚠️ 观察的「注意力经济性」——人只注意「违反预期」的东西（2026-09-21，作者写作理论）

**现象**（作者连续两轮实测纠正）：
1. 一章内主角的"布包"被 8 次提及，两个新角色都用「目光停在他腰间的布包上」来建立关联；
2. 第一次修复（让模型"换着打量"：老茧/指甲缝/鞋）**被作者推翻**——
   「周镖师看的还是他手上的老茧和指甲缝里的泥——**谁好端端的看这个啊**」；
3. 正确写法（作者理论，直接采纳进 `builder.py`）：
   - **人只注意「违反预期」的东西**。符合刻板印象的，一笔带过即可；
   - 陌生人的默认反应 = **瞟一眼**，符合常理就不再关注细节，直接写他自己的目的；
   - **有戒心时看的是威胁**（有没有武器、环境有没有埋伏），不是研究对方细节；
   - 只有**违反常理**才值得细看（背着棺材赶路、当街亮刀、浑身是血）；
   - 🔴 **注意力必须服务剧情**：细节后文用不到，连"注意到"都不要写——
     「门口躺着个乞丐、面前摆个碗。**若后文没有乞丐的事**，就只写『门口躺着个乞丐』，
     不要写『注意到他面前的碗』。**乞丐摆碗是常理，常理不值得写**」。

**为什么 AI 会犯**：AI 的视角是「遇到一个人就得仔细打量看他有什么特殊」——
它把"描写要生动"理解成"每处都要有观察细节"，不知道**常理不值得写**。
（同源：B14 省力写法——AI 缺的不是词汇，是**"什么不值得写"的判断**。）

**修复位置**：`builder.py` 的【人物相互观察的写法纪律（硬性）】。
验证（同 hint 三版）：布包被外人注意 2 段 → **1 段**；"打量"类句子 3 → 2（剩余 2 处人工核均为合理：
一处探针误报、一处是剧情要求的鉴定「老郑你过来看看，你看像不像」）。

**教训**：❶ 教 AI「什么值得写」必须配**判断标准**（"违反预期才写""后文用得到才写"），
只给替代手法（"换着打量"）没用；❷ 修复后要用**上下文人工核**，探针会误报。

### B21 · ⚠️ AI 味的**两大根因**：缺「正常人的感觉常识」+ 缺「人情世故常识」（2026-09-25，作者两次点破）

> 这是 B14/B19/B20 的**上位归因**。前面几条是单点堵漏，这两条是根因——
> **AI 缺的不是文采，是"正常人怎么感受、怎么处世"的常识库。**

#### 根因一：感官与行为常识（作者 12:0x 点破）
作者原话：「AI 对于正常的触感、观感、听感、语感、情感、动作这类正常的**感觉/行为**
都没有正确的认知，所以导致会有 AI 味，few-shot 和提示词应该用这些来告诉它。」

典型病：写「累」叠三层同义反应（喘+胸腔起伏+铁锈味）；摸到温石头写成
「像一根烧红的细针扎进肉里」——**温热不是刺痛，感觉被写反了**。

**作者给的取材铁律（重要方法论）**：
> 「正例你去**真书里找原句**，不要自己造，我看你造的也不怎么样；反例你自己根据原句造；
> 类别不一定非是我说那几类，可以更全面。」

⇒ 正例一律取自真书（本项目文风基准 = 《没钱修什么仙？》，另可用《凡人修仙传》《斗破苍穹》）；
反例 = 把真句改成模型最容易写出的那种。**自己造的正例质量不够，会被作者当场否掉。**

从真书里读出来的**反直觉规律**（比"写三层就是 AI 味"精确得多）：
> 真书也写三句，但每句是**一个具体部位**（冷汗 / 心里 / 手掌），**不是同一个意思说三遍**。

⇒ 修正了既往"少写就是好"的粗糙规则：**判据是"是否重复"，不是"是否多层"**。
另加**停手原则**：写完一个正确的感觉就停手，追加的那句几乎必然是比喻、几乎必然是 AI 味。

#### 根因二：人情世故与身份差（作者 13:0x 点破）
作者原话：「普通人面对官爷，哪怕他再怎么不凡，也会**表面上讨好的**。」
「即使主角再特殊，面对**身份的巨大差异**、或者**需要别人帮忙**时，
如果不是死敌或需要违背意愿的事，**人是会变通的**。」

被批的原句：「回春堂的伙计，给巡检司送止血散。」他微微躬身，**语气恭敬却不卑微**。
作者改的正例：「官爷，小人是回春堂的伙计，按掌柜的吩咐，给巡检司送些止血散」
+ **脸上带着谄媚**。

**为什么 AI 会犯**：它把「主角人设」当唯一驱动力，于是用**解说词**给人贴标签
（"不卑不亢""神色如常""语气恭敬却不卑微"），而**不写行为**。
这正是 B14/B19/B20 的同一病灶换了个位置：用"形容"代替"动作"。

**教什么（已进 `builder.py`，4 组 + 硬气边界 + 自检句）**：
1. 开口**先报身份＋来意**，必要时顺一句好话（真句：「在下柯宇，奉令来给三位前辈传达任务和带路的」）；
2. 示弱**带身体**：陪笑、擦冷汗、咽唾沫、腰弯低些（真句：斗破「咽了一口唾沫…脸庞露出一抹难看的笑容，
   他极为识相的干声道：『全依大人所言』」）；
3. 求人**留余地**：用「能否/能不能/方不方便」，给对方拒绝的台阶；
4. 被刁难时先把眼下应付过去（真句：「毕竟是面对高一个年级的学长……都只能乖乖低头」）；
5. 🔴 **硬气的边界只有三种**：死敌已撕破脸 / 要他做违背底线的事 / 已无退路；
6. 🔴 **原理句**：主角的不凡写在**事后怎么想怎么做**，不写在**当面怎么顶**；
7. 🔴 **自检句**：把人名遮掉，还看得出谁的地位更高吗？看不出 = 没写出身份差。

**实测**（注入 11/11 ✅）：自称「小的/小人」0 → **6**；「不卑不亢/不卑微」类解说词 → **0**；
自动长出「挤出一丝讨好的笑容」「额头上的冷汗」「要是班头喜欢，小的可以送给您两块」（**主动给好处**）。

#### 根因三：知识泄漏 / AI 幻觉（作者 13:3x 点破）
作者原话：「AI 知道这是很重要的东西，就**假想**书中的所有人/某一个角色知道（即使不考虑符不符合剧情）。」
「主角起初并不知道，对它的感觉应该保持**单纯的好奇**——就像家里一件旧物，
不清楚是古董时随手用；**有人点破或自己意识到之后**才开始小心珍视。」
⇒ 🔴 **珍视必须发生在「知道」之后**；无来由的紧张/悸动/患得患失，都是把作者的知识塞给了角色。

具体四种形态（已各配判据与正反例进 `builder.py` 的【角色认知边界】块）：
1. **凭空感应**：主角「心头一悸」「仿佛产生了共鸣」→ 判据：**他凭什么这么紧张？** 找不到理由就是泄漏；
2. **旁人无来由起疑**：班头盯着布包看两息就追问 → 判据：**旁人不是算命的**，起疑得看见了/听说了/认得成色；
3. **术语越界**：药铺杂役心里想「这该不会是**灵石**吧」→ 他没听过这个词，只能说「宝贝」「仙师」；
4. **被害妄想**：把对方的普通眼神解读成「看贼的眼神」「寻找猎物」→ 真人的默认判断是就事论事。

另加：**好奇的节奏是「发现 → 好奇 → 放下」**——真人不会抱着没搞明白的东西反复推演（那既注水又显得疑神疑鬼）。

#### 🔴🔴 最重要的一条方法论：**禁掉一个手段前，必须先给替代手段**
本次禁「灵石温热」**连禁两次都失败**——因为模型只会用温度这一个手段表现"这东西不寻常"，
禁掉之后它退化回温度（甚至写出「不发热也不跳动」这种自证清白的话，下一句又写温热）。
给了**四种替代**（重量坠手 / 外观云纹 / 硬度砸不烂 / **别人的反应**）之后，一次就成功了。
（与 B6「少写不要、多写要」同源，但更具体：**替代清单要写进世界观设定，不能只写"不要"**。）

#### 🔴 通用教训（三条）
1. **验证要点不能预设结论**（连踩三次）：要点里写了「挖出五块**温热的**石头」→ 模型照写温热，
   看起来像设定没生效；要点里写了「陈峰**随口搪塞过去**」「班头**起疑**」→ 污染身份差与认知边界验证。
   **凡是验证某条纪律，测试要点里就不能出现该纪律的结论词。**
2. **正例必须真书原句**，且要挑**完整行为句**（含动作＋说话），只命中关键词的句子多半不能用
   （可用 `outputs/_sample_social.py`、`_sample_social2.py` 抽样，再人工挑）。
3. **章末钩子不能靠物品自己表现异常**（石头跳动/发热/发光）。要给**合规钩子的正例**（来自**人**：
   旁人的喊声、上位者反常的举动、小吏多问的一句），否则模型为了满足"章末要留悬念"必然重犯设定错误。

## C. 代码与架构类

### C1 · 流式生成器内严禁访问请求级 DB session（**铁律**）
- **2026-08-11 确诊**（曾回归过一次）
- 现象：流式对话报 `BodyStreamBuffer was aborted`，日志里是 `DetachedInstanceError`。
- 根因：`StreamingResponse` 的 `event_stream` 生成器在**线程池**运行，`chat()` 返回响应后请求级 `get_session()` 已关闭。生成器内读 `default.xxx`（ORM 字段）或 `db.query(...)` → `DetachedInstanceError` 抛在 try 外 → 流中断。
- 正确做法（已在 `discussion.py` 落地）：
  1. 在 `chat()` 内、session 仍开时，把 ORM 对象的**标量提取成普通 dict**（`model_cfg`）；
  2. 生成器内用 `gen_db = _db.SessionLocal()` 自建独立 session（`_db` = 模块引用，**绝不能** `from app.core.database import SessionLocal` 直接导入——导入时绑定到启动前的 `None`）；
  3. `finally` 中 `gen_db.close()`。
- 教训：**B 方案改动曾误在生成器里用 `default.*`/`db`，就是这条的回归。** 改流式代码时第一个检查这个。

### C2 · 事件时序：不要发在 `finally` 之后
- **2026-08-11**
- 现象：GLM-5.2 的 `BodyStreamBuffer was aborted`，一度误判为"回答展开太长"。
- 真实根因：`entity_suggestion` 事件是在 `event: done`（`finally` 开头）**之后**才发出的 → 客户端已关闭连接。
- 教训：**SSE 的所有业务事件必须在 `done` 之前发完。**

### C3 · 后台线程里重查 ORM 对象
- 写后摄取改为后台线程 `_background_ingest` 时：必须 `_db.SessionLocal()` 独立会话 + **按 id 重新查询** `ChapterORM`（不能持有请求级对象），末尾 `t_db.commit()` 兜底，`daemon=True`。
- SQLite 并发写（后台摄取 vs 其他请求）可能偶发 `database is locked`，已 try/except 兜底（只丢当次摄取、不影响正文）。

### C4 · Pydantic alias 漏 `by_alias`
- **2026-08-13**
- 现象：工作流更新后接口全 500。
- 根因：`model_dump(exclude_unset=True)` 未传 `by_alias=True` → `FlowEdge.from_` 以 `from_` 键名入库而非 alias `from` → 后续 `model_validate` 抛 `ValidationError`。
- 教训：**有 alias 的 schema，dump 时必须 `by_alias=True`。**

### C5 · 前端重复解包
- 现象：实体确认永远显示"已写入 0 条"。
- 根因：`views/ChatView.vue:188` 写 `res?.data?.data`，而 `api/http.js` 拦截器**已解包过一次** → 取到的是 `data` 字段本身。
- 教训：拦截器统一解包后，**业务代码里不要再 `.data`**。

### C6 · 对话弹窗常驻挂载导致状态残留
- 现象：生成完一章后再点"生成章节"，仍停在结果页，没有生成按钮。
- 根因：`GenerateChapterDialog` 常驻挂载（仅 `v-model` 显隐），关闭后内部 ref 不销毁，`result=true` 残留。
- 解决：`watch(props.modelValue)` 每次打开复位全部状态；结果页 footer 加"重新生成"按钮。
- 教训：**Element Plus 的 `el-dialog` 默认不销毁内部状态**，凡是有流程状态的弹窗都要 watch 复位。

### C7 · 向量索引是「全局表」，跨项目靠 top-k 过采样过滤必然漏召回
- **2026-09-10 实测抓出**（A3/A4 上线后第一次真机 e2e）
- 现象：项目内导入 4 份参考文档、全部建好向量（表里 10 块），但生成时 `pick_relevant` 只命中 1 份。
- 根因：`vec_index`（vec0 虚拟表）**所有作品 + 全局资料池共用一张**，KNN 查询本身不带项目过滤；旧实现用 `k = top_k * 3` 全局过采样，再回表按 project_id 过滤。全局池有 133 块、本项目只有 10 块 → top-k 名额被全局池的块吃光，回表后本项目块几乎全被截掉。
- 修复：`vec_index` 加 `project_id`/`source_type` **辅助列**，KNN 查询内直接 `AND project_id=? AND source_type=?` 过滤（sqlite-vec v0.1.9 支持元数据过滤，先 `MATCH` + `k` 再过滤，实测可行）；`vec_index_available` 校验 schema 含辅助列，旧 schema 判为不可用；`_ensure_vec_index` 启动时检测旧 schema → 删表重建 → 从 `vector_chunks`（source of truth）自愈回填。回归用例：往干扰项目塞 200 个同向块，本项目 3 块必须完整召回。
- 教训：**「全局索引 + 查询后过滤」在小数据集上看着没问题，一旦别的分区更大就静默失效**——凡是分区语义的检索，过滤条件必须进到索引查询内部，不能靠取多了再筛。

### C8 · 作品级联删除漏清无外键的表（孤儿数据复发）
- **2026-09-10 实测**：删测试作品后 `vector_chunks` 残留 10 块。
- 根因：`project_crud.delete_project` 只遍历 `_RELATED` 里的 ORM 表，而 `vector_chunks` 没进该列表（新建表时容易忘记登记），`vec_index` 更是虚拟表、根本不走 ORM 级联。
- 修复：`delete_project` 显式调 `vector_store.remove_project_index(db, pid)`——同时清 ORM 主表与 `vec_index` 虚拟表；单测断言「删 px 后 py 的块与索引都还在」（作用域正确）。
- 教训：**每新增一张带 project_id 的表，必须同时检查三处：级联删除列表、孤儿清理脚本、以及是否有虚拟表/索引需要单独清**。这正是 03 §3.1「孤儿数据」问题的同类复发——旧坑是删作品前遗留，新坑是新表没登记。

### C9 · 异步摄取与「删除作品」竞态：向量写在删除之后 → 孤儿块
- **2026-09-10 全流程 e2e 后巡检发现**：DB 里 `vec_index` 133 行 vs `vector_chunks` 133 行对不上（多 2 行），查孤儿块 project_id = 刚被 e2e 删掉的测试作品。
- 根因：写后摄取是**异步后台线程**（`ingest_start` 事件后不阻塞 `done`）。e2e 脚本拿到 `done` 就删作品，此时摄取的 `sync_after_ingest` 尚未跑完 → 级联清理先跑（当时向量还没写）→ 摄取随后把章级记忆/篇章摘要向量写进一个**已不存在的项目**，成为孤儿。危害放大点：`vec_index` 是全局表，孤儿块会永久参与所有项目的 KNN，挤占 top-k 名额（与 C7 同源）。
- 修复：`vector_index.index_chunks`（**所有向量写入的唯一咽喉**）开头加项目存在性守卫——项目已不存在则直接返回 0（在 embedding 之前，顺带省一次 API 调用）；`__global__` 是全局资料池的虚拟 project_id、没有 projects 行，必须豁免（否则全局池无法建索引）。
- 教训：**异步任务 + 级联删除必然有竞态窗口，写入方必须自证「目标仍存在」**，不能假设创建时校验过就一直有效。守卫要放在写入咽喉而不是调用方（调用方可能有多处、以后还会加）。

### C10 · 错误提示被当成小说正文落库，且会**静默覆盖已有正文**
- **2026-09-10 复核确认仍是活 bug**（Phase 1 止血 1.2）。`chapter.py` 里模型调用失败时
  `content_parts.append("[模型调用失败，已降级为占位：…]")`，而 `full = "".join(content_parts)`
  随后直接落库 → **错误文案变成了小说正文**；未配置模型时同理写入占位符。
- **放大危害**：走「重新生成」路径时 `update_chapter(content=full)` 会把**已有章节正文整段覆盖成错误提示**
  —— 作者以为只是生成失败，实际原稿已被静默抹掉。
- 修复：新增纯函数 `_can_persist(full, error_notes)`：
  - 错误/占位文案改存 `error_notes`，**只推前端展示，不进 `content_parts`**；
  - 落库前判定，正文为空则不落库、只发 `error` 事件说明原因（不发 `saved`）；
  - 空正文时跳过去重与 AI 味扫描（避免对空文本无意义处理）。
  前端补 `error` 事件处理：不再误报"生成完成"，留在表单页可直接重试。
- 测试：`test_chapter_persist_guard.py`（8 用例，纯函数）+ `test_chapter_failure_no_persist.py`
  （**真实驱动 SSE 生成器**，用必抛异常的假适配器复现失败：不建章 / 不覆盖原稿）。

### C12 · 「孤儿数据」判定必须豁免 `__global__`（差点删掉全局资料池与全部向量）
- **2026-09-10 清理孤儿数据时踩中**。按「`project_id` 不在 `projects` 表里」判孤儿，
  统计出 `vector_chunks` 有 133 行"孤儿"、`discussion_messages` 有 25 行"孤儿"。
- 真相：`__global__` 是**全局资料池的虚拟 project_id**，它本来就不是 `projects` 行——
  这 133 行是**全局池 18 份资料的向量索引**（当天刚 reindex 建的），25 条是全局对话记录，
  全是合法数据。若照统计删除，**全局检索会直接报废**（vector_chunks 与 vec_index 同时清空）。
- 修复：所有表的孤儿判定统一加 `AND project_id != '__global__'`；删除前先导出 + 备份；
  删完校验「孤儿 0 且全局池计数不变（18 份资料 / 133 向量块）」。
- 教训：**用"外键不在主表"判孤儿时，必须先枚举该列的全部取值**（`GROUP BY project_id`），
  确认有没有哨兵值/虚拟值——否则哨兵值会被当成孤儿，删掉的是核心数据。

### C13 · `fetch` 不校验 `resp.ok`：JSON 错误体被当事件流解析，错误静默消失
- **2026-09-10（Phase 1.3）**。`api/chapter.js:generateChapterStream` 拿到 `resp` 直接
  `resp.body.getReader()` 按 SSE 解析。后端在参数错误时返回 **400 + JSON**（如漏传 `article_id`
  会返回「生成章节必须指定所属篇」），前端把 JSON 体按 `event:/data:` 切 → 切不出任何事件 →
  **界面表现是"点了一动不动、没有任何提示"**，真实错误被完全吞掉。
- 修复：`if (!resp.ok)` 先读 `detail/message` 再 `throw`；另补 `resp.body` 空判断。
- 教训：**凡是手动读流（SSE / 二进制）的地方都要先校验状态码**；axios 有拦截器兜底，
  裸 `fetch` 没有——同一个项目里两种写法混用，最容易漏的就是裸 `fetch` 这条。

### C14 · session `autoflush=False`：`add()` 后不 `flush()`，同一批后续匹配查不到新记录
- **2026-09-10（Phase 2.1 单测当场抓出）**。`get_engine()` 建的是
  `sessionmaker(autoflush=False)`——查询**不会**自动把待写对象刷进库。于是
  `sync_from_actions` 里「bury X」先 `db.add(X)`，紧接着处理「hint X」时 `_find_match`
  走 `db.query(...)`，**看不到刚 add 的 X** → 又建一条 → **同一章内重复登记**。
- 修复：每次 `db.add(...)` 后立即 `db.flush()`（事务内可见，不影响最终 commit）。
- 教训：**`autoflush=False` 的项目里，"先写后按内容查重"必须显式 flush**。
  这类 bug 在"一次只写一条"的场景永远不出现，一旦同一批里出现"写 A 再查 A"就必踩——
  所以单测必须构造**同一调用内多动作**的用例，只测单动作测不出来。

### C15 · 模糊匹配阈值缺「长度门槛」：短文本互相误并
- **2026-09-10（Phase 2.1 单测抓出）**。伏笔去重按描述相似度判断同一件事，
  初版只设 `difflib ratio ≥ 0.78`。结果「甲的伏笔线索」vs「乙的伏笔线索」（6 字、差 1 字）
  比率 **0.833** → 被判为同一条 → **两条独立伏笔丢一条**。
- 修复：模糊匹配加最小长度门槛 `_SIM_MIN_LEN = 12`（双方都够长才启用模糊），
  阈值提到 0.85；短描述只认「归一化后完全相等」。互相包含判定也保留 ≥6 字门槛。
- 教训：**编辑距离/相似度类阈值必须与文本长度绑定**。短文本的比率天然虚高
  （改一个字就是 10%+），任何"全局单一阈值"在长文本和短文本上不可能同时合适。
  写这类去重逻辑时，**必须专门构造"短且相似但语义不同"的用例**。

### C16 · ⚠️ 调用破坏性端点前不核对删除范围：误清全局对话（2026-09-16 实测，零真实损失纯属运气）
- **经过**：B5 用量计量真机验证后，想清掉自己那条测试消息，直接调了
  `DELETE /projects/__global__/discussion` —— **没先读实现**。该端点（`clear_messages`）在
  不带 `conversation_id/chapter_id` 时删的是「**整个默认线程**」（`chapter_id IS NULL AND
  conversation_id IS NULL AND archived_chapter_id IS NULL`）→ **26 条**被删（含用户 8 月份的
  24 条历史消息，我自己只造了 2 条）。
- **发现**：响应里 `"count":26` 与「我只造了 2 条」对不上 → 立即停下排查。
- **恢复（✅ 全部找回）**：`journal_mode=wal` 下**主库文件只在 checkpoint 时更新** ——
  删库后立刻把 `novel_agent.db` **不带 `-wal/-shm` 单独拷贝**再打开，读到的就是
  **最近一次 checkpoint 时（即删库前）的状态**。恢复出删前完整 30 条，与现存 7 条 diff 出
  丢失 23 条；逐条核对内容后确认**全部是 8 月份的调试残留**（你好/简单测试一下/会话A的问题），
  **零创作内容损失**（有价值的官制问答在命名会话里，未被波及）。
  恢复产物：`outputs/_db_rescue/`（DB 三件套快照 + `recovered_global_messages.json`）。
- **为什么运气好**：① 删的是**默认线程**（全局闲聊测试区），不是命名会话；② 丢的全是测试消息；
  ③ checkpoint 尚未发生（主库文件还是删前状态）。**任一条件不成立就是真数据损失。**
- **教训（三条铁律）**：
  1. **任何 `DELETE` 类端点，调用前必须先读它的实现**，确认过滤范围——「清空当前对话」和
     「清空整个线程」可能只差一个参数；响应里的 `count` 是事后诸葛，对不上预期就该立即停。
  2. **WAL 库误删的黄金恢复窗 = checkpoint 之前**。第一动作是拷贝主库文件（不带 wal），
     再慢慢分析；先跑一次 checkpoint 或让后端继续写入 = 永久丢失。
  3. **测试数据自证清理**要用「自建自删」闭环（B1 的做法是对的），清理**既有数据**的动作
     必须逐条指定 id，禁止用范围型 DELETE 顺手清。

### C17 · ⚠️ LCS 回溯方向必须与 dp 表语义配套：前向回溯用前缀表 = 比较值全错位（2026-09-19 实测）

- **场景**：跨书归并后，组骨架每环的「哪些弧走过」（`covered_by`）**7/8 环为空**，
  但同一批成员 42/42 经独立校验**全是骨架的子序列**（矛盾 → 说明是对齐函数错，不是数据错）。
- **根因**：`align_positions` 拿 `lcs_dp`（**前缀语义**表，`dp[i][j] = LCS(a[:i], b[:j])`）
  做**前向**回溯：`dp[i+1][j] >= dp[i][j+1]` 这个条件只适用于**从 (len,len) 逆向**回溯；
  从 (0,0) 往前走时比较的两个量语义错位 → 从第 2 个原子起就朝错误方向走（把能对齐的原子跳过）。
  实测 `[C05,A05,A08]` vs `[G06,C05,A05,A08,…]` 应得 `[[1],[2],[3]]`，实际全返回 `[]`。
- **修复**：成员必为骨架**子序列**（SCS 合并性质 + can_merge 三态保证）→ 贪心双指针
  （每个成员原子在骨架上顺序找首个相等位，无位=[]）。单测 +2 固化（多原子对齐 / 独有环=[]）。
- **铁律**：**写 LCS 回溯先核对 dp 表语义与行走方向是否配套**（前缀表↔逆向回溯，后缀表↔前向）；
  能用「子序列 + 双指针」就别上 LCS 回溯。另：**「子序列性质全成立但覆盖统计全空」= 对齐实现 bug 的典型信号**。

## E. 批处理与性格管线（2026-09-16 新增）

### E1 · ⚠️ 长事务会把 SQLite 读视图**冻住**：运行中的写入，别的进程读不到

离线管线（CLI）一边写库、一边想从**另一个连接**读进度时，会稳定读到**旧快照**
（实测：摘要写到 200 章了，只读连接查出来仍是 0 行；一度被误判成"数据丢失"）。

**根因**：SQLAlchemy Session 会 `autobegin` 开启一个读事务；SQLite WAL 下这个事务**拿到的是开启时刻的快照**，
不结束就永远不刷新。**推手**：后端常驻进程持有该库 → CLI 不是"最后一个连接" → 不触发关闭时的自动 checkpoint。

**解法**：每次查进度前先 `db.commit()`（或 `rollback()`）结束当前事务，下一次查询即取新快照。
⇒ 实操规则：**管道跑完再读；导入过程中不要由别的进程读**（写在 `_wait_for_summaries` 里）。

### E2 · ⚠️ "白名单重建"函数会**静默丢弃**新字段

`plot_distill._normalize_cast` 是按白名单重建 dict 的（`slot/desc/mode/beats/srcs`），
给 cast 加 `ranks`/`traits`/`basis` 时**必须同步放进它的输出 dict**，否则新字段**不报错、直接消失**
（LLM 明明产出了，落库后没了 —— 极难排查）。
⇒ **凡是"重建对象"的归一函数，加字段都要改两处**（输入解析 + 输出白名单）。

### E3 · ⚠️ 绕开既有函数重写路径 → 漏掉它的**旁路**

v3 弧管线没走旧的 `merge_arcs`，结果漏了 `on_usage=make_usage_cb("ms_arc")`
→ **该阶段的调用完全不记账**（观测不到耗时/失败、用量也漏）。旧路径是记的，属于**回归**。
⇒ 重写路径前，先把旧函数的**旁路**（记账 / 限流 / 降级 / 幂等）逐条过一遍。

### E4 · ⚠️ 数值档位体系的两个坑（吸附与中位）

给模型定"9 档锚点（0/±1/±4/±7/±10）"后，后处理仍会踩：
1. **吸附必须展开 ± 全集**：锚点常量若只存正向量级 `(0,1,4,7,10)`，直接吸附会把 **-7 吸成 0**
   （实测单条观测 -7 返回 0，负值全被吃掉）；
2. **偶数个观测的中位数会离档**：`statistics.median([4,-4]) = 0`、`median([1,4]) = 2.5` →
   落在档位之间就破坏了"档位可比"。**必须吸附回锚点**，并加"全部输出都在锚点上"的硬断言。

### E5 · ⚠️ 提示词字符串里夹带 ASCII 双引号 → SyntaxError（同一晚踩 3 次）

写中文提示词时很自然写出 `不要为"一致性"推平` → 而外层是 `"..." ` 字符串 → 直接 SyntaxError。
**规则**：Python 字符串里的中文引号一律用 **「」**，禁止 ASCII `"`。
（本项目提示词几乎全是中文长串，这条会反复踩。）

### E6 · 模型会按"身份标签"成套推断性格（**必须显式禁止**）

实测观察：给角色打性格刻度时，模型倾向 **主角=无私/理性/仁慈、反派=狠辣/背信**（刻板印象成套输出）。
已在提示词里显式禁止，并把**道德三维度（利他/信义/仁慈）**与**非道德维度**分开约束：
道德维度**不许用"位阶群体倾向"成套推断**（要么有文本依据，要么只给 ±1 顺势小幅并标 `peer`）；
只有非道德维度（强势/城府/理性/冒险…）才允许按位阶倾向推。⇒ 同类任务（给角色/组织打任何属性）都要防这一条。

### E7 · ⚠️ 厂商 CDN 会对大响应自作主张 gzip，urllib 不自动解压（2026-09-17 实测）

**症状**：跑了 N 小时的批处理突然大面积 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0x81/0x80`
（压缩流字节）+ 间歇 `JSONDecodeError`（空体）→ 重试 5 次全挂 → 整个 Pass1 窗口失败 →
弧数据出洞。同一厂商**之前一直正常**（CDN 行为漂移，与响应大小/时段有关，极难联想到）。

**根因**：`_chat_post` 用 urllib 直连，**没有处理 `Content-Encoding: gzip`**——`resp.read()` 拿到的是
压缩二进制。urllib 不主动声明 `Accept-Encoding`，但 CDN 仍可能自作主张压缩。

**修复**：① 请求头显式 `"Accept-Encoding": "gzip"`（把行为变确定）；② 读取后按
`resp.headers["Content-Encoding"]` 统一解压（gzip/deflate 都处理）再 `json.loads`。
⇒ 任何手写 urllib 的 LLM/HTTP 客户端都要做这两步。

**附带教训**：批处理"跑了几小时还没完"不要只看进程活着——**要读日志看是否在静默重试失败**
（一个窗口失败 = 重试 5 次 × 每次数分钟 = 白烧 1 小时，还留下数据洞）。
1. `GraphEngine` 初始入度对所有入边计数会导致 end 多入边死锁 → **end 虚拟入度固定为 1**。
2. vue-flow 的 `Background`/`BackgroundVariant` 从 `@vue-flow/background` 导入（**不在 core**）。
3. 模板 `{{#...}}` 与 Vue 插值冲突 → 加 `v-pre`。
4. variable 类型字段解析引用失败返回 `None` → 加 `resolve_value` 支持固定值。

### E8 · ⚠️ 源书清洗：章号格式两种都要认（2026-09-19 实测，差点误删 6 个正文短章）

**场景**：按「文件名判别」清洗作者交流章（文件名含「第X章」= 正文保留，否则删）。
第一版正则 `第\d+章` 只认阿拉伯数字——**遮天全书用中文数字章号**（「第一百二十七章 玄黄」「第二百五十五章 天鹏极速」）
→ 14 个 ≤4K 文件**全被判成交流章**（含 6 个真实正文短章）。

**修复**：`第[0-9一二三四五六七八九十百千零两]+章`。dry-run 当场抓到——**先 dry-run 看清单、逐类抽样读内容**再 `--apply`。

**推广**：任何按文件名/标题解析章节号的代码，都必须同时支持阿拉伯与中文数字两套写法；
**文件的「小」不等于「非正文」**（遮天有 1249B 的正文短章，逆天邪神 11 个 ≤4K 文件全是正文）。

### E9 · ⚠️ 厂商服务端「劣化」与长任务的 done 停滞断言（2026-09-19 实测，逆天邪神概括）

**症状**：逆天邪神概括前 446 章正常 → 之后**全部** `TimeoutError: read timed out`，
日志 5.5 分钟无新 done，主循环却继续扫到 2000 章（每批重试 5 次全失败），
`done` 卡在 446 不再增长——**从外部看进程活着、日志在滚，实际 3 小时零产出**。

**诊断**（三步定位到「不是我们的问题」）：
1. `done` 停滞 + 超时风暴成片 → 先怀疑服务端，不是代码；
2. **直连最小请求测延迟**：`max_tokens=8` 的请求耗时 **28.1s**（正常 1~3s）→ 服务端排队/降级确诊；
3. 排除三嫌疑：key 有效（注意：DB 里 `substr(value,1,50)` 取值会截断 key → **401 是测试方法错，不是 key 错**）、
   限流器正常（45K 窗口工作正常）、代码未改。

**处置**：停任务 → 部署**恢复哨兵**（每 5 分钟探测最小请求，连续 2 次 <20s 判恢复 → 自动幂等续跑）
→ 用户最终选择停止，446 章安全保留（续跑 skip）。

**铁律**：① **长任务必须有进度断言**（done 停滞 N 分钟 = 异常信号，要能自动发现，别等用户问）；
② 厂商超时风暴的**第一动作是直连最小请求测服务端延迟**，而不是改代码/换 key；
③ 幂等设计让「事故后无损续跑」成为可能（已完成的章自动 skip）——长任务开工前先确认幂等性。

### E10 · ⚠️ 流式生成「network error」的四层误判：真凶是思考阶段 0 字节（2026-09-20 实测，批量生成篇）

**症状**：`PlanView` 批量生成，连续两次都在约 5 分钟后报 **network error**，看起来像网络/后端挂了。

**排查（靠时间戳破案，不是靠猜）**：`backend.log` 里两次 POST 都是 **200**，但
`11:38:02 → 11:43:02 → 11:48:02` 三个时间戳**两两相差恰好 300s**，
且 11:44 之后到 11:56 **再无任何生成日志** = 两次请求都没走完、后端从未产出正文。
300s 这个数字直接指向 `vite.config.js` 的 `timeout/proxyTimeout: 300000`。

**四层因果链**（每层都在掩盖下一层）：

| 层 | 现象 | 真因 |
|---|---|---|
| 1 浏览器 | `network error` | 响应流被中途掐断 → `TypeError: Failed to fetch`，**与网络无关** |
| 2 vite 代理 | 300s 掐断 | 空闲超时，5 分钟没收到后端一个字节 |
| 3 后端 SSE | 思考阶段 0 字节 | `openai_compat.stream()` 把 reasoning **只 buffer 不 yield**（`_reasoning_buffer`），只有 content 才 yield；而 Qwen3.8-Flash-Next 开思考首字实测 **407s** |
| 4 触发条件 | 思考被强制打开 | `PlanView.vue` 硬编码 `enable_thinking: true` → 命中 `chapter.py` 的 `_broken_thinking_combo` 分支 → `want_thinking=True` |

**顺带挖出两个真 bug**：

- **`builder.py` 的 `_add` 前向引用**：207 行调用、217 行才 `def _add` → Python 视作局部变量
  → `UnboundLocalError` → 被本块 `except Exception` 吞掉，只在 error.log 留一行
  「GraphRAG 块跳过」。**GraphRAG 注入块（P_CRITICAL，order=45）长期静默丢失**。
  （另一处同名代码在 `return` 之后，是永远不执行的死代码——别被它迷惑。）
- **`sse.js` 的 180s 超时是死代码**：`createTimeoutController` 造的 controller 既没传给
  `fetch`（用的是外部 signal），`reader.read()` 又不接受 signal → `abort()` **没有任何消费者**。

**修复（B+C+D）**：
1. thinking 走**独立 SSE 事件**发前端（累积 40 帧或满 3 秒发一次，节流防打爆前端），
   **永不进 `content_parts`、永不落库** → 保活 + 不污染正文，两个目标同时满足；
2. 新增 `openai_compat.stream_dual()`：**绝不做 reasoning→正文兜底**。
   ⚠️ 不能直接用 `stream_with_thinking`——它有「流结束且无 content 就把 reasoning 当正文输出」
   的兜底，而那道防线是「英文占比 >15%」，**对中文思考的模型（Qwen3.8）完全放行**，
   会原样复现 2026-09-09 的老坑。优先级：`stream_dual` > `stream_with_thinking`（ollama 版无兜底，安全）
   > `stream`（claude 等）；
3. `sse.js` 超时语义改为**空闲超时**（每次收到数据 `reset()` 拨满），并把 abort 真正接上
   `reader.cancel()`。⚠️ 必须改语义：按总时长计时的话，407s 首字即便有 thinking 保活也会被 180s 误杀；
4. `chapter.py` 的 max_tokens **彻底放开**为 32768（用户拍板）：旧公式 `min(目标字数×1.2+256, 8192)`
   在开思考时是错的——reasoning 与正文共用同一预算，3000 字算出 3856，思考吃掉大半后正文只剩几百 token。
   max_tokens 只是上限、按真实生成量计费，给满不多花钱。

**铁律**：
① **"network error" 往往不是网络问题**——先比对时间戳差值，看是否卡在某个配置的整数秒上
   （300s → vite proxy；180s → 前端 SSE 超时）；
② **长思考模型必须让思考阶段有字节流动**，否则中间链路（代理/浏览器）会按空闲掐断，
   且错误信息完全掩盖真因；
③ **超时语义要想清楚「总时长」还是「空闲」**：有保活帧的场景必须用空闲，否则保活白做；
④ **兜底逻辑要看它对什么输入失效**：「英文占比」这类防线对中文思考=零防护；
⑤ **任何 `except Exception` 吞掉的异常都要定期扫 error.log**——本次若不是顺手看日志，
   GraphRAG 块会继续静默丢失。

**回归测试**：`tests/unit/test_chapter_thinking_not_in_body.py`（3 条）锁死
「thinking 必须发」+「reasoning 绝不进正文/绝不落库」，含一条**中文思考**用例
（专门绕过英文占比防线）。

### E11 · ⚠️ 行为变更只改了 `if` 分支、漏改 `else`：同函数内新不变量没传导（2026-09-20 实测，2 条红灯）

**症状**：`tests/unit/test_plot_cast.py` 2 例失败，`IndexError: list index out of range`
（`plot_distill.py:330`）。两条失败**自 2026-09-18 起就是红灯**，与当次改动无关。

**根因**：`_normalize_cast` 在 **2026-09-18** 改过一条行为约定 ——
「`srcs` 全非法时**保留槽位、`srcs` 置空**」（原为"整个槽位丢弃"，因实测太荒 68 条模板 cast 全 0）。
改动**只落在 `if not srcs:` 分支**（加了一条 warning），而**紧随其后的 `else` 分支仍在裸用 `srcs[0]`**：

```python
if desc:
    desc = anonymize_text(desc, strong)
else:
    desc = desc_of.get((srcs[0]["book"], srcs[0]["alias"]), "")   # srcs 可能为空
```

触发条件是**两个条件的合取**：① 槽位 `srcs` 为空（新语义才允许的状态）；② 该槽位 LLM **没写 `desc`**。
**即：新行为 × 旧分支的组合态从未被测过**——测试文件写于 09-18 16:03，实现改于 09-18 17:31，**实现变更时没跑测试**。

**影响面（已逐一取证，别凭感觉说"严重/不严重"）**：

| 路径 | 是否命中 | 兜底 |
|---|---|---|
| `distill_all`（跨书凝练） | 命中 | `plot_distill.py:754` 组级 `except Exception` → 该组记 `failed`，其余组照常 |
| `plot_distill_singles.py`（单弧兜底） | 命中 | 第 226 行批级 `except` → 该批记 `failed` |
| **在线检索 / 选角 / 章节生成 / 商讨** | **不命中** | `plot_template_crud` 对 `plot_distill` 仅一处懒加载 `TRAIT_DIMS`（纯常量 dict）；`app/routers/**` 零引用 |

⇒ 表现是**离线凝练链路的静默 cast 丢失**（不中断整轮、不报错，只进 `failed` 列表），
**不影响任何在线功能**，也不影响已入库的 75 条骨架（那批走 `ingest_merge_skeletons.py`）。

**修复（2026-09-20）**：`elif srcs:` 回填原描述 / `else:` 留空——**不猜**。
`test_plot_cast.py` 2 例转绿，全量 **534 passed / 0 failed（18.38s）**。

**铁律**：
① **在一个函数里改出新不变量（"X 现在可以为空/为 None"）时，必须 grep 该变量在本函数内的全部使用点**——
只改"报错的那一处"会留下**组合态才触发**的坑（单看每一处都"逻辑正确"）；
② **行为变更的测试与实现必须在同一次改动里对齐**，且改完立刻跑全量——
本次红灯挂了 2 天，靠"基线是红的"当借口，实际是**没人负责**；
③ 排查"某组/某批静默失败"时，**先看它是不是被 `except` 吞了**——
本项目的批量链路大量使用 `except Exception → logger.warning + 记 failed`，
这是**故意的韧性设计**，但也意味着**真 bug 会伪装成"偶发失败"**。
