### A2 · 沙箱起后端产生关不掉的 8000 孤儿进程
- **2026-08-11 确诊**
- 现象：沙箱里起后端后，`taskkill` 报"找不到进程"，但端口一直被占，只能重启机器。

### A7 · ⚠️ 在沙箱里跑 `git fetch` / `git rebase` 会**破坏 `.git`**（2026-09-10 实测，代价很大）
- **现象**：一次 `git rebase <远程sha>` 报 `could not mark as interactive: No such file or directory`，
  随后所有 git 命令变成 `fatal: not a git repository`。
- **根因**：`.git/refs/` 整个目录被抹掉（连同 `refs/heads/main`），且**新写入的松散对象丢失**
  （`git commit` 刚成功的提交对象、`git fetch` 刚拉下来的提交对象都读不出来）。
  沙箱对 `.git/refs/**`（尤其 `refs/remotes/`）的写/改名做了拦截，git 拿不到预期的文件系统语义，
  清理或回滚时把目录一起带走了。同类现象：`git fetch` 报告 `[new branch] main -> origin/main` 成功，
  但 `refs/remotes/origin/main` 根本不存在（`git rev-parse origin/main` 报 unknown revision）。
- **判别方法**：git 判定「有效仓库」要求 `HEAD` + `objects/` + **`refs/`** 三者齐全。
  一旦 `.git/refs/` 消失，git 会直接说 "not a git repository"，**而不是**报 refs 缺失——很容易误判成仓库被删。
- **恢复流程（已验证有效，约 5 分钟）**：
  1. **立刻 `cp -r .git /e/AI_novel_git_backup_<ts>`**（把损坏的 .git 整体留档，禁止在原件上试错）；
  2. `mkdir -p .git/refs/heads .git/refs/tags`（**只建目录**）→ git 立刻恢复识别仓库；
  3. `git cat-file --batch-all-objects --batch-check` 枚举现有 commit，确认历史断在哪一条；
  4. 本地 pack 若也缺对象（`git ls-tree <sha>` 报 unable to read），**以远端为准重建**：
     `mv .git .git.corrupt.<ts>` → `git init -b main` → 配 remote → `git fetch origin main`
     → `git update-ref refs/heads/main <FETCH_HEAD>` → `git reset --mixed`（重建索引，**不动工作区**）；
  5. `git status` 会列出全部未提交变更 → 重新提交 → push。
- **关键前提**：**工作区文件从不受影响**（沙箱只搞 `.git`），所以只要远端有完整历史，就能 100% 还原。
- **铁律（写进工作方式）**：
  1. **沙箱里不要用 `git rebase`**。要同步远端新提交，用 `git fetch` + `git merge`，或干脆以远端为准重建本地仓库；
  2. **push/rebase 前的第一件事是 `cp -r .git` 备份**（1.6MB，一秒的事）；
  3. 每次 `git push` 前先 `git ls-remote origin main` 对一下远程 SHA，避免"远程被别人改过"导致的拒绝+随后一串危险操作；
  4. 远端仓库本身就是最好的备份——**保持每次工作结束都 push**，本地 `.git` 就不是单点。

### A8 · ⚠️ 沙箱里删「目录内任一文件」会**连带清空整个同级目录**（2026-09-10 实测，Phase 3.1 踩中）
- **现象**：用 `git rm frontend/src/components/workspace/ChapterElementsPanel.vue`（只删 1 个文件），
  结果 **`components/workspace/` 整个目录 7 个文件全没了**；把 `Remove-Item -Recurse` 指向 `_deprecated/`
  时，连 `views/  store/  router/  layout/  utils/  styles/` 一起消失（共 31 个文件）。`git status` 显示一地 ` D`。
- **根因**：沙箱的文件系统拦截层在「删除受保护目录内的条目」时，会把**同级目录树**一并标记删除，
  不是 git 的错（`git rm` 本身只删指定路径）。同一命令**单文件 `rm -f` 时不触发**，
  但 `git rm` 或 `Remove-Item -Recurse` 会触发。
- **判别方法**：删完**立刻数文件**——`find <dir> -type f | wc -l`，与期望值逐一核对；
  再看 `git status --short | grep "^ D"` 有没有出现**你没打算删的路径**。
- **恢复（100% 可靠，全部源码都在 git 里）**：
  ```bash
  rm -f .git/index.lock                     # 被杀进程常留陈旧锁
  git restore --source=HEAD --worktree --staged <path>
  ```
  本次 31 个文件、63 个文件规模都秒级还原；**工作区内容从不受损，只是被误删**。
- **铁律**：
  1. **删文件优先用 `rm -f <单个文件>`**（实测安全），**不要**用 `git rm` / `Remove-Item -Recurse`
     在**多文件目录**上操作；
  2. 必须让 git 记录删除时，用 **`git update-index --force-remove <path>`**——纯索引操作，
     **完全不碰文件系统**，彻底绕开此 bug；之后再 `rm -f` 单个文件清磁盘；
  3. 批量删除前先 `cp` 备份到 `/tmp/`，删完立刻数文件核对；
  4. 一旦发现误删，**先 `git restore`**，不要在乱状态上继续操作（尤其别 `git add -A`，
     否则把误删写进暂存区，风险陡增）。

### A10 · ⚠️ git commit「报错但实际成功」+ 同名分叉提交的处置（2026-09-10 实测，Phase 3.4）
- **现象一：commit 报 `nothing added to commit`，但提交其实已经产生。**
  本次执行 `git commit -F <msgfile>` 时，输出是：
  ```
  nothing added to commit but untracked files present
  ```
  紧接着 `git status` 显示**暂存区空、工作区也干净**，而 `git log` 里**已经多出了那条提交**。
  根因：前一步 `git reset --soft HEAD~1` + 紧接着的 `git add` 之间，**索引被并发/沙箱包装层写坏**，
  commit 在读取到旧索引的另一条路径上完成了。
  → **铁律：`git commit` 后不要只信它的 stdout，必须 `git status --short` + `git log --oneline -1` 双验证。
  看到「nothing to commit」而工作区又干净时，先查 `git log`，十有八九已经提交成功，再 commit 一次会建重复提交。**
- **现象二：远端与本地出现「同名不同 sha」的分叉提交。**
  因为上面那次「报错但成功」，远端留下了 `832ef4f`，随后我又压了一条 `2ec2e51`；
  两者 **`parent` 都是 `dae35c4`** → 是**兄弟分叉**，不是父子，所以普通 `git push` 必被拒
  （`non-fast-forward`）。
  **判别分叉**（别硬猜，一条命令看清）：
  ```bash
  git log --format="%h %p %s" -1 <A>   # 看 A 的 parent
  git log --format="%h %p %s" -1 <B>   # 看 B 的 parent
  # parent 相同 = 兄弟分叉；A 的 parent 是 B = A 是 B 的后代
  ```
  **处置（本次采用）**：先 `git diff --stat <远端sha> <本地sha>` 看清两者**实际差什么**——
  本次只差 CHANGELOG 的 2 行（本地版修了一个多余的 `- ` 前缀 + 补了路由口径说明），
  即**本地版严格更优**，且仓库是**单人本机工具**、远端无他人提交 → 打两个备份 tag 后
  `git push --force-with-lease=main:<远端sha> origin main`（**带 lease 比 `-f` 安全**：
  若远端在此期间被别人推进过，lease 校验会直接拒绝）。
  推完 `git ls-remote origin main` 核对 sha，并删除备份 tag。
  → **反例警示**：如果两者差异是「各有对方没有的内容」，就必须走 `merge`/`rebase` 合流，
  **绝不能 force**。force 只适用于「远端那条已被证明是废弃品且无独有内容」。
- **现象三：`origin/main` 报 `unknown revision` 但 push 却成功。**
  沙箱拦截 `refs/remotes/**` 写入（同 **A7**），`git fetch` 显示 `[new branch] main -> origin/main`
  但盘上**只生成了 `.git/FETCH_HEAD`、没生成 `.git/refs/remotes/origin/main`**。
  → **核对远端状态一律用 `git ls-remote origin main`（直接问服务器），不要信 `origin/main` 这个本地 ref。**
  同理 `git status -sb` 里的 `[gone]` 也是这个原因，**不代表远端分支被删**。
- **衍生教训（编码误判）**：我一度以为提交里 CHANGELOG 是乱码，差点据此做决策。
  实际把 `git show <sha>:CHANGELOG.md` 的**字节流**取出来解码数 `\ufffd` 与 `\uXXXX` 字面量，
  两个提交**都是干净的** —— 我看到的是**工作区的临时中间态**。
  → **判断「提交内容坏没坏」必须看提交对象（`git show <sha>:<path>`），不能看工作区当前文件。**

### A11 · ⚠️ 用 `git checkout -- <file>` 还原「实验性改动」会**连未提交的正式改动一起回滚**（2026-09-10 实测，Phase 3.5）
- **场景**：为验证新写的护栏测试**真的能抓到违规**，我临时把 `load_observation.py` 的一个
  handler 改成 `except Exception: pass`（违规版）。验证通过后想还原这个**实验性改动**，
  顺手执行了 `git checkout -- backend/app/services/load_observation.py`。
- **后果**：该文件**尚未 commit** 的 Phase 3.5 正式改动**被一起回滚掉了**——因为
  `git checkout -- <file>` 的语义是「**把工作区该文件恢复成 HEAD 的版本**」，
  它**不认识**"哪部分是实验、哪部分是正式"，一律丢弃。
  （侥幸发现：我在注入前 `cp` 过一份 `.bak`，但命令里 `git checkout ... || cp .bak` 的
  短路顺序写错——`git checkout` 成功返回 0，`.bak` 分支**根本没执行**，差点白丢。）
- **铁律**：
  1. **任何"改代码做实验"之前**，若该文件有**未提交**改动，先 `git stash push -- <file>`
     或 `cp` 到项目外的临时路径（**别信 `||` 兜底，成功即短路**）。
  2. 实验完还原时，**优先用 `cp` 把备份放回去**（语义明确），不要用 `git checkout --`（它回 HEAD）。
  3. 若确实误回滚了：未提交改动**无法从 git 恢复**（`git reflog` 只救 commit 过的）。
     只能靠备份 / 重新实现。**所以备份是唯一保险。**
- **自检习惯**：回滚一个文件后立刻 `git status --short` 看它**是否还在修改列表里**——
  若本该有改动却消失了，就是被回滚了（我这次正是靠这步发现）。

### A7. `git push` 静默 128：真凶是 gh credential helper 子进程（2026-09-13，三次更正终版）

- **现象**：push 恒 rc=128，stderr 只有 `Pushing to ...` 一行（PowerShell 管道连 fatal 文本都捕不到）。
- **三次误判史**：①最初判"凭据助手被杀"→ ②推翻为"PowerShell 静默即杀看门狗，GIT_TRACE 是开关"
  （15:10 无 trace 连挂 3 次、带 trace 首试即中）→ ③ 16:15 **带全套 trace 依然 128**，二次推翻。
- **对照实验（终版定论）**：两次推送都带全套 GIT_TRACE，唯一差异 `-c credential.helper=`——
  禁 helper 一次成功（pack 传输 trace 全程可见）。trace 尾部证据：HTTP 正常完成后
  `run_command: gh.exe auth git-credential store`，助手子进程没回来 → git 128。
  **真凶 = gh credential helper 子进程被环境杀（get/store 阶段都可能，呈随机性）；
  "带 trace 即成功"是幸存者偏差——那几次 helper 恰好活着。**
- **最终稳定方案（token URL 下 helper 纯多余，禁用无副作用）**：
  ```powershell
  $tok = gh auth token
  git -c credential.helper= push --progress "https://oauth2:$tok@github.com/<owner>/<repo>.git" main
  ```
- **排障顺序**：push 128 → 先 `git ls-remote` 确认网络/仓库可达 → token URL + 禁 helper 重推
  → 仍 128 才叠加 GIT_TRACE 系列看卡在哪个阶段。

- 根因：`openai_compat.py` 把 `nvidia` 归进 `chat_template_kwargs.enable_thinking` 阵营；而 NVIDIA NIM 的 GLM-5.2 应用**顶层 `thinking:{"type":"enabled"}`**（同 zhipu/deepseek）。字段不匹配 → 模型进入"只走 reasoning、content 为空"的异常态。
- 解决：厂商白名单——`qwen`/`nvidia`… 修正为：
  - `zhipu` / `nvidia` / `deepseek`：顶层 `thinking.type`（deepseek 还需 `reasoning_effort`）
  - `qwen`：`chat_template_kwargs.enable_thinking`
  - `openai`：无思考字段（o1/o3/o4 用 `max_completion_tokens`）
  - kimi/ernie/spark/siliconflow/custom：无标准字段
- 现状：已修。**新增厂商时先确认它认哪个字段，否则 400 或正文丢失。**

### B3 · vendor 填错导致安全网被绕过
- **2026-08-14 确诊**
- 现象：默认模型标 `vendor="custom"`（非 `qwen`），而 `chapter.py` 的 `_broken_thinking_combo` 安全网与 `openai_compat._payload()` 都只匹配 `vendor=="qwen"` → **完全绕过**；`custom` 又不发任何思考字段 → 模型按默认 thinking=ON 跑 → reasoning 泄漏进 content，表现为"无标点长段 + 英文推理词 + 同义反复循环"。

### B4 · 长文复读（RepetitionGuard）的正确姿势
- **2026-08-10 → 08-12 三轮迭代**
- 现象：小模型/非思考模型写长文，同一段落复读 4–5 遍，直到 token 烧爆。
- 演进：
  1. 第一代：滑动窗口检测（600 字符，重叠率 >55% 且 >40 字符）→ 触发后停止 yield 但**继续消费迭代器** → 云端继续计费，且第二次生成内容未过滤混入正文。
  2. **错误修复**：有人写成 `for _rest in adapter.stream(...)` → **重新发起一次完整生成**（双倍计费 + 内容错乱）。已改为 `loop_stopped=True` 标志。
  3. 终版：触发后 `break` + `finally` 里 `gen.close()` → 关闭 HTTP 连接 → **模型立即停止、云端立即停计费**。
- 附带发现：GLM-5.2 **关闭思考**写 3000 字长文必复读；开 thinking 后恢复正常（2362 字完整）。→ `chapter.py` 章节生成**强制 `want_thinking=True`**（vendor≠ollama 时；ollama 例外，因为 ollama 在 think=true 时正文为空）。

### B5 · "越多约束越好"对 LLM 是假命题
- **2026-08-13 确诊**
- 现象：章节正文突然变成"成语接龙 + 无标点长段"。

### B10 · 按模型版本字面量做特判，换代必失配

### B11 · 后处理"防复读"误杀：字符集 Jaccard 对中文短段落完全失效
- **2026-09-09**（Qwen3.8-Flash-Next 开 thinking 实测发现）
- 现象：开 thinking 后字数反而暴跌（流式 3018 字符 → 落库仅 1536），**DB 与流式不一致**；表面看像"模型写短了"。
- 根因：`_dedup_trailing_repeats`（尾部复读兜底）用**字符集合 Jaccard** 判段落相似。中文短段落 6~7 个字，字符集只差一个字 Jaccard 就爆 0.85——实测「沈砚看水洼。」vs「沈砚看向水洼。」= 0.857，触发"从此段全裁"，**后面 97 段正常剧情（1482 字符）全部陪葬**（含收尾钩子"牙印上刻着'伍'"，0 段真重复）。
- 修复（三重防线，离线 4 用例全过）：① 短段 <20 字不参与判定（短句呼应是正常手法）；② 相似度换 difflib（内容敏感），字符集 Jaccard 仅作 0.3 以下快速预筛；③ 连续 ≥3 个长段相似才判定复读（单段相似=呼应）。
- **最终定案（对照实验汇总）**：Qwen3.8-Flash-Next 正确配置 = **惩罚 0 + thinking 可开**。开 thinking 实测写 1894~2800 字达标正文（关 thinking 只自然停 1493），代价是首字 ~130s（reasoning 时间）。路由层 `_content_only_stream` 保证 reasoning 不进正文。
- **教训：① 判"重复"要看内容序列（difflib/编辑距离），不能看用字面（字符集合）——中文叙事段用字面高度重合是常态；② 兜底逻辑（防复读/防退化）本身必须有防误杀设计和测试用例，否则它杀的正常正文比病还重；③ e2e 报告里"DB 与流式不一致"是发现这类静默坑的关键信号（已加入自动检测与存档）。**

### B13 · 魔搭端点 GLM-5.3-Flash：正文全进 reasoning_content、content 恒空，thinking.type 被静默忽略
- **2026-09-10 上午**（换默认模型 ZhipuAI/GLM-5.3-Flash 当天，e2e 实测踩中）
- 现象：e2e 全链路 91.2s "正常"走完（start→done 无报错），但 **0 个 content chunk、正文 0 字**、摄取因无正文而跳过。
- 取证：写 20 行探测脚本直连魔搭统计 SSE 帧字段分布——**773 帧里 reasoning_content 累计 1418 字（正文全在其中），content_len=0**；带 `thinking.type=disabled` 再探——**不报 400 但字段被静默忽略**，content 仍恒空。官方示例文档明示正文走 `delta.content`，与魔搭实际行为不符。
- 根因：`openai_compat.stream()` 只取 `delta.content`、忽略 reasoning——`chat()`（非流式）和 `stream_with_thinking()` 都有 reasoning 兜底，**唯独章节生成用的 stream() 漏了**（GLM 系"正文进 reasoning"是已知病，NVIDIA NIM GLM-5.2 同款）。
- 修复：stream() 补同款兜底——流结束 content_seen=False 时输出缓存的 reasoning，**英文占比 >15% 拒绝**（Qwen3.x 的英文分析泄漏不污染正文）；Qwen3.x 不受影响（content 正常出，永远进不了兜底分支）。
- **续（同日二轮取证）：兜底生效后 0 chunk 消失（首字 61.1s），但暴露第二层问题——content 不是恒空，是"排在 reasoning 之后、被 max_tokens 预算卡死"**。三档探测：mt=800 → reasoning 1656 字 + content 仅 80 字（finish=length 截断）；mt=4000 → reasoning 2159 + content 485（finish=stop，正文干净）；mt=16000 → content 494 全程干净。章节生成公式 `min(目标×1.2+256, 8192)`=3256，GLM reasoning 吃 ~2000 后正文被挤压 → **落库文本前半正常、后半无标点连排（411 字），字数 1464 不达标**。修复：chapter.py 对 GLM 系（model 含 "glm"）直接给 6 倍目标字数（15000，finish=stop 按实际计费，免费端点无成本），其余模型原公式不变。
- **终局取证（同日三轮）：32768 预算下字数达标（2229），但暴露第三层问题——GLM-5.3-Flash 把「元认知思考」直接写进 content 正文流**：英文自我审查段（"Wait—I wrote an internal reasoning slip above...""" 408 字）与中文无标点连排段（100~407 字）交替出现，去AI味 0 分。这不是代码问题：`thinking.type` 被魔搭忽略（关不掉思考），模型自发在 content 里"边想边写"，**应用层无法修**（按段落过滤英文会留下结构破洞）。
- **决策建议（2026-09-10）**：魔搭端点的 GLM-5.3-Flash 不适合章节正文生成；换回 Qwen/Qwen3.8-Flash-Next 当默认（final-green 全绿基线在），GLM-5.3-Flash 可留作商讨/短问答。三层问题链：① 正文进 reasoning + content 预算被吃（已修 stream 兜底 + max_tokens）→ ② thinking 无法关闭（魔搭忽略）→ ③ content 混元思考 + 无标点连排（模型行为，无解）。
- **教训：① 接入任何新模型，先跑最小探测脚本看原始 SSE 帧的字段分布，别信官方文档的响应结构说明——文档描述的是官方端点，第三方兼容层（魔搭/NIM）各有各的魔改；② "静默忽略未知字段"比 400 更阴：不带错误提示，症状只剩"安静地空"，取证必须回到原始帧；③ 同一行为在 chat/stream/stream_with_thinking 三个入口要一致兜底，漏一个就是静默黑洞；④ 推理模型（reasoning-first）的 max_tokens 是「思考+正文」共享预算——reasoning 长度波动直接侵蚀正文，×1.5 老经验对它们全部失效，必须按模型家族单独放宽；⑤ e2e 全绿是"能不能用"的判据：链路通了不等于质量能用，**模型本体的输出风格崩坏（元思考混正文）换任何参数都救不了，及时止损换模型**。**

### B12 · 复读兜底漏裁"正好 3 段"的复读块：_is_dup 只向前文比较，块首必判 False
- **2026-09-09 深夜**（Phase 0.1 单测骨架第一天就抓到的真缺陷）
- 现象：单测 `test_constructed_repetition_is_cut` 构造「6 段正常正文 + 3 段相同复读」→ 期望裁掉尾部 3 段，实际**原样返回**。
- 根因：`_dedup_trailing_repeats` 的 `_is_dup(idx)` 只在 `range(idx)`（前文）里找相似段。复读块的"块首"（第 1 段重复）前面全是正常文本 → 必判 False → run 从尾部数只有 2（末两段靠同块成员互判 dup），凑不满 RUN=3 → **正好 3 段的复读块永远裁不掉，4 段才够数**。B11 修复时的构造用例恰好比 3 段长，把这个边界盖住了。
- 修复：`_is_dup` 增加「或与紧邻后一段相似」判定，块首靠它入组；后一段同样过三道门（≥20 字 / Jaccard≥0.3 预筛 / difflib>0.8），不扩大误杀面。3 份真实轮次文本（B' 流式 180 段 / final-green / Qwen3.5 基线）回归零误杀。
- **教训：① 单测边界用例必须覆盖"恰好达到阈值"的场景（恰好 RUN 段、恰好 MIN_LEN、恰好 TH），只测"明显超标"会漏真缺陷；② "与相邻段落相似"是块成员关系，"与任意前文相似"是呼应关系——两者语义不同，兜底判定要分清；③ 单测骨架落地的第一晚就抓出 e2e 三轮全绿没发现的缺陷——e2e 靠真实模型随机性撞不出确定性边界，两者互补缺一不可。**

## C. 代码与架构类

### C1 · 流式生成器内严禁访问请求级 DB session（**铁律**）
- **2026-08-11 确诊**（曾回归过一次）
- 现象：流式对话报 `BodyStreamBuffer was aborted`，日志里是 `DetachedInstanceError`。
- 根因：`StreamingResponse` 的 `event_stream` 生成器在**线程池**运行，`chat()` 返回响应后请求级 `get_session()` 已关闭。生成器内读 `default.xxx`（ORM 字段）或 `db.query(...)` → `DetachedInstanceError` 抛在 try 外 → 流中断。
- 正确做法（已在 `discussion.py` 落地）：
  1. 在 `chat()` 内、session 仍开时，把 ORM 对象的**标量提取成普通 dict**（`model_cfg`）；
  2. 生成器内用 `gen_db = _db.SessionLocal()` 自建独立 session（`_db` = 模块引用，**绝不能** `from app.core.database import SessionLocal` 直接导入——导入时绑定到启动前的 `None`）；
  3. `finally` 中 `gen_db.close()`。
- 教训：**B 方案改动曾误在生成器里用 `default.*`/`db`，就是这条的回归。** 改流式代码时第一个检查这个。

### C2 · 事件时序：不要发在 `finally` 之后
- **2026-08-11**
- 现象：GLM-5.2 的 `BodyStreamBuffer was aborted`，一度误判为"回答展开太长"。
- 真实根因：`entity_suggestion` 事件是在 `event: done`（`finally` 开头）**之后**才发出的 → 客户端已关闭连接。
- 教训：**SSE 的所有业务事件必须在 `done` 之前发完。**

### C3 · 后台线程里重查 ORM 对象
- 写后摄取改为后台线程 `_background_ingest` 时：必须 `_db.SessionLocal()` 独立会话 + **按 id 重新查询** `ChapterORM`（不能持有请求级对象），末尾 `t_db.commit()` 兜底，`daemon=True`。
- SQLite 并发写（后台摄取 vs 其他请求）可能偶发 `database is locked`，已 try/except 兜底（只丢当次摄取、不影响正文）。

### C4 · Pydantic alias 漏 `by_alias`
- **2026-08-13**
- 现象：工作流更新后接口全 500。
- 根因：`model_dump(exclude_unset=True)` 未传 `by_alias=True` → `FlowEdge.from_` 以 `from_` 键名入库而非 alias `from` → 后续 `model_validate` 抛 `ValidationError`。
- 教训：**有 alias 的 schema，dump 时必须 `by_alias=True`。**

### C5 · 前端重复解包
- 现象：实体确认永远显示"已写入 0 条"。
- 根因：`views/ChatView.vue:188` 写 `res?.data?.data`，而 `api/http.js` 拦截器**已解包过一次** → 取到的是 `data` 字段本身。
- 教训：拦截器统一解包后，**业务代码里不要再 `.data`**。

### C6 · 对话弹窗常驻挂载导致状态残留
- 现象：生成完一章后再点"生成章节"，仍停在结果页，没有生成按钮。
- 根因：`GenerateChapterDialog` 常驻挂载（仅 `v-model` 显隐），关闭后内部 ref 不销毁，`result=true` 残留。
- 解决：`watch(props.modelValue)` 每次打开复位全部状态；结果页 footer 加"重新生成"按钮。
- 教训：**Element Plus 的 `el-dialog` 默认不销毁内部状态**，凡是有流程状态的弹窗都要 watch 复位。

### C7 · 向量索引是「全局表」，跨项目靠 top-k 过采样过滤必然漏召回
- **2026-09-10 实测抓出**（A3/A4 上线后第一次真机 e2e）
- 现象：项目内导入 4 份参考文档、全部建好向量（表里 10 块），但生成时 `pick_relevant` 只命中 1 份。
- 根因：`vec_index`（vec0 虚拟表）**所有作品 + 全局资料池共用一张**，KNN 查询本身不带项目过滤；旧实现用 `k = top_k * 3` 全局过采样，再回表按 project_id 过滤。全局池有 133 块、本项目只有 10 块 → top-k 名额被全局池的块吃光，回表后本项目块几乎全被截掉。
- 修复：`vec_index` 加 `project_id`/`source_type` **辅助列**，KNN 查询内直接 `AND project_id=? AND source_type=?` 过滤（sqlite-vec v0.1.9 支持元数据过滤，先 `MATCH` + `k` 再过滤，实测可行）；`vec_index_available` 校验 schema 含辅助列，旧 schema 判为不可用；`_ensure_vec_index` 启动时检测旧 schema → 删表重建 → 从 `vector_chunks`（source of truth）自愈回填。回归用例：往干扰项目塞 200 个同向块，本项目 3 块必须完整召回。
- 教训：**「全局索引 + 查询后过滤」在小数据集上看着没问题，一旦别的分区更大就静默失效**——凡是分区语义的检索，过滤条件必须进到索引查询内部，不能靠取多了再筛。

### C8 · 作品级联删除漏清无外键的表（孤儿数据复发）
- **2026-09-10 实测**：删测试作品后 `vector_chunks` 残留 10 块。
- 根因：`project_crud.delete_project` 只遍历 `_RELATED` 里的 ORM 表，而 `vector_chunks` 没进该列表（新建表时容易忘记登记），`vec_index` 更是虚拟表、根本不走 ORM 级联。
- 修复：`delete_project` 显式调 `vector_store.remove_project_index(db, pid)`——同时清 ORM 主表与 `vec_index` 虚拟表；单测断言「删 px 后 py 的块与索引都还在」（作用域正确）。
- 教训：**每新增一张带 project_id 的表，必须同时检查三处：级联删除列表、孤儿清理脚本、以及是否有虚拟表/索引需要单独清**。这正是 03 §3.1「孤儿数据」问题的同类复发——旧坑是删作品前遗留，新坑是新表没登记。

### C9 · 异步摄取与「删除作品」竞态：向量写在删除之后 → 孤儿块
- **2026-09-10 全流程 e2e 后巡检发现**：DB 里 `vec_index` 133 行 vs `vector_chunks` 133 行对不上（多 2 行），查孤儿块 project_id = 刚被 e2e 删掉的测试作品。
- 根因：写后摄取是**异步后台线程**（`ingest_start` 事件后不阻塞 `done`）。e2e 脚本拿到 `done` 就删作品，此时摄取的 `sync_after_ingest` 尚未跑完 → 级联清理先跑（当时向量还没写）→ 摄取随后把章级记忆/篇章摘要向量写进一个**已不存在的项目**，成为孤儿。危害放大点：`vec_index` 是全局表，孤儿块会永久参与所有项目的 KNN，挤占 top-k 名额（与 C7 同源）。
- 修复：`vector_index.index_chunks`（**所有向量写入的唯一咽喉**）开头加项目存在性守卫——项目已不存在则直接返回 0（在 embedding 之前，顺带省一次 API 调用）；`__global__` 是全局资料池的虚拟 project_id、没有 projects 行，必须豁免（否则全局池无法建索引）。
- 教训：**异步任务 + 级联删除必然有竞态窗口，写入方必须自证「目标仍存在」**，不能假设创建时校验过就一直有效。守卫要放在写入咽喉而不是调用方（调用方可能有多处、以后还会加）。

### C10 · 错误提示被当成小说正文落库，且会**静默覆盖已有正文**
- **2026-09-10 复核确认仍是活 bug**（Phase 1 止血 1.2）。`chapter.py` 里模型调用失败时
  `content_parts.append("[模型调用失败，已降级为占位：…]")`，而 `full = "".join(content_parts)`
  随后直接落库 → **错误文案变成了小说正文**；未配置模型时同理写入占位符。
- **放大危害**：走「重新生成」路径时 `update_chapter(content=full)` 会把**已有章节正文整段覆盖成错误提示**
  —— 作者以为只是生成失败，实际原稿已被静默抹掉。
- 修复：新增纯函数 `_can_persist(full, error_notes)`：
  - 错误/占位文案改存 `error_notes`，**只推前端展示，不进 `content_parts`**；
  - 落库前判定，正文为空则不落库、只发 `error` 事件说明原因（不发 `saved`）；
  - 空正文时跳过去重与 AI 味扫描（避免对空文本无意义处理）。
  前端补 `error` 事件处理：不再误报"生成完成"，留在表单页可直接重试。
- 测试：`test_chapter_persist_guard.py`（8 用例，纯函数）+ `test_chapter_failure_no_persist.py`
  （**真实驱动 SSE 生成器**，用必抛异常的假适配器复现失败：不建章 / 不覆盖原稿）。
- 教训：**"降级/占位"这类兜底文案只应出现在展示层，绝不该进入持久化路径**。写兜底前先问一句「这条文案会被存下来吗」。

### C11 · 调试日志把模型输出写进仓库目录（隐私 + 硬编码绝对路径）
- **2026-09-10 清理 print 时顺带发现**：`openai_compat.stream_with_thinking` 里残留的 GLM 排查调试块，
  把每帧 `CONTENT_SAMPLE` / `REASONING_SAMPLE`（各 120 字**模型输出正文/思考**）写进
  `r"E:\AI小说创作\backend\glm_sse_raw.log"`。
- 三个问题：① 用户小说内容落盘（与 1.1 隐私同类）；② 硬编码绝对路径，换机器即崩；
  ③ 每次带思考的流式都开文件写入 + flush，白耗 IO。
- 修复：整块移除（原始帧探测能力保留在 `tests/e2e/probe_glm_ms.py`）；删除残留日志文件。
- 教训：**调试代码写完必须当场删除或迁到 `tests/`**，尤其涉及打印/落盘用户内容与绝对路径时。
  临时调试留在生产路径上，迟早会变成隐私事故或跨机器故障。

### C12 · 「孤儿数据」判定必须豁免 `__global__`（差点删掉全局资料池与全部向量）
- **2026-09-10 清理孤儿数据时踩中**。按「`project_id` 不在 `projects` 表里」判孤儿，
  统计出 `vector_chunks` 有 133 行"孤儿"、`discussion_messages` 有 25 行"孤儿"。
- 真相：`__global__` 是**全局资料池的虚拟 project_id**，它本来就不是 `projects` 行——
  这 133 行是**全局池 18 份资料的向量索引**（当天刚 reindex 建的），25 条是全局对话记录，
  全是合法数据。若照统计删除，**全局检索会直接报废**（vector_chunks 与 vec_index 同时清空）。
- 修复：所有表的孤儿判定统一加 `AND project_id != '__global__'`；删除前先导出 + 备份；
  删完校验「孤儿 0 且全局池计数不变（18 份资料 / 133 向量块）」。
- 教训：**用"外键不在主表"判孤儿时，必须先枚举该列的全部取值**（`GROUP BY project_id`），
  确认有没有哨兵值/虚拟值——否则哨兵值会被当成孤儿，删掉的是核心数据。

### C13 · `fetch` 不校验 `resp.ok`：JSON 错误体被当事件流解析，错误静默消失
- **2026-09-10（Phase 1.3）**。`api/chapter.js:generateChapterStream` 拿到 `resp` 直接
  `resp.body.getReader()` 按 SSE 解析。后端在参数错误时返回 **400 + JSON**（如漏传 `article_id`
  会返回「生成章节必须指定所属篇」），前端把 JSON 体按 `event:/data:` 切 → 切不出任何事件 →
  **界面表现是"点了一动不动、没有任何提示"**，真实错误被完全吞掉。
- 修复：`if (!resp.ok)` 先读 `detail/message` 再 `throw`；另补 `resp.body` 空判断。
- 教训：**凡是手动读流（SSE / 二进制）的地方都要先校验状态码**；axios 有拦截器兜底，
  裸 `fetch` 没有——同一个项目里两种写法混用，最容易漏的就是裸 `fetch` 这条。

### C14 · session `autoflush=False`：`add()` 后不 `flush()`，同一批后续匹配查不到新记录
- **2026-09-10（Phase 2.1 单测当场抓出）**。`get_engine()` 建的是
  `sessionmaker(autoflush=False)`——查询**不会**自动把待写对象刷进库。于是
  `sync_from_actions` 里「bury X」先 `db.add(X)`，紧接着处理「hint X」时 `_find_match`
  走 `db.query(...)`，**看不到刚 add 的 X** → 又建一条 → **同一章内重复登记**。
- 修复：每次 `db.add(...)` 后立即 `db.flush()`（事务内可见，不影响最终 commit）。
- 教训：**`autoflush=False` 的项目里，"先写后按内容查重"必须显式 flush**。
  这类 bug 在"一次只写一条"的场景永远不出现，一旦同一批里出现"写 A 再查 A"就必踩——
  所以单测必须构造**同一调用内多动作**的用例，只测单动作测不出来。

### C15 · 模糊匹配阈值缺「长度门槛」：短文本互相误并
- **2026-09-10（Phase 2.1 单测抓出）**。伏笔去重按描述相似度判断同一件事，
  初版只设 `difflib ratio ≥ 0.78`。结果「甲的伏笔线索」vs「乙的伏笔线索」（6 字、差 1 字）
  比率 **0.833** → 被判为同一条 → **两条独立伏笔丢一条**。
- 修复：模糊匹配加最小长度门槛 `_SIM_MIN_LEN = 12`（双方都够长才启用模糊），
  阈值提到 0.85；短描述只认「归一化后完全相等」。互相包含判定也保留 ≥6 字门槛。
- 教训：**编辑距离/相似度类阈值必须与文本长度绑定**。短文本的比率天然虚高
  （改一个字就是 10%+），任何"全局单一阈值"在长文本和短文本上不可能同时合适。
  写这类去重逻辑时，**必须专门构造"短且相似但语义不同"的用例**。

## D. 认知与方法论类

### D1 · 短测试通过 ≠ 没问题（最重要的一条方法论）
- B1 是全项目最痛的教训：**"前段正常后段摆烂"类症状，短生成测试永远复现不了。**
- 复现方法：用真实 `build_chapter_messages` + `max_tokens ≥ 5000`，对输出的**头/中/尾分段量化**（标点密度、最长无标点段、拉丁字母数）。
- 推广：**排查生成质量问题时，优先怀疑解码参数（惩罚项/温度），不要先怀疑提示词。A/B 必须控制单一变量。**

### D2 · 文档会骗人，代码不会（但代码也会）
- 旧 `README.md` 状态矩阵把桩模块标成 ✅，旧 `API接口规范.md`（v0.2/v0.3）把已真实落地的章节 SSE / 指令入库 / 记忆压缩全标成"⚠️桩"。
- 2026-08-11 做过一次文档审计，列出 7 处 ❌ 错误陈述。
- **本项目因此立规**：02 的每一个状态必须实测，禁止凭读代码或读旧文档下结论。

### D3 · 0 行 ≠ 死代码，有行 ≠ 活着（两个方向都会骗人）
- 判断模块死活必须 grep ORM 读写点（`XxxORM(` / `query(XxxORM`）。
- **0 行**可能是：**未使用**（skills）、**未触发**（stage_summaries）、**走默认值**（app_configs）——都是正常的。
- 真正空壳的特征是：**既无读又无写**，只出现在级联删除列表里（directions / outlines）。
- **反过来更要命**：表里有大量数据，可能全是**孤儿**。见下方 D6。

### D6 · 数据库里 62%~91% 是孤儿数据（2026-09-09 查明）
- 现象：统计显示 chapters 8、volumes 20、articles 22、chapter_memories 33、reference_docs 42——看起来是个有内容的项目，实际**只有 3 章有效**。
- 根因：21 部作品被删除，但**删除发生在 2026-08-13 补全级联删除之前**，Volume/Article/ChapterMemory/ReferenceDoc 等表当时没进级联清单 → 残留至今。
- 佐证：`characters`/`relations`/`factions`/`locations` **0 孤儿**（这几张表当时在清单里）。
- **验证方法**（可复用）：
  ```sql
  select project_id, count(*) from <表> group by project_id;
  -- 再与 select id from projects 做差集；注意 __global__ 是合法的全局行，不算孤儿
  ```
- **已实测确认当前删除是干净的**：新建 → 塞数据 → 删除 → 残留 0。**所以只需清一次历史数据，不需要改代码。**
- 教训：① 统计产量前先排除孤儿；② 级联删除改过之后，**老垃圾不会自动消失**，要单独清一次。

### D4 · 排查"多个模型同时坏"的思路
- 先怀疑公共链路：超时 / 网关 / 前端拦截器 / 后端未重启。
- 沙箱实测两个模型都正常（Qwen3-8B 22.9s、GLM-5.2 34.2s）→ 确认代码无回归。

### D5 · 工作流引擎踩坑（2026-08-14 上线时）
1. `GraphEngine` 初始入度对所有入边计数会导致 end 多入边死锁 → **end 虚拟入度固定为 1**。

4. variable 类型字段解析引用失败返回 `None` → 加 `resolve_value` 支持固定值。
