# 07 · 任务分发手册（多 agent 协同 · 轻量版）

> 最后更新：2026-09-09
> 适用：**主力单干为主**，任务积压时把独立子任务投递给 TRAE / Zcode / OpenCode，用户当"邮差"。

---

## 1. 工作模式（一句话）

**默认所有活都由主力 AI（本对话）自己干。** 只有当你判断"一下要改的任务太多、一个对话排队太长"时，才让主力 AI 把**可独立、不交叉**的任务拆成「投递单」，你复制粘贴给对应 agent 并行做。

**为什么这样定（2026-09-09 决策）**：
- 调研过现成编排方案（Agent Orchestrator / AI-Coding-Tools-Collaborative / um-agent-orchestration 等），它们的前提是 agent 必须是**可被命令行 spawn 的 CLI**——只有 OpenCode 满足，WorkBuddy / TRAE / Zcode 均不可编程驱动。
- 多 agent 编排的收益随任务量增长，当前单人小项目阶段不划算。
- 你真正需要的不是"自动调度"，而是"任务多时不排队"——投递单 + 你复制粘贴，零基建达成。

## 2. 角色定位（按模型能力分，调度时照此匹配）

| Agent | 主用模型 | 适合接什么 | 不适合接什么 |
|---|---|---|---|
| **主力（本对话）** | GLM-5.3-flash / deepseek-v4-flash / 混元4 | 全部；尤其架构、跨模块重构、调试、后端、prompt、流式 | —— |
| **TRAE** | deepseek-v4-flash | 改前端组件、写单元测试、补类型定义、生成测试数据 | 复杂推理、跨模块协调、架构决策 |
| **Zcode（周末专用）** | GLM-5.3-flash | **集中攻坚**：有难度的模块、长上下文任务、复杂 bug 排查 | 日常小活（额度宝贵） |
| **OpenCode** | Ling / Muse / Nemotron / MiMo / Big Pickle（免费轻量） | **仅轻量微任务**：单文件改写、写注释、补测试用例、改 README、处理日志、生成 fixture | 架构、调试、长上下文、长生成 |

**核心规则**：模型能力差 3 倍以上，不要让它们协作同一段代码——强模型写骨架，弱模型填血肉。

## 3. 何时分发 / 何时绝不

### 可以分发（同时满足）
- 任务彼此**文件不重叠**（用文件划分地盘，见 §5"允许碰的文件"）
- 任务**不需要主力当前上下文**（自包含，能靠 02/06/04 独立完成）
- 是**外围活**：前端组件、测试、文档、fixture、数据整理

### 绝不分发
- 改 prompt / SKILL / 设定注入逻辑
- 后端流式 / DB session / 模型适配器
- 跨模块重构、架构决策
- 数据清理 / 迁移
- 任何需要长对话上下文才能做对的事

## 4. 分发流程（每次只跑 4 步）

1. 你喊"任务多，分发" → 主力 AI 产出 **1~N 张投递单**（格式见 §5），每张对应一个 agent
2. 你**整段复制**投递单 → 粘贴到对应 agent 的对话
3. 该 agent 按单干活，干完**必须**：更新 `docs/02` 对应行 + `CHANGELOG.md` 加一行（投递单里写死这两条，否则算没完成）
4. 你回主力 AI：把 CHANGELOG 最近的改动贴给它 → 它验收（见 §6）

> 需要留档的投递单副本放 `.workbuddy/tasks/`，命名 `YYYY-MM-DD-<任务名>.md`。纯留档，不是流程必需。

## 5. 投递单模板（主力 AI 生成，用户整段复制）

```markdown
# 投递单 · <任务名>（<日期>）

**收件**：TRAE / Zcode / OpenCode（三选一）
**项目根目录**：E:\AI小说创作

## 开始前必读（按顺序）
1. `docs/06-AI工作手册.md` → 2.1 准确性铁律 + 2.2 代码铁律 + 第 4 节常见误判
2. `docs/02-已实现清单.md` → 找到本任务对应行，记住当前状态
3. `docs/04-踩坑档案.md` → 搜索本任务相关关键词

## 任务
<一段话：做什么、做完长什么样。目标 agent 无项目上下文，必须自包含>

## 允许碰的文件
- <逐个列绝对路径>

## 禁止碰
- `docs/_archive/**`、`.workbuddy/memory/_archive/**`
- <其它 agent / 主力划定的地盘>

## 验收标准
- 改完跑什么命令 / 发什么请求 / 看什么输出 = 算通过

## 完成后必须做（漏一项 = 没完成）
1. `docs/02-已实现清单.md` 对应行更新状态，格式：
   `[2026-09-09] <改动摘要>（<agent> 实施，验证方式：…）`
2. `CHANGELOG.md` 顶部加一行：
   `- <日期> · <改动摘要>（<agent> 实施）`

## 回复格式
✅ 完成 / ❌ 卡住（卡在哪一步）
- 改了哪些文件
- 验证输出（贴最后几行）
- 有没有发现其他问题
```

**自检**：投递单要**短**（收件 agent 没有你的上下文，长单子它会丢）、**自包含**（绝对路径、必读文档、验收命令全给到）、**铁律前置**（它不需要懂项目哲学，照做就行）。

## 5.1 阶段规划收尾：归档与标记纪律（🔴 2026-09-15 新增，主力 AI 同样适用）

> **立此规则的原因**：`docs/03` 曾涨到 1335 行，已完成的实施记录与真实待办**混在同一层级、写法一模一样** ——
> 都是「### 标题 + 修复：…」。结果：**看不出到底做没做**，AI 和人都被误导（实测出 8 处文档失真 + 6 处「实施记录里埋着活遗留项」）。

**规则一：阶段规划做完，立即归档**

- **归档落点**：`docs/_archive/<阶段名>-实施记录归档-YYYY-MM-DD.md`（命名沿用先例 `Phase0-4与R-实施记录归档-2026-09-12.md`）
- **原地只留一行指针**，不留正文：「详细实施记录已移至 `docs/_archive/xxx.md`」
- **归档 ≠ 删除**：`_archive` 常规任务禁读，考古时可查

**规则二：没做完的，必须显式标出剩余项**

❌ **禁止写法**（这是本次混乱的直接成因）：
```
**修复**：切分 prompt 强化"优先 3~6 章/段" + 后处理合并（相邻且 embedding 相似的段自动合并）
```
—— 看着像已完成，实际**后处理合并从未实施**，且没有任何标记。

✅ **正确写法**：
```
**状态**：🟡 半完成
- ✅ prompt 已调为「每段 2~6 章」
- ❌ 后处理合并**未实施**（`grep` 无 merge/similar 命中）
```

**规则三：三要素齐全才算「做了」**

| 要素 | 要求 |
|---|---|
| **状态标记** | ✅ 已实测 / 🟡 半完成（写明剩余）/ ⬜ 未做 / 🔵 需用户手动验证 —— **不许用「修复」「解决」这类词代替状态** |
| **验证证据** | pytest 输出 / Playwright 截图 / curl 返回 / DB 查询。**读代码不算验证**（04-D2：文档会骗人，代码也会） |
| **落点同步** | 做完必须同步更新 `docs/03`（进度）+ `docs/02`（状态三要素）+ `CHANGELOG`，**不许只改一处** |

**规则四：遗留项集中登记，不散落**

未完成项统一登记到 **`docs/08-遗留问题总表`**（唯一清单）。**不许在实施记录里随手写「下轮修」就完事** —— 那是本次 6 处「活遗留项被埋在已完成段落里」的成因。

**归档前必查（防失传）**：该段落的**活遗留项是否已全部登记进 `08`**？没有 → 先登记再归档，否则等于失传（`_archive` 禁读）。


## 6. 验收（回到主力 AI）

把对方回的 `✅ 完成` + CHANGELOG 新增行 + 改动文件列表贴给主力 AI，它判断：

1. `docs/02` 是否真的更新了（状态 + 验证方式 + 日期三要素齐不齐）
2. 改动是否触碰了禁止清单（`git diff` 看实际改了哪些文件）
3. 是否违反 06 铁律（打印用户数据 / 流式里碰 DB session 等，grep 关键字）
4. 结论二选一：**通过** / **打回**（打回时写明具体问题，生成一张新投递单让原 agent 修）

## 7. 什么情况下才重新考虑"调度框架"

以下**同时**出现才值得重启调研（届时优先看 Agent Orchestrator 类，能原生驱动 OpenCode + git worktree 隔离）：

- [ ] 你开始**并发**投递（不等 A 回来就发 B），人工邮差成为瓶颈
- [ ] 多个 agent 频繁改**同一批文件**，投递单划地盘划不过来
- [ ] 主力换成了可 CLI 驱动的 agent（如直接主力就是 OpenCode / Codex / Claude Code），编排器够得着

当前阶段：**不投入、不建框架。投递单就是全部。**
