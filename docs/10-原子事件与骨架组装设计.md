## 1. 为什么换架构（一句话）

旧架构拿“整个桥段”算一个向量，只要入场方式/竞价内容/偷袭方向任一不同就组不出来；即使组出来，给 AI 的也是**大体相同的方案**。
新架构把桥段拆成**原子事件**，用**核心原子精确匹配**（不依赖阈值），逐环从不同书取不同的走法——**差异正是要借鉴的多样性**。

---

## 2. 三层架构

```
① 原子事件库（atomic_events）   最小可复用单元，自带起承转合     ~49 → 可无限增
② 变体库（atomic_variants）     每本书每段的具体走法 + 向量      随新书增长
③ 骨架库（event_skeletons）     原子序列 + 核心原子 + 可选环节    ~20 → 可增
                     ↓ 检索时组装（不落库）
             一份注入文本（用完即弃）
```

**关键：库里没有“模板”这个存量概念。** 模板是检索时现算的产物——所以不存在“需要重建的资产”，也就不会有删库事故。

## 3. 可扩展性设计（本文核心）

### 3.1 词表即数据，不是代码

四张表驱动全部行为，**新增任何东西都只是 `INSERT` 一行，不改代码、不重跑管线**：

| 想加什么 | 操作 | 对老数据的影响 |
|---|---|---|
| 新原子事件 | `INSERT INTO atomic_events` 一行 | **零影响**（老变体靠 `atomic_id` 外键，不冗余存名字） |
| 新大类 | `INSERT INTO atomic_categories` 一行（含 `sort_order`） | **零影响** |
| 新骨架 | `INSERT INTO event_skeletons` 一行 | **零影响** |
| 新题材（架空历史/都市） | 新原子/新骨架带 `scope_tags` 标题材 | **零影响**（老数据保持原题材标签） |

### 3.2 题材维度：`scope_tags` + `domain`

每个原子/骨架带两个维度字段：

- **`domain`**：题材领域（`xuanhuan` 玄幻 / `xianxia` 仙侠 / `history` 架空历史 / `urban` 都市 / `suspense` 悬疑 / `general` 通用）
- **`scope_tags`**：更细的场景限定（如"宗门""朝堂""商界""公门""娱乐圈"）

**检索规则**：`命中 = 目标题材的原子 ∪ 通用原子`。

这带来你问的那个能力——**换题材时**：
```
写架空历史 → 检索 domain IN (history, general) 的原子/骨架
  · 通用原子（单挑决斗/谈判交涉/追击追杀/集会宴请…）直接复用旧数据 ✓
  · 历史特有原子（朝堂论辩/科举应试/边关军议/赈灾平乱…）新增即可
  · 老玄幻数据的变体照常在库里，不影响，也不会被检索到
```
都市同理（商战谈判 / 舆论风波 / 职场倾轧 / 警匪对峙…）。

### 3.3 防膨胀机制（豆包提的“原子 vs 标签”要机制化）

新增原子前必须过两道闸，避免词表爆炸导致标注准确率下降：

1. **相似度预检**：新原子描述与现有原子算相似度，>0.85 → 提示“可能等同于 X，建议作为变体标签”
2. **标签优先**：以下类型**一律不做原子**，作为变体标签：
   - 手法类（扮猪吃虎 / 苦肉计 / 借刀杀人 / 幻术迷惑）
   - 状态类（伤心 / 富有 / 重伤）
   - 叙事手法（梦境 / 回忆闪回 / 旁白伏笔）
   - 单本书专属（如盗墓的"听雷"，作为 `G03 破阵解谜` 变体）

### 3.4 老数据零迁移的保证

- 变体表**只存 `atomic_id` 外键**，不存原子名/大类名 → 改名、分类调整都不影响已有行
- 标注错了 → **只改那一行的 `atomic_id`**（局部修正），不需要重标、不需要重建
- 旧 `plot_templates`（164 个整体模板）**保留不动**，作为回标素材；新旧双轨运行，验证通过后再切检索

## 4. 表结构（草案）

```sql
-- ① 大类（可增）
CREATE TABLE atomic_categories (
  id          TEXT PRIMARY KEY,          -- 'A'/'B'/... 或 'HIS' 等新题材大类
  name        TEXT NOT NULL,             -- 战斗 / 交易 / 社交 … 朝堂 / 商界
  domain      TEXT DEFAULT 'general',    -- 题材领域
  sort_order  INTEGER DEFAULT 100,
  note        TEXT
);

-- ② 原子事件（可增）
CREATE TABLE atomic_events (
  id           TEXT PRIMARY KEY,         -- 'A01' / 'C11' / 'HIS03'
  name         TEXT NOT NULL,            -- 4~8 字动词性短语，检索锚点
  category_id  TEXT NOT NULL,            -- → atomic_categories.id
  definition   TEXT,                     -- 一句话定义
  beat_start   TEXT,                     -- 起
  beat_mid     TEXT,                     -- 承
  beat_turn    TEXT,                     -- 转
  beat_end     TEXT,                     -- 合
  is_core_capable INTEGER DEFAULT 1,     -- 能否当骨架核心
  domain       TEXT DEFAULT 'general',
  scope_tags   TEXT,                     -- JSON：["宗门","朝堂"]
  status       TEXT DEFAULT 'active',    -- active / candidate（待定池）/ deprecated
  created_at   TEXT
);

-- ③ 变体（随新书增长；纯追加）
CREATE TABLE atomic_variants (
  id          TEXT PRIMARY KEY,
  atomic_id   TEXT NOT NULL,             -- → atomic_events.id
  book_name   TEXT,
  arc_ref     TEXT,                      -- '太荒吞天诀#51'
  segment_no  INTEGER,
  text        TEXT NOT NULL,             -- 具体走法（100~160 字，起因/经过/结果）
  tags        TEXT,                      -- JSON：["扮猪吃虎","苦肉计"]
  source      TEXT DEFAULT 'ai',         -- ai（自动追加）/ author（作者手加）
  is_variant_of TEXT,                    -- 变体族：指向最像的那条（sim 0.70~0.85 时填）
  hit_count   INTEGER DEFAULT 1,         -- 被多少条弧命中（sim ≥0.85 时累加，不新增行）
  quality     TEXT DEFAULT 'draft',      -- draft / reviewed / rejected
  created_at  TEXT
);
CREATE INDEX ix_variant_atomic ON atomic_variants(atomic_id);

-- ④ 骨架（可增）
CREATE TABLE event_skeletons (
  id           TEXT PRIMARY KEY,
  name         TEXT NOT NULL,            -- 拍卖会风云
  core_atomic  TEXT NOT NULL,            -- 核心原子 id（组装时必须相同）
  steps        TEXT NOT NULL,            -- JSON：[{atomic_id|slot, required, trigger, order}]
  domain       TEXT DEFAULT 'general',
  scope_tags   TEXT,
  evidence     TEXT,                     -- JSON：代表弧 ["斗破苍穹#5", ...]
  status       TEXT DEFAULT 'active',
  created_at   TEXT
);
```

**向量**：`atomic_variants` 走现有向量表（`source_type='atomic_variant'`），复用 `embedding_client` + 现有回填脚本，**无需新基础设施**。

  → **准确率 10/11 不能直接外推到逐章概括层，必须在该层重测。**


### 5.1 变体自动追加协议（AI 爬新弧时自动长库）

AI 标注一个段时做**两步判断**，第二步决定"是否新增变体"：

```
段摘要
 ① 选原子：给 59 个原子的表 → 选最贴合的一个
      · 都不合适 → 写入 candidate 池（待作者确认新增原子），本段不入库
 ② 判是否新走法：该段向量 vs 同原子下已有变体，取最高相似度 sim
      · sim ≥ 0.85 → **不新增**（同一走法的又一实例）：只在原变体上追加 arc_ref 计数
      · 0.70 ~ 0.85 → 新增变体，并标 is_variant_of = 最像那条（形成"变体族"）
      · sim < 0.70  → 真正的新走法 → 新增变体
 ③ 新增时必填：book_name + arc_ref + 走法文本(100~160字) + tags[]，标 quality='draft'
```

**三条保护（缺一就退化成垃圾场）**：

| 保护 | 规则 | 为什么 |
|---|---|---|
| 去重阈值 | ≥0.85 不新增，只计数 | 否则同一走法被反复入库，变体数无意义膨胀 |
| **溯源必填** | `book_name` 必须真实存在、`arc_ref` 必须能在 chapter_summaries 里找到 | 防 AI 编造来源（cast 溯源已踩过这个坑） |
| 标签优先 | 手法类/情绪类差异（"用苦肉计"）写进 `tags`，不构成新变体 | 否则同一走法被拆成几十条 |

**触发时机**：灌书/弧入库时**异步触发**（后台队列，每 20 个新弧或单书入库完成一次），不阻塞灌书主流程。

**作者手加**：UI 支持手动新增/编辑变体，`source='author'`；检索排序时作者手加的加权优先（最懂行的是作者）。变体表加 `source` 字段（`ai` / `author`）。

**变体数量预期**：一个原子下 5~30 条为健康区；>50 条说明去重阈值太松或该原子粒度不对（应拆原子）。

## 6. 检索组装协议

```
用户/计划："写个拍卖会风云"
 ① 识别核心原子：语义匹配 → 拍卖竞价（标签命中，非阈值）
 ② 取骨架：event_skeletons WHERE core_atomic='B01' AND domain ∈ (目标题材, general)
 ③ 逐环取变体：每环 top-k（k=2~3）atomic_variants
     · **去重键 = 走法相似度，不是书**：sim ≥0.85 视为同一走法，只留一条（docs/10 §5.1 同口径）
     · **「跨书」只是排序偏好，不是硬条件**：同环有跨书素材时，让不同书各占席位（避免单一作者腔调刷屏）；
       素材只有一本书时**照常全给**，不做任何降级、不报缺环
     · 落地：若某环只有 1 条走法 → 就是 1 条，注入块照常成立（「只有一条路」≠「不可用」）
 ④ 组装注入文本（每环标注来源书，供 AI 借鉴而非照抄）：
      【骨架】拍卖会风云（核心：拍卖竞价）
      【入场集会】A书：受邀赴会，遭门房刁难… ｜ C书：被迫卷入，被人当成货物押上台
      【拍卖竞价★】B书：抬价试探三巡… ｜ B书：闷声捡漏被识破 ｜ D书：以物抵价抬到底
      【谈判争端】…
      【伏击偷袭】（可选，触发条件：竞价出现搅局者）
      【追击追杀】【遁走逃离】
      【本环暂无素材】（确实无变体的环必须**显式标注**，不许静默省略——否则注入块会悄悄变薄）
      ⚠️ 以上均为**借鉴结构**，禁止照抄专名与原文
 ⑤ 用完即弃，不落库
```

**为什么去重键是「相似度」而不是「书」（2026-09-18 实测更正）**：
`跨书` 只是**保证「不同走法」在当前素材分布下的一个手段**，不是目的。原设计稿把手段写成了硬条件，实测被证伪：

| 原子 | 走法数 | 是否同书 | 两两相似度 | 判定 |
|---|---|---|---|---|
| `A02 擂台比试` | 4（太荒#22 段80~83） | **全部同一本书、同一条弧** | 0.075 ~ 0.183 | **4 条都是真正不同的走法** |
| `B01 拍卖竞价` | 3（九星#5 段19~21） | **全部同一本书、同一条弧** | 0.136 ~ 0.220 | **3 条都是真正不同的走法** |

→ 「同一弧里同一原子被展开成多段」是常态（报告 §0：平均每弧 4.11 段），这些段**天然就是同一环的多路走法**。
→ 拿「书数」当多样性指标是错的：按相似度口径，`A02` 现有 **4 路**、`B01` 现有 **3 路**，P2 的素材是够的。
→ 相似度阈值与 `atomic_variants` 的增量协议（§5.1）**共用同一套口径**（<0.70 新走法 / 0.70~0.85 变体族 / ≥0.85 只计数），全链路只有一个"什么算新走法"的定义。


**与 cast 的关系**：骨架各环可带"典型角色功能位"（拍卖 = 买主/卖主/主办/搅局者），复用现有 cast 体系映射到作者自己的角色。

### 8.1 素材真实形态的两条实测（2026-09-18，影响 P2 怎么做）

**① 真实的弧 ≠ 完整骨架，更像是"骨架某一环被展开成多段"。** 已标注 3 弧的原子序列：

| 弧 | 原子序列 | 形态 |
|---|---|---|
| 太荒吞天诀#22 外门大比夺魁 | `A02 → A02 → A02 → A02` | 单原子展开 4 段（首战 / 淘汰赛 / 半决赛 / 决赛） |
| 九星霸体诀#5 拍卖会争锋 | `B01 → B01 → B01 → C06` | 单原子展开 3 段 + 1 个后置环 |
| 北派盗墓笔记#25 西夏秘闻 | `G05 → B08 → B02` | 短链（3 环） |

**没有一条对得上 `S01~S06` 那种 7~9 环的完整链。** 含义：
- **P2 不该只演示"填满一条 7 环骨架"** —— 那会撞上大面积「本环暂无素材」，得不出结论；
- P2 更要演示的是「**某一环给 N 路走法**」——这才是素材的真实形态，也正是最稀缺、最有用的东西；
- 副产物：`A02` 被展开成 4 段的这个结构，暗示**骨架的"环"粒度可能偏粗**（"擂台比试"内部有"逐轮推进"的天然节拍）→ 记为一个观察，P2/P3 之后再看要不要引入"环内子节拍"，**现在不动**。

**② 单弧是有价值的，但定位是「某环的多路走法包」，不是「完整骨架实例」。**
只要一段弧里同一原子被展开成多段，这份素材立刻可用（无需等跨书配对）；
将来新弧入库时，同一原子下的走法自动累积（§5.1 自动追加协议）——
**所以"现在只有 1~4 路"是时间点问题，会在灌书过程中自愈，不需要专门补标去凑。**

## 11. 生成式骨架管线（2026-09-18 用户提案 · 🅿️ 待拍板）

> 本节记录用户提案**原文要点** + 与 §2/§5/§6/§8 现行设计的**对照** + **7 个待拍板项**（含建议默认值）。
> 拍板前不要按本节实施；拍板后本节升级为正式设计、并与 §5/§6 合并。

### 11.1 提案要点（五层）

```
① 原子事件切分（AI 按语义切章区间，不再复用既有 segment 边界）
     AI 读一章区间的概括 → 输出一串原子事件，每个带**章区间 + 该区间起承转合概括**：
       擂台比试：（1-5 章）+ 1~5 章的总概括（起承转合）
       拍卖竞价：（6-10 章）+ 6~10 章的概括
     · 增量：**每次运行自动跳过已组装成弧的章节**，不重头跑

② 单弧模板组装
     把连续的原子事件串成一条弧（= 单弧模板）：
       赶路迁徙 → 试炼考核 → 擂台比试 → 立威震慑 → 拜师结盟
     每本书都跑 → 得到多个单弧模板

③ 第一轮归并
     判据：**架构相似度 + 核心原子事件相同**（**核心可多个，一个不能少**；非核心**可缺**）
       A: 受托领命 → 赶路迁徙 → 试炼考核 → 擂台比试 → 立威震慑 → 拜师结盟
       B: 受托领命 → 赶路迁徙 → 试炼考核 → 擂台比试 → 立威震慑 → 诀别辞行
       → 合并为：受托领命 → 赶路迁徙 → 试炼考核 → 擂台比试 → 立威震慑 → 拜师结盟 → 诀别辞行
     合并后的形态 = **每环位挂多本书的走法**：
       受托领命：书B｜赶路迁徙：书A、书B｜擂台比试：书A、书B｜拜师结盟：书A｜诀别辞行：书B
     反例（不并入）：赶路迁徙 → 试炼考核 → 群殴混战 → 立威震慑 → 拜师结盟
       —— 该模板核心设为「试炼考核 + 擂台比试」，它没有擂台比试 → 核心缺一不可 → **它可以单独当一个模板**
     部分匹配（可并入）：受托领命 → 试炼考核 → 擂台比试 → 诀别辞行
       —— 缺的「赶路迁徙 / 立威震慑」都是非核心 → 可以加组合模板

④ 迭代归并：第一轮之后再次匹配归并（**但要加限制**）

⑤ 连续同原子：擂台比试 → 擂台比试 → 擂台比试 → 擂台比试
     这类连续情节**只设一个「擂台比试」为核心原子**，
     并告知 AI：可以用「擂台比试」的**多个变体**来连续铺多个相同原子事件
```

### 11.2 与现行设计对照

| 维度 | 现行（§2/§5/§6） | 提案（§11） | 评价 |
|---|---|---|---|
| 原子边界来源 | 复用既有 `segment` 边界 → 给段**打标签** | **AI 按语义切章区间** | ✅ 提案更好（见 11.3-①） |
| 原子事件的文本 | 让模型把 30 字段摘要**复述**成 100~160 字 | **AI 自己写该区间的起承转合概括** | ✅ 提案更好（见 11.3-②） |
| 骨架来源 | **手工先验** 6 个（S01~S06） | **数据涌现**：单弧模板 → 归并 | ✅ 提案可扩展性更高 |
| 核心原子 | 恰好 **1 个** `core_atomic` | **可多个，缺一不可** | ✅ 提案更准 |
| 非核心环节 | `required` + `trigger`（可选+挂载条件） | **可缺**（部分匹配） | ⚠️ 见 11.4-③（爆炸风险） |
| 归并判据 | 无 | **架构相似度 + 核心全覆盖** | 需定义「相似度」（见 11.4-②） |
| 迭代 | 无 | 多轮归并 + 限制 | ⚠️ 需定「限制」 |
| 连续同原子 | 未考虑 | 显式规则（算 1 核心 + 多用变体铺） | ✅ 实测支持（太荒#22 就是 `A02×4`） |
| 增量粒度 | `(arc_ref, segment_no)` 幂等 | **跳过已成弧的章节** | ✅ 同精神，见 11.4-④ |

### 11.3 为什么这个提案比现行设计好（用实测数据说话）

**② 的分母口径（`min` 而非 `max`）—— 2026-09-18 用提案自己的例子验出来的**：

归并的语义是「**短链被长链吸收**」，不是「两条差不多长」。若用 `max(len)` 作分母：
- 提案要并的 `D = 受托领命→试炼考核→擂台比试→诀别辞行`（4 环）vs `A`（6 环）：LCS = 3，
  `3/max(4,6) = 0.50` → **< 0.7 被误杀** ❌（与提案意图相反）
- 换成 `min`：`3/min(4,6) = 0.75` → **≥ 0.7 通过** ✅

所以口径是 `LCS / min(len)`。同时**不需要再加"LCS 绝对长度门槛"**：
防止"两条长序列只共享 2 个环却都有核心"的情形，已由「包含度 ≥0.7」自动拦住
（2 个核心 / 20 环 = 0.1，远低于 0.7）。

### 11.9 检索条数：别把「整体模板 top-k」和「骨架环位路数」混着调（2026-09-18）

问：既然「核心全中 + 序列被包含」会放宽命中面，那 top-k 要不要从 4 扩到 8？

**答案：现在不动旧链路的 4。** 三条依据：

1. **旧链路已"瘦身到只给节拍名"**（`plan_crud._plan_prompt`：模板只送 `name/logline/rhythm` + 各 phase 的 beat 名，

2. 🔴 **更关键：`03 §8.3` 已认定「top-k 语义近邻命中集稳定，库大只会稳定地雷同」，解法在检索层
   （排除最近用过 + 跨书组轮换），不在条数。** 而实测 grep：`plot_template_crud` / `plan_crud` 里
   **没有任何 exclude / recent / 轮换逻辑** —— 即该解法**尚未实现**。

   `template_id` 返回并存进计划，纯 SQL 即可），**再**谈扩到 8。反过来做没有收益。

**新架构不受这条约束**：它是**按环位取多路走法**，控制维度是「环位覆盖 × 每环路数」，

### 11.11 🔴 窗口化增量切弧协议（2026-09-18，用户提案 + 实测必要性）

#### 为什么必须要有它（实测证据）

**同样这 12 章，在不同窗口下切法不同**：

| 运行 | 输入范围 | 切出的弧 |
|---|---|---|
| 单弧小样本 | **只给** 1~12 章 | **2 条弧**：弧1「重生崛起之路」1~6｜弧2「血仇与班底」7~12 |
| 99 章窗口 | 1~12 章**在 99 章里** | **1 条弧**：弧1「赘婿崛起篇」**1~12** |

→ **AI 切弧依赖上下文窗口**：只给 12 章它会切两半；给了上下文它认出这是一个完整篇章。
→ 所以**绝不能"简单分批跑"** —— 批次边界处必然把横跨边界的一条弧切两半。
→ 用户给的解法是对的：**续跑时把「当前最后一条弧所占的章节」+ 后面 100 章一起发**，让那条弧在完整上下文里重切。

#### 协议（落地按此实现）

```
WINDOW = 40 章（🔴 **实测 40 可靠、100 不可靠**，见下方"窗口化验证"；40~50 均可）

首次：  win_start = 1
续跑：  win_start = 上次结果里「最后一条弧」的起始章        ← 回炉，防切断
        win_end   = min(全书末章, win_start + WINDOW - 1)
发送：  [win_start, win_end] 的**全部逐章概括**
返回：  atoms + arcs
锁定：  🔴 **只锁定「除最后一条弧之外」的所有弧**（最后一条下次回炉重切）
终止：  win_end == 全书末章 → 全部锁定，结束
```

**为什么这样不会切断**：若某条弧是 90~120 章，下个窗口是 `[90, 189]` —— 它被**完整**重切一遍；
若它实际该延伸到 135 章，新窗口看得出来；若该在 120 结束，新窗口也会得到同样边界。

**成本**：每次推进 = `WINDOW − 最后一条弧长度 ≈ 40 − 12 = 28 章`
→ 太荒 1009 章 ≈ **36 次窗口**；全库 3980 章 ≈ **142 次**（仍在魔搭 200 次/天额度内，1 天可跑完）。

**与 §11.4-④ 的关系**：④ 拍板"自动判断、无需手动传参" —— 判断依据就是本协议的窗口位置，
不是"该弧有原子行就跳过"（那样会切断弧）。

#### 🔴 落库方式：新弧用**新表 + 新弧号**，不动 `arc_no`

**"重做新弧"与"不断链"并不冲突** —— 只要新弧不复用旧弧号：

```
新表 atom_arcs         : id / book_name / arc_no_new / name / chapter_start / chapter_end
                         / core_atomics(JSON) / origin('merged'|'prior') / member_arcs / status
atomic_variants        : + chapter_start / chapter_end（原子区间）
                         arc_ref 指向**新弧**（如 '太荒吞天诀#N22'）
chapter_summaries.arc_no  ：**原样不动**（v3 篇章弧继续存在）
```

- ✅ 新弧按拍板**重做**（新边界、新弧名、多核心原子）
- ✅ `164/164` 个旧模板的 `arc_refs`（形如 `'九星霸体诀#3:炼药扬名风波'`）**一根线都不断** —— 它们指向旧 `arc_no`，新弧用新编号，互不干扰
- ✅ 可对比（旧弧 vs 新弧）、可回滚（删新表即回到现状）
- ✅ 不需要动 `chapter_summaries` 表结构（新旧弧都靠章区间定位）

#### 🧪 首次窗口化验证（2 步，太荒）——机制可用，但暴露一个必须处理的缺陷

|---|---|---|---|---|---|---|

2. **概括长度随原子变小而掉线** —— 窗口化下出现了大量 1~3 章的原子（seq 90~90、91~91、119~119），

#### 🧪 窗口化验证：**WINDOW 必须小**（40 可靠／100 失败）——2026-09-18 对照实验

| WINDOW | 窗口覆盖结果 | 结论 |
|---|---|---|
| **40** | 窗口 [1,40] ✅完整｜[33,72] ✅完整｜[60,99] ✅完整 → **3 窗 0 缺口 0 重叠** | ✅ **可靠** |

**结论**：🔴 **WINDOW = 40（推荐 40~50），不要用 100。**

**推荐：A 阶段只补九星 601~1200（600 章）+ 斗破 601~1200（600 章），不追 1800/1671。**

理由：§11 的效果验证**只需要"几本书都有可比体量"**，不需要"每本都灌满"。

| 方案 | 章数 | 墙钟 | 换来什么 | 风险 |
|---|---|---|---|---|
| **补齐到 1200（推荐）** | 1200 | **≈1.6 小时** | 3 本可比体量（太荒 1200 + 九星 1200 + 斗破 1200）→ **能立即验跨书归并** | 无 |
| 追满源文件 | 2271（九星 1800 + 斗破 1671） | ≈3 小时 | 多 1071 章 | 体量仍与太荒不齐（斗破满 1671 ≠ 1800） |
| 全库放量 | 7959 | ≈6 小时 | 全库可比 | 验证未过就先烧 6 小时，返工成本高 |

**关键洞察**：**逐章概括是"素材"，切原子才是"生产"**。素材灌满但不能用（§11 效果未验）＝白等；
反过来**先灌到 1200 × 3 本 → 立刻跑一轮切原子 + 归并 → 看跨书效果 → 再决定要不要灌满**，
每一步都有可回退的中间态。**这也符合用户一贯的「先小步验证、再放量」节奏。**

**唯一例外**：**太荒那 191 章缺口必须补**（章号跨到 1200 但只有 1009 章有概括）——
否则「太荒 1200 章」是虚的，切原子会出现 191 章的窟窿。见 §11.15。

### 11.15 ✅ 太荒「191 章缺口」是**假警报** —— 源书本身跳号（2026-09-19 查证，结论推翻）

**我先误判了，这里留完整证据链，因为这类误判很容易重犯。**

**第一印象（错）**：`chapter_summaries` 里太荒 `chapter_no` 跨到 1200，但只有 **1009 行** → 以为「191 章漏了概括」。
**实际查证（对）**：

| 检查项 | 结果 |
|---|---|
| 源目录 `小说/太荒吞天诀` 的 .txt 数 | **2276**（章号 1 ~ 2491） |
| 源文件**自身跳号**数 | **215**（`1~2491` 区间内缺 215 个号） |
| 库内章数 | 1009 |
| **「库内有、源没有」的章号** | **0** |
| **「源里有、库内没有」的章号（≤1200 内）** | **0** |
| `源 ∩ 库` | **1009** ← 完全一致 |

→ **源书本身就是跳号的**（网文实体书分卷/删章，2491 是"原书章号"而实际只有 2276 个文件）。
**库里 1009 行 = 源文件里 1~1200 的全部真实章，一章不漏。**
我之前列的那 191 个"缺口章号"（100,101,102,104…）**在源目录里压根没有对应文件**。

**🔴 修正后的正确结论**：
- **§11.12「太荒 1200 章 / 覆盖 1200/1200」的说法要改成「覆盖 1~1200 内的全部 **1009** 个真实章节，覆盖 100%」**
  —— 分子分母应该都用**源文件真实章数**，不是章号上界。
- **`_repair_partition` 吸收的 89 章不是"填补缺口"**，而是把**真实存在于源、但模型切窗时漏掉**的章并进相邻原子
  → 它是**真修复**，不是"给空气占位"。
- **不需要补跑任何章**。（我先前写的补跑命令 `--start 1 --end 1200` 会是**空跑**，已作废。）

> 💡 **元教训（重要，比结论值钱）**：**「章号上界」和「章数」在有跳号时会分离**，
> 而**跳号既可以来自数据缺失，也可以来自源书本身**。
> 判据不是 `max(chapter_no) - min + 1`，而是**「库内章号集合 vs 源文件章号集合」的对称差**：
> - 对称差为空 → 素材完整（无论章号长什么样）；
> - 有「源有库无」→ 才叫缺口，要去补；
> - 有「库有源无」→ 是脏数据，要查来源。
>
> 我做这步只花了**两条只读查询**，却避免了①空跑 37 分钟、②把"1009 章"误当成"缺 191 章"写进文档误导后续决策。
> **凡是"个数对不上"的异常，先做集合对称差，再谈补数据。**

#### ② 🐛 本轮修掉的一个真 bug：分区修复会**补出源里不存在的章**

**症状**：凡人验收 `越界 1 章` —— 第一个原子区间被写成 `1~5 章`，但**凡人源文件从第 2 章开始**（第 1 章缺失）。

**根因**：`_repair_partition` 的"首尾补齐"用的是**请求区间端点** `c0`（=1），
它并不知道"源里到底有没有第 1 章" → 于是**补了一章空气**。

**修法**（`cut_atoms_from_chapters.py`，两处）：
1. `_repair_partition(atoms, c0, c1, real_chapters=set[int]|None)` 新增参数，**必传**：
   - 端点先**吸附**到窗口内最接近的真实章（`c0=1 → 2`）；
   - 缺口吸收/首尾补齐**只在真实章号上做**（跳号处不补）。
2. 新增 **`0) 越界章号吸附`** 步骤（本次补的）：模型若切出**根本不存在**的章（不是"补"出来的，是它自己写的），
   - 起点越界 → 向后找第一个真实章；
   - 终点越界 → 向前找最后一个真实章；
   - 区间塌缩 → 就近吸成单个真实章；
   - 改动记 `clamped_from=[原区间]` + `span_repaired=true`，**不掩盖**。
3. `--repair-json` 抢救模式同步改：原来用 `MIN/MAX(chapter_no)`，现在查 `DISTINCT chapter_no` 拿真实集合，
   且统计口径改成「对**真实章集合**的缺/越」而非「对 `range(c0,c1)`」。

**修复后复核**：`分区修复：[2,600]（真实章 599 个）｜前缺 0 → 后缺 0｜吸收 0｜修重叠 0｜重叠残留 0｜**越界 0**`

### 11.19 ✅ 拍板②：动态 min 门槛（短宽长严）+ cross-first 边序（2026-09-19 用户拍板，当日实施）

> 针对 §11.18-④ 的斗×太桥（3环对3环 LCS=2 → min=0.67 差 0.03 被卡），用户提出
> 「弧短时要的是降低 min 来帮助弧扩充，弧长时需要限制扩充」——min 门槛改为**按环数分段**。

#### ① 拍板内容 → 实现（`merge_arcs_crossbook.py`）

1. **动态 min 分段**（分段依据 = **较长方的环数**，与「主环达到十个时」语义一致）：

   | 较长方环数 | min 门槛 | 语义 |
   |---|---|---|
   | < 5（短弧段） | **0.65**（`--min-short`） | 短弧取值离散（3 环只有 0.33/0.67/1.0），0.7 卡掉「只差一环」的自然档位 → 降 min 帮短弧聚合 |
   | [5, 10)（常规段） | **0.70**（`--min-mid`） | 拍板②原值 |
   | ≥ 10（长组段） | **0.85**（`--min-long`） | 使 5/6=0.83 **拦**、6/7=0.857 **过**（用户原话「主环十个时 5/6 没必要并、至少 6/7」） |

   实现：`min_threshold_for(la, lb, t_short)`；分段常量收进模块级 **`GATE` dict（唯一出处）**——
   🔴 不能用函数默认参数承载（Python 默认值 def 时绑定，运行期覆盖模块常量不生效）。
   `main()` 参数重构：`--min-ratio` 拆为 `--min-short/--min-mid/--min-long/--short-lt/--long-ge`，
   JSON 输出带 `gate` 字段；`diagnose()` 逐对算 `t_eff` 与 can_merge 同口径。
2. **cross-first 边序**（flat 模式新增 `--cross-first`）：跨书边**整体先于**书内边处理。
   动机：书内 1.0 分边先吸成巨组后，跨书 0.67 边轮到时对端已是巨组代表，
   被「单向核心（组核心=成员并集，越并越多）+ 长组段门槛」双重拦死——
   **斗×太 0.67 桥在弧对弧层面已通、却在组对组层面被堵**（插桩复现实录）。
   归并目的是跨书，书内聚合是副产品。
   🔴 **实现级教训：排序键一次写反**——`(-e[0], -e[1], e[2])` 里 cross=0（跨书）取负为 0、
   cross=1（书内）取负为 -1，升序下 **-1 排前面 = 书内优先**（比不开关还糟）。
   正确键：`(e[0], -e[1], e[2])`（cross 升序 + 组内分数降序 + merge 先于 reference）。
