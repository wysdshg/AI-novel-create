## 1. 分层结构

```
frontend/src                       Vue3 + Element Plus + Pinia
  api/      全部后端调用集中在此（http.js 拦截器自动解包 data，code≠0 自动弹错）
  store/    project.js（Pinia 全局态）
  views/    页面   components/ 组件
  utils/    nameGen|slash|templateParser|sse.js（SSE 统一读取，Phase 3.3）
  composables/ useSvgViewport.js（SVG 平移缩放，Phase 3.3）

backend/app
  routers/   17 个路由模块（HTTP 层，只做鉴参 + 调用 service）
  services/  业务逻辑 + CRUD（模型解析统一走 `model_crud.resolve_model`，Phase 3.4）
  core/
    config/   常量（温度预设 / 字数阈值 / DB URL）
    response/ 统一信封 ok/fail/paginated/not_implemented + SSE 帧编码 sse_event（Phase 3.4）
    database/ 引擎 + session + init_db（自动补列）
    context/  【上下文引擎】layers(取数) → budget(裁剪) → builder(装配)
    gateway/  【模型网关】base(抽象基类) + registry(注册表) + adapters(3 个真实适配器)
    workflow_engine/  DAG 执行引擎（engine/pool/nodes）
  models/    orm.py（23 张表）
  schemas/   Pydantic 请求/响应模型
```

## 2. 统一契约

- **响应信封**：`{code, message, data, trace_id}`，成功 `code:0`
- **路径前缀**：`/api/v1`；业务路径含 `{project_id}` 做数据隔离；全局资源用 `GLOBAL_PROJECT_ID="__global__"`
- **列表返回格式不一致（已知问题）**：作品/设定/SKILL/工作流返回对象或数组（视端点而定）；角色/势力/地点返回**纯数组**。前端已做兼容。
- **SSE**：本章生成与商讨对话用 `text/event-stream`，前端用原生 `fetch` 直连（绕过 axios 拦截器）

## 4. 上下文引擎（核心资产）

```
layers.py   取数 → Block(key, title, content, priority, order, min_chars, required)
budget.py   裁剪 → 按 priority 降序装入字符预算；装不下且 min_chars>0 则截断，
                   连最小值都不够则整块丢弃；全程留痕 debug()
builder.py  装配 → system = BASE_SYSTEM + SKILL块 + 去AI味块
                   user   = budget.render()（**本章任务压尾**，required=True 永不裁剪）
```

- **预算口径用字符不用 token**（中文 ≈1 token/1.5 字符，各家分词器不同，字符口径稳定零依赖）
- 三档：`tight` 8k / `standard` 32k（默认）/ `loose` 120k
- 层：`layer_world`(设定) / `layer_characters` / `layer_entities` / `layer_foreshadows` / `layer_stage_summaries` / `layer_recent_memories` / `layer_prev_chapter` / `layer_discussion`
- **小模型对末尾指令遵循度最高** → 重要内容一律压尾（本章任务、高优先级 SKILL）

### 设定库注入策略（B 方案，2026-08-11 落地）
- `build_setting_catalog` 只列「名称 + 摘要」作稳定前缀目录 → system 不爆
- 模型按需输出 `LOAD_SETTING:<id1>,<id2>` 一行 → 后端 Pass1 解析 → `fetch_settings_by_ids` 批量取详情 → Pass2 再生成
- 与参考文档的 `LOAD_REFS:<ids>` 平行，**不同 id 空间**
- ⚠️ 章节生成链路（`build_chapter_messages`）**仍未接 B 方案**，用 `layer_world` 的 full/relevant 模式

## 5. 模型网关

- 3 个真实适配器：`ollama_native`（本地 Ollama）/ `openai_compat`（OpenAI 兼容多厂商）/ `claude`
- 均用 `urllib.request`（stdlib，无 httpx 依赖）
- 新增厂商：继承 `core/gateway/base.py: BaseModelAdapter`，在 `registry.py` 注册 vendor 字符串，引擎层零改动
- API Key 从 `ModelConfigORM.api_key` 读，**无硬编码密钥**（实测 `/models` 返回已脱敏 `***ab8e`）
- ⚠️ 思考字段按厂商白名单组装，填错会 400 或导致正文丢失 → **见 04-B2**

### 5.1 模型解析 `model_crud.resolve_model(db, model_id)`（Phase 3.4 统一）

**所有需要「本轮该用哪个模型」的地方都调这一个函数**，不要再手写查询。语义：

| 入参情况 | 返回 |
|---|---|
| 传了 `model_id` 且该模型 `status == "active"` | **该模型**（尊重用户显式选择） |
| 传了 `model_id` 但模型不存在 / 非 active | 回退到**默认模型** |
| 没传 `model_id` | 默认模型 |
| 默认模型本身非 active，或库里无可用模型 | `None`（调用方须自行 `fail(...)` 提示去配置） |

调用点：`routers/chapter.py`、`routers/discussion.py`（`_resolve_model = model_crud.resolve_model` 别名）、
`routers/assist.py`、`services/config_command.py`、`services/ingestion.py`（摄取走 memory 角色兜底）。

> ⚠️ **抽本函数前这段逻辑在 4 处各写一份，且已漂移出真 bug**：`chapter.py` 原先直接用
> `db.query(ModelConfigORM).filter_by(id=body.model_id).first()`，**完全绕过 active 校验** ——
> 只要库里有这个 id，即使用户已把它停用/删除状态也照样拿来发请求，会 401/404 甚至打错模型。
> 现统一后行为一致且正确。回归保护见 `tests/unit/test_model_resolve.py`（14 例）。

## 6. 写后摄取（ingestion）流程

```
生成正文落库
  → 后台线程 _background_ingest（独立 session，按 id 重查）
     1. 抽取：模型按填空题式 JSON → parse_json_loose 容错（去围栏/首尾花括号/去尾逗号/全角转半角）
              → 仍失败则 fallback_extract 规则兜底（保证记忆链不断）
     2. 落库：upsert_chapter_memory（有新实体 → status=pending，否则 confirmed）
     3. 篇章摘要：append_article_digest（按 <!-- ch:N --> 标记追加，重生成只替换单段）
     4. 走向卡片：add_message(meta.type=post_chapter_directions)
     5. 阶段压缩：find_uncompressed_range 够 N 章（默认 10）→ compress_stage
```

- **每步独立 try，前步失败不阻断后步**
- `foreshadow_actions` 被抽取并存入 `ChapterMemoryORM`，**但不写入 `ForeshadowORM`**（**断链已于 2026-09-10 修复**，Phase 2.1：`foreshadow_crud.sync_from_actions` 每章自动回注）
- 新实体**不自动入库**，先 `pending` → 作者确认 → 才落 character/faction/location（重名跳过）
- **3.5 向量索引同步**（A 线，2026-09-10 新增，位于 3 与 4 之间）：`vector_index.sync_after_ingest` → 章级记忆（summary+hook+plot_points）与篇章摘要向量化入库；全链失败静默（无 key / API 失败只打日志），见 §6.5

### 6.5 向量检索层（A 线，2026-09-10 落地 A1+A2+A3）

```
embedding_client.py   bge-m3（硅基流动，纯 stdlib urllib）；key 三级查找：
                      env NA_SILICONFLOW_KEY > app_configs retrieval.siliconflow_key
                      > ModelConfigORM vendor=siliconflow；批量 ≤16/请求；L2 归一化
rerank_client.py      bge-reranker-v2-m3（同一 key，纯 stdlib）；批量 ≤64 自动分批 +
                      下标还原；失败抛 RerankError → 调用方降级保留原序
vector_store.py       VectorStore 协议（upsert/delete_by_source/search/count）
                      ├ SqliteVecStore   主实现：vec0 虚拟表 KNN（L2），回表过滤 project/source
                      └ BruteVectorStore 回退：纯 Python 余弦（无 numpy），vec_index 缺失时自动用
                      写路径 = SQLite 原生 INSERT OR REPLACE（同 PK 幂等，绕开 ORM UoW 排序问题）
vector_index.py       编排：段落切块(500字) → embed → 入库；index_reference_doc /
                      reindex_project_references(存量补建) / sync_after_ingest(摄取钩子) /
                      search_similar(对外检索口)；全部失败静默返回 0/[]
```

- **表**：`vector_chunks`（ORM，source of truth，向量存 JSON）+ `vec_index`（vec0 虚拟表，加速索引可重建；init_db 自动建，失败不阻断启动）
- ⚠️ **vec_index 是全局表**（所有作品 + 全局资料池共用）：KNN **必须**带 `project_id`/`source_type` 辅助列元数据过滤（`WHERE embedding MATCH ? AND k = ? AND project_id = ? AND source_type = ?`）。只靠「取多了再回表筛」会被更大的分区挤占 top-k 导致静默漏召回（见 04-C7）。启动时 `_ensure_vec_index` 检测旧 schema → 删表重建 → 从 `vector_chunks` 自愈回填
- **source_type**：`ref_doc`（参考文档）/ `chapter_memory`（章级记忆）；project_id 强隔离
- **实体图一跳扩展（A5）**：`entity_graph.expand` 从种子实体（本章要点/商讨命中）走一跳 —— relations 双向（按 strength 降序）、factions.members/leader_id 归属、locations.related_ids；扩展出的实体提升为「本章重点实体」，交给各 layer 全量渲染。**不递归**；trace 进 `context` 事件的 `entity_graph` 字段；开关 `retrieval.graph_expand`（默认开）
- **融合检索**：`pick_relevant`（reference_crud）= 关键词 score_reference + 向量 search_similar → RRF 融合（k=60）→ **rerank 重排**（RRF 取 top_k×3 候选，bge-reranker 逐对打分取 top_k；失败降级 RRF 序）；向量通道为空时行为与旧版一致；明细含 kw_score/vec_score/rerank_score/channels
- **生命周期**：上传/导入参考文档 → 自动建索引；删除 → 同事务清向量；`POST /projects/{pid}/references/reindex` 存量补建
- **总开关**：app_configs `retrieval.vector_index`（默认开）；**未配 key 时一切静默跳过，生成链路与现状完全一致**

## 7. SSE 事件序列

**章节生成** `POST /chapters/generate`
```
start → context(读了哪些块/资料) → thinking → chunk* → stopped(复读截断)
      → validate(AI味报告) → saved(落库) → ingest_start(async:true) → done
                                            └─ 摄取在后台线程，不阻塞 done
```

**商讨** `POST .../discussion/chat` · `POST /discussion/global-chat`
```
context(项目商讨才有) → [refs(加载了哪些资料/设定)] → thinking* → chunk* → done
（Pass1 非流式探测是否需要 LOAD_REFS/LOAD_SETTING → Pass2 流式生成）
```
> 两个入口**共用** `discussion.py::_stream_two_phase()`（2026-09-10 Phase 3.2 合并，原先各存一份 80 行）。
> 四条分支：① 短路——Pass1 直接作答（只 1 次调用，无 refs 事件）；② 两阶段——Pass1 请求参考 → 发 `refs` → Pass2 流式；
> ③ Pass1 异常 → 降级单次流式；④ 适配器无 `chat` → 单次流式。
> `assistant_text`/`assistant_thinking` 以**引用**传入供调用方 `finally` 落库；返回观测 dict 供 `discussion_load_logs`。

**工作流** `POST /workflows/{id}/runs`
```
node_start / node_end / … → run_end（终帧：run_id + status + outputs + duration_ms）
                          失败时先 error 再 run_end(status=failed)
```
> ⚠️ 工作流的**终帧是 `run_end`，不是 `done`**（2026-09-10 核对代码修正；本节原先误写为 `done`）。
> 前端监听结束一律按 `run_end` 判断。

> **后端编码统一在 `core/response.py::sse_event(event, payload)`**（2026-09-10 Phase 3.4）：
> 原先 `chapter.py` / `discussion.py` / `workflow.py` **各写一份逐字相同的 `_sse()`**（3 份定义）
> 外加 15 处**手拼裸帧**（如 `f"event: done\ndata: {}\n\n"`），已全部收敛到这一个函数。
> 两条契约由函数内部保证，调用方无需再操心：
> - **`ensure_ascii=False` 不能漏** —— 否则中文正文全变成 `\uXXXX` 转义（体积翻倍且前端要再解一次）
> - **帧尾必须是空行 `\n\n`** —— 前端按 `split('\n\n')` 切帧，缺空行会把相邻两帧粘成一帧
>
> `tests/unit/test_sse_stream.py::test_no_raw_sse_frames_left_in_routers` 会扫描 `app/routers/*.py`
> 禁止再出现裸帧字面量，防止回潮。

> **前端读取统一在 `utils/sse.js`**（2026-09-10 Phase 3.3）：以上 4 条流原先各手写一份
> 「getReader + TextDecoder + split('\n\n') + 正则抠 `event:`/`data:`」，已合并为
> `readSseStream(resp, onEvent, {signal, timeoutMs, tolerant, errorPrefix, stoppedMessage})`。
> 调用方只需自己 `fetch`（method/body 各异）；**HTTP 状态校验、超时中止、`GenerationStopped`
> 语义由本函数统一负责**。`tolerant:false` 供工作流（畸形数据直接抛），默认 `true` 供长对话流。
> ⚠️ 各接口的 `errorPrefix` 必须传对（如「章节生成接口」），这是 400/500 时用户看到的文案。

## 9.1 `app_configs` 行为开关一览（改这些不用改代码）

运行时可调，存 `app_configs` 表；代码里读 `app_config.get(db, KEY_xxx)`，**默认值即旧行为**。

| 键 | 默认 | 作用 | 影响 LLM 调用数 |
|---|---|---|---|
| `context.budget_level` | standard | 上下文预算 tight/standard/loose | — |
| `db.write_mode` | review | 抽取后预览 / 直接落库 / 模型自主调工具 | — |
| `humanize.inject_on_generate` | True | 生成时前置注入去 AI 味规则 | — |
| `humanize.scan_after_generate` | True | 生成后跑 AI 味检测（**本地算，不调模型**） | 0 |
| `memory.ingest_after_generate` | True | **写后摄取总开关**（关掉 = 抽记忆+走向+伏笔+篇章摘要+概览全不做） | 省 2 |
| `memory.extract_enabled` | True | 摄取时用 LLM 抽章级记忆；**关掉改走 `fallback_extract` 规则兜底**（记忆仍落库、链路不断，只是摘要不精炼） | 省 1 |
| `memory.aggregate_overview` | True | 摄取时用 LLM 精炼**篇级**概览；关掉改纯拼接（概览页仍有内容） | 省 1 |
| `memory.push_directions_to_chat` | **False** | 章后走向建议推成对话卡片。**2026-09-13 用户拍板下线**：不再每章自动推（省心）；抽取 prompt 的 `next_directions` 字段与推送代码全保留，恢复 = 设置页开 True 或 DB 落 `{"key":"memory.push_directions_to_chat","value":true}` | — |
| `memory.stage_compress_every` | 10 | 每 N 章滚动压缩阶段摘要（**不满 N 章不触发**，即单章/2-3 章测试天然免费） | 0 |
| `memory.recent_chapters` | 3 | 注入下一章的最近章级记忆条数 | — |

**一次全链路（生成 1 章）的 LLM 调用构成**：正文生成 **1**（阻塞）+ 记忆抽取 **1**（后台）+ 篇级概览聚合 **1**（后台）+ 实体抽取（走 `/command` 时 **1**，可选）。卷/小说级概览在自动模式下只拼接不调 LLM；阶段压缩不满 10 章不触发。

**测试省调用**：`test_full_chain.py --rounds 5 --verify-db` → 第 1 轮全跑、2~5 轮 `ingest_level=none`，5 轮从 15 次降到 7 次。

## 9.2 日志约定（Phase 0.2 / 3.5 固化）

统一入口 `core/logging_config.py`：`setup_logging()` 幂等初始化根 logger，级别由 `NA_LOG_LEVEL` 覆盖（默认 INFO）；`httpx/httpcore/urllib3/sqlalchemy.engine/watchfiles` 压到 WARNING 免刷屏。
模块内约定 `logger = logging.getLogger(__name__)`。

### `except Exception` 铁律（Phase 3.5，有测试护栏）

`backend/app/**/*.py` 里的 broad-except **必须满足以下三者之一**，否则 `tests/unit/test_except_logging.py` 会红：

| 情形 | 该怎么做 |
|---|---|
| **吞掉异常继续跑**（`pass` / `continue` / `return 降级值`） | **必须** `logger.warning(...)`，并带上能定位的上下文（关键 id、原始片段、"降级成了什么"） |
| **异常要转成用户可见文案**（`fail()` / SSE 消息 / `NodeResult(failed)`） | **再加** `logger.exception(...)` —— 前端只有 200 字截断文案，**堆栈只有日志里有** |
| **异常交给上层** | `raise`（含 `raise X from e`）即可，由上层负责记录 |

其他细则：
- **每个新连接都会触发**的位置（如 sqlite-vec 扩展加载）用 `logger.debug`，否则 warning 刷屏；排查时设 `NA_LOG_LEVEL=DEBUG`。
- 确实不该记的极少数情形，在 `except` 行加 `# noqa: BLE001` 并在**紧邻注释里写明原因**（护栏认 `noqa` 豁免，但人工评审时会看理由）。
- **`# noqa: BLE001` 本身不是"免记日志"的通行证**——它只免 lint 告警。判断标准是"出问题时有没有线索可查"。

> 清理前全项目实测 107 处 broad-except / 53 处静默；清理后静默 0 处。**新写代码若一静默，护栏立刻失败。**

> ⚠️ 唯一豁免：`core/logging_config.py`（日志基础设施自身）。它的 except 分支**不能调用 logging** ——
> handler 还没建好时再记日志会二次失败，异常 hook 里再记会递归，退出阶段 handler 可能已 shutdown。
> 豁免登记在 `tests/unit/test_except_logging.py` 的 `_EXEMPT_FILES`，**其他模块不适用**。

### 9.2.1 日志落盘与崩溃取证（2026-09-10 新增）

**背景**：后端出现「运行着运行着就挂了」但**事后无任何证据**——原先只输出到控制台，终端窗口一关就查无此案
（项目根下那几个 `.log` 全是 8 月的旧文件）。故补上落盘 + 关键取证信息。

**文件位置**：`backend/logs/`（已 gitignore）

| 文件 | 级别 | 轮转 | 用途 |
|---|---|---|---|
| `backend.log` | INFO+ | 5MB × 5 | 全量。看请求流水、启动/退出、心跳 |
| `error.log` | WARNING+ | 2MB × 3 | **排查先看这个**：只看异常/降级，附完整 traceback |

**环境变量**（都可选）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `NA_LOG_LEVEL` | `INFO` | 日志级别；排查 SQL/细节时设 `DEBUG` |
| `NA_LOG_DIR` | `backend/logs` | 日志目录 |
| `NA_LOG_FILE` | `backend.log` | 主日志文件名 |
| `NA_HEARTBEAT_SEC` | `300` | 心跳间隔（秒），设 `0` 关闭心跳 |

**启动方式不用改** —— 只要走 `main.py`（`python dev.py` 或 `uvicorn main:app` 都一样），落盘自动生效。

**★ 挂掉后怎么判读（这是本次改造的核心价值）**：

| 日志里的现象 | 结论 |
|---|---|
| 有「进程启动」但**没有**「进程退出」 | 被**强杀**（taskkill /F、任务管理器、关机/重启）或硬崩溃 —— `taskkill /F` 不触发 `atexit` |
| 「启动 / 退出」**成对**出现 | **优雅退出**（Ctrl+C / uvicorn 正常关闭） |
| `CRITICAL [uncaught] 已捕获未处理异常（主线程…）` | Python 层异常导致退出，**下方附完整 traceback** |
| `CRITICAL [uncaught] …（后台线程 thread='xxx'）` | 某个后台线程炸了（写后摄取/工作流/SSE 都是线程） |
| `INFO [app.heartbeat]` 的**最后一条时间** | **进程确切死亡时间**；`RSS=` 若持续上涨 → 内存泄漏 |

**排查示例**：
```
# 先看有没有异常
type backend\logs\error.log

# 看这次的启动/退出是否成对、心跳停在哪
findstr /C:"进程启动" /C:"进程退出" /C:"heartbeat" backend\logs\backend.log
```

> **前端（vite）日志**：`npm run dev` 的输出去向取决于启动方式，默认只在终端。
> 需要落盘可自行重定向，例如：`npm run dev > ..\logs\frontend.log 2>&1`（Windows PowerShell 用 `*> ..\logs\frontend.log`）。
> 后端挂了通常后端日志已足够定位；前端 vite 崩溃一般会直接在终端刷出明显报错。
